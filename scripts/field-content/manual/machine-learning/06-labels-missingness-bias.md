# 06 · 空白标签背后藏着三种不同事实

> 数据生成图里有 318 份合同没有得到续费标签。工程同事提议把空值填成 0，理由很直接，付款表里没有成功记录，自然就是没有续费。团队抽查十份合同以后，发现有人完成了线下转账，有人迁移到了新账户，还有人的付款记录晚了两天才同步。一个空格正在替三种事实作答。

## 先不要填空，先问答案去了哪里

318 份空标签看起来像一种数据质量问题，抽查却显示它们至少经过了三条不同路径。

合同 3310 的企业客户按时完成线下转账，付款没有进入统一支付表。它在现实里续费成功，当前标签系统却看不见。

合同 4482 在到期前迁移到新账户，旧合同停止观察。新账户后来续费，旧合同既不能确认为成功，也不能确认为失败。

合同 5901 使用正常支付渠道，结果窗口结束时仍未付款。它是真正的未续费，只是夜间批处理异常，训练表没有写入 0。

把三者都填成 0，会引入两份错误负例。把三者全部删除，又会让企业客户、迁移用户和同步异常时段从训练数据中消失。缺失处理必须回到标签怎样产生，不能只看单元格现在是什么。

第二章已经说明标签要等观察窗成熟。本章继续处理另一层问题。窗口成熟以后，现实结果是否被系统看见，看到的记录能否正确关联，又能否按同一规则变成训练标签。

## 标签把现实压缩成可计算的记录

团队关心合同是否延续了付费关系。这个业务概念叫作目标构念。它不能直接塞进数据表，需要选择一个可以观察和计算的信号。

当前标签写成“合同到期后七天内是否出现成功续费付款”。这是一种代理标签。它把付费关系压缩成统一支付系统里的成功记录，便于自动计算，却会漏掉线下转账、账户迁移和延迟对账。

几乎所有真实任务都需要代理测量。团队要知道代理与目标构念之间隔着哪些条件。

| 想知道的现实 | 当前代理怎样测量 | 可能失真的地方 |
|---|---|---|
| 合同是否继续付费 | 七天内统一支付系统出现成功记录 | 线下转账与跨账户迁移不可见 |
| 用户是否愿意续费 | 最终是否付款 | 支付故障可能掩盖真实意愿 |
| 人工提醒是否有效 | 被提醒合同后来是否续费 | 高风险对象更容易被提醒，缺少可比对照 |

三行不能混成一个问题。模型预测最终付款，可以帮助安排支付检查；它无法仅凭这个标签判断用户意愿，也不能证明某次提醒产生了效果。标签名称若只写 `churned`，这些边界很快会被忘掉。

合格的标签规范应当使用可观察事实命名。它要写明对象、事件、窗口、来源系统、迟到规则和不可确认条件。名称越像抽象概念，越需要补充测量说明。

## 沿五个站点追查一条标签

合同 3310 的现实结果要经过五个站点，才能变成训练表里的 1。

```text
发生付款
   │
   ▼
支付渠道留下事件
   │
   ▼
事件同步到数据平台
   │
   ▼
付款与原合同正确关联
   │
   ▼
判定规则在窗口结束后生成标签
```

每一站都可能让答案丢失或改变。

事件没有发生，才接近真正的负例。事件发生但渠道没有记录，属于采集缺口。记录存在却同步失败，属于传输缺口。数据已经到达，但账户迁移导致关联不到原合同，属于实体解析缺口。所有记录都齐全，规则却在第七天上午运行，漏掉当天晚些时候的付款，属于判定缺口。

调查空值时，团队需要为每一站准备一个可以核对的状态，最终标签只是其中一项。

| 站点 | 建议保留的状态 | 合同 3310 |
|---|---|---|
| 现实事件 | 是否有续费证据 | 线下转账凭证存在 |
| 来源记录 | 哪个系统捕获事件 | 财务对账系统 |
| 数据同步 | 何时进入分析平台 | 尚未接入每日同步 |
| 实体关联 | 能否关联原合同 | 可通过订单号关联 |
| 标签判定 | 规则版本与运行时间 | 当前规则未查询财务系统 |

这张表让修复方向变得具体。合同 3310 不需要更聪明的填充值，它需要扩充来源与关联逻辑。合同 5901 则需要修复批处理并重新生成。若无法确认合同 4482 的观察是否完整，它应保留为不可确认状态，不能被算法自动猜成 0。

## 缺失怎样透露业务流程

把 318 份合同按渠道分组，团队得到下面的结果。

| 渠道 | 合同数 | 标签缺失数 | 缺失比例 |
|---|---|---|---|
| 统一支付 | 8200 | 41 | 0.5% |
| 企业线下 | 900 | 171 | 19.0% |
| 新账户迁移 | 430 | 92 | 21.4% |
| 其他渠道 | 470 | 14 | 3.0% |

缺失显然没有均匀散落。它与支付渠道和迁移路径强相关。删除空标签以后，训练集会大量失去企业线下与迁移合同。模型学到的主要是统一支付用户的规律，却可能被部署到所有合同上。

分析缺失时常见三个名字。若是否缺失与对象及结果都无关，可以近似称为完全随机缺失。若已观察到的渠道、地区或套餐足以解释缺失，可以称为条件随机缺失。若缺失仍与未观察到的结果或过程本身有关，例如越可能失败的企业越不愿提交线下凭证，就属于非随机缺失。

这些名字用于区分处理方法所依赖的机制，不能凭感觉贴到某一列上。

完全随机的少量缺失有时可以删除，主要损失是样本量。已知渠道导致的缺失，可以在明确假设下分层、加权或补采。未观察结果本身影响缺失时，单靠现有表格通常无法消除偏差，需要新增数据、抽样复核或做敏感性分析。

当前案例已经能够排除“随手删除不会改变总体”的想法。至于企业线下合同的缺失能否被已知字段充分解释，还需要额外抽样和业务调查。把缺失机制写成假设，比把一个统计术语写成事实更诚实。

## 观测更完整的人会替所有人发言

运营团队只详细检查高风险名单。进入名单的合同会留下支付失败类型、客服判断和建议动作，未入选合同只有最终付款结果。

若团队用“人工确认的支付问题”作为新标签，训练样本会天然集中在旧模型认为高风险的人。旧模型没有选中的合同缺少同类审核，团队无法知道它们是否存在支付问题。

这会形成选择偏差。进入可标注集合的机会与旧模型分数相关，旧模型分数又与许多用户特征相关。新模型看见的是旧政策筛选后的世界。

不同群体被系统看见的程度也可能不同。企业客户更容易走线下流程，老年用户更可能通过电话完成服务，某些地区的数据同步更慢。总体缺失率只有 3%，不代表每个群体都拥有 97% 的可见性。

标签审计至少要同时查看三类切片。

- 业务路径切片，包括渠道、产品、地区和人工处理流程。
- 人群切片，包括任务关心且允许分析的用户群体。
- 时间切片，包括版本发布、故障、节假日和规则变更前后。

切片要定位谁的现实更难被当前系统测量，以及这种不可见性会不会改变模型使用后的利益与负担。总体平均表回答不了这个问题。

## 人工标签也有自己的生产线

有些支付问题无法从日志判断，需要客服阅读工单后标注“用户主动拒绝”“支付技术故障”或“暂时无法确认”。同一条工单交给两个人，答案可能不同。

团队随机抽取 120 条工单，让两位标注员独立判断。两人在 84 条上给出相同类别，36 条存在分歧。直接保留第一位标注员的答案会隐藏规则含糊，也会让模型学习个人习惯。

这时先不要追求一个神奇的一致性数字。团队更需要查看分歧集中在哪些边界。

| 分歧类型 | 例子 | 规范需要补什么 |
|---|---|---|
| 类别边界含糊 | 用户说“最近太忙，过几天再看” | 明确暂缓与主动拒绝的判定条件 |
| 证据不足 | 工单只有一句“无法付款” | 允许标记不可确认，不强迫二选一 |
| 多个原因并存 | 价格异议同时伴随银行卡失败 | 规定主标签与附加标签的优先级 |
| 时间点不一致 | 一人看首次工单，一人看结案记录 | 固定标注时可使用的信息范围 |

规范修改以后，重新抽样复标，观察分歧是否下降。仍有合理争议的样本可以保留多位标注、软标签或不确定状态。把争议强行压成单一真相，只会让数据看起来整齐。

标注质量还要随时间复查。产品话术变化、客服流程调整或新支付方式上线，原有示例会逐渐失效。标签规范需要版本号，训练数据要记录使用的规则版本。

## 给标签建立一份能执行的规范

续费任务最终形成下面的标签卡。

| 项目 | 当前约定 |
|---|---|
| 目标构念 | 一份合同是否延续付费关系 |
| 代理标签 | 到期后七天内出现可关联的成功续费付款 |
| 正例 | 窗口内统一支付或已核对线下支付成功 |
| 负例 | 完整观察至窗口结束，且所有接入渠道均无成功付款 |
| 不可确认 | 账户迁移、观察中断、来源未接入或对账尚未完成 |
| 数据来源 | 统一支付、财务对账、合同迁移映射 |
| 迟到规则 | 窗口结束后再等待两天完成同步，超期修正进入下一版 |
| 实体关联 | 订单号优先，迁移映射次之，不使用姓名模糊匹配自动定案 |
| 人工标注 | 双人独立判断，争议样本进入复核，允许不可确认 |
| 必看切片 | 渠道、地区、合同类型、处理政策与月份 |
| 版本触发 | 支付渠道、迁移流程、窗口或判定规则变化 |

这份规范将“0、1、空白”还原成一套可检查的测量过程。模型训练前，团队可以报告各状态数量、切片差异与人工分歧。上线后，标签质量异常也能追到具体站点。

填充、删除、重采样和加权仍然是可用工具，但它们排在机制调查之后。工具只能在写清假设时工作。若缺失来自一个完全未记录的结果过程，复杂的插补模型也只是把现有观测规律复制到未知区域。

你可以从自己的项目里挑一个最常用标签，先把名称换成一句可观察的事件描述。随后画出它的五个站点，找十个空值和十个边界样本逐条核对。调查结束以后再决定哪些能修复、哪些要删除、哪些必须保留为未知。

## 下一章让测试集代表真正的未来

标签规范已经把可确认样本与未知状态分开。现在还不能把所有已确认样本随机打散。若同一客户、同一月份或同一地区的近似记录同时进入训练和测试，实验仍会得到一个过于容易的未来。下一章会从系统准备面对的场景反推切分协议。
