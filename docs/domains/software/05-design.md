# 05 · 分层、状态机与幂等

<div class="lesson-meta"><span>SW12—SW13</span><span>必修核心</span><span>预计 2 × 60 分钟</span><span>前置：SW09—SW11</span></div>

## 本章可观察目标

你能把业务规则与框架/数据库细节分开；用显式状态机描述生命周期；为写操作、队列消费和外部回调建立幂等边界。

## SW12 · 分层不是文件夹数量

一个实用的最小分层：

```text
接口层：HTTP/CLI/消息，解析并验证输入
应用层：编排一个用例，控制事务与权限
领域层：业务规则、实体、值对象、状态转换
基础设施：数据库、队列、模型、第三方 API
```

边界的判断标准是**变化原因**。更换数据库不应改库存规则；修改 HTTP 路径不应改状态机。小项目无需制造几十个抽象，但要把副作用集中在可替换、可测试的位置。

依赖倒置的直觉：不是业务代码去询问“PostgreSQL 怎么查”，而是业务声明“我需要按 ID 取订单”，数据库适配器满足它。这样测试业务规则时不必启动所有基础设施。

## SW13 · 状态机、幂等与一致性

布尔字段组合很快产生非法状态。显式状态机列出状态、允许事件、守卫条件和副作用。

| 当前状态 | 事件 | 条件 | 下一状态 | 副作用 |
|---|---|---|---|---|
| queued | start | worker 获得租约 | running | 写 started_at |
| running | succeed | 结果已持久化 | succeeded | 发布完成事件 |
| queued/running | cancel | 用户有权限 | cancelling | 写取消意图 |
| succeeded/failed | cancel | — | 拒绝 | 返回稳定错误码 |

幂等意味着同一意图执行多次，业务效果与一次相同。常见做法：客户端提供幂等键；服务端以“租户＋键”建立唯一约束；保存第一次结果；参数不同却复用键时拒绝。它与重试配套，但不等于所有响应字节完全相同。

跨数据库与消息系统无法天然一个事务时，可使用 transactional outbox：业务写入和待发送事件进入同一数据库事务，后台发布器重复发送，消费者幂等。不要先发消息再提交数据库。

## 练习：状态转换表

为报告生成任务写出不少于 6 个状态、10 个事件、非法转换和每次转换的持久化/消息副作用；再设计创建、回调和消费三个幂等键。让 AI 生成实现后，逐条用表格反查遗漏。

常见误区：用多个布尔字段表达生命周期；状态在内存变了但事务没提交；副作用发生后状态写入失败；把“请求 ID”误当业务幂等键；消费者处理完成前确认消息。
