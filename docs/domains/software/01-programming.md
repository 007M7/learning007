# 01 · 程序、类型、模块与 Git

<div class="lesson-meta"><span>SW01—SW03</span><span>必修核心</span><span>预计 3 × 45 分钟</span><span>前置：无</span></div>

## 本章可观察目标

你能沿着“输入 → 分支 → 函数调用 → 输出/副作用”解释一段代码；能写出函数与 API 的数据契约；能用模块边界和 Git 提交约束 AI 的改动范围。

## SW01 · 程序如何执行，而不是“代码看起来像什么”

源代码是给人读的指令，运行时才把它变成实际动作。阅读代码时先追踪四件事：**输入从哪来、状态在哪里改变、可能走哪些分支、结果去哪里**。函数调用形成调用链；异常若未被本层处理，会沿调用链向上传播。

```python
def reserve(stock: int, count: int) -> int:
    if count <= 0:
        raise ValueError("count must be positive")
    if stock < count:
        raise OutOfStock()
    return stock - count
```

不要只问 AI“解释这段代码”。应问：`列出所有输入类别、正常返回、异常、状态写入和调用者必须处理的情况`。上例至少有合法扣减、非法数量、库存不足三个路径。

::: tip 调试最小闭环
先复现 → 缩小到最小输入 → 观察事实（变量、日志、堆栈）→ 提出假设 → 只改变一个条件 → 重新验证。打印很多日志但没有假设，不等于调试。
:::

## SW02 · 类型与契约

类型是在代码执行前后对“允许出现什么数据”的约束。它不能证明业务正确，但能把一批错误提前变成可见反馈。

| 层次 | 例子 | 仍需补充的约束 |
|---|---|---|
| 基础类型 | `count: number` | 是否整数、范围、单位 |
| 结构类型 | `{id, status}` | 必填字段、枚举、版本 |
| 业务类型 | `OrderId` | 不能与 `UserId` 混用 |
| 边界 Schema | JSON Schema / OpenAPI | 外部输入仍要运行时验证 |

**静态类型不会验证网络上收到的 JSON。** 外部数据必须先经过运行时 Schema，再进入业务逻辑。可空值也要有语义：`null` 是“明确没有”，字段缺失常表示“未提供”，不要让 AI 随意互换。

## SW03 · 模块、依赖与 Git

模块把共同变化的代码放在一起，并只暴露必要接口。依赖方向应从易变的外部细节（数据库、模型供应商）指向稳定业务规则的反方向：业务层定义所需接口，适配器实现接口。

Git 保存的是提交构成的有向历史，不是网盘快照。一次好提交应：范围单一、能解释原因、可测试、可回退。让 AI 改代码前先要求它列出文件清单和不修改的边界；完成后查看 `git diff`，而不是只听总结。

```text
需求/测试 → 业务模块 ← 数据库适配器
                    ← HTTP 适配器
                    ← 模型适配器
```

## 练习：审查一次 AI 改动

选择一个不超过 100 行的改动：

1. 画出调用路径并标注副作用；
2. 列出输入契约、输出契约和三个错误路径；
3. 找出跨模块依赖，判断方向是否合理；
4. 把混杂的改动拆成 1—3 个可验证提交。

常见误区：把能通过类型检查当成业务正确；在工具函数里偷偷写数据库；为了“复用”建立无业务含义的公共目录；让 AI 一次修改几十个文件后才看结果。

## 本章完成标准

不看正文解释一次函数调用和异常传播；为一个外部输入写出 Schema；用 diff 说明某次提交改了什么、没改什么、怎样验证。三项练习平均至少 7/10 才算基本掌握。
