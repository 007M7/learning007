# 04 · SQL、事务、索引与迁移

> 一句话点题：业务系统真正不能随便错的是事实；数据库的价值不是“把 JSON 放进去”，而是在并发、崩溃和版本演进中仍然守住这些事实。

## 本章可观察目标

你能把业务规则翻译为表、键、约束和事务；能解释隔离级别下可能出现的异常；能用查询计划而不是猜测判断索引；能设计向后兼容、可回退或可前滚的数据库迁移。

## SW10 · 数据建模：先确定事实与不变量

任务运行器至少有用户、工作区、任务和状态变化。不要从 ORM 类开始，从业务问题开始：什么必须唯一、什么必须存在、谁拥有什么、什么时间值需要保存、哪些变化要审计。

```sql
create table tasks (
  id uuid primary key,
  workspace_id uuid not null references workspaces(id),
  idempotency_key text not null,
  status text not null check (status in ('pending','running','succeeded','failed','cancelled')),
  version integer not null default 1,
  created_at timestamptz not null default now(),
  unique (workspace_id, idempotency_key)
);
```

这几条约束比应用里的 `if` 更接近事实最终防线：主键保证身份唯一；外键避免孤儿；check 限制状态集合；复合唯一约束保证同一工作区幂等。应用仍需提前验证并返回友好错误，但数据库约束能在并发和多入口下守住底线。

### 规范化与反规范化

规范化减少重复事实，避免更新一处忘记另一处。例如用户名称应以用户表为事实源，而不是复制进每个任务。反规范化是为了特定读取性能或历史快照有意复制数据，但要写明谁是事实源、怎样同步、允许多旧。没有同步语义的重复字段不是性能优化，只是未来冲突。

金额用整数最小单位或精确 decimal，避免二进制浮点；时间通常存带时区的绝对时刻，展示时转用户时区；枚举是否用数据库 enum 取决于演进频率，check/text 更易变更但约束略松。选型要围绕变化和约束，不围绕个人偏好。

## SW11 · 事务：把多个动作变成一个可承诺边界

事务的原子性意味着边界内要么全部提交，要么全部回滚；一致性依靠约束与正确逻辑；隔离处理并发交错；持久性意味着已提交数据在承诺的故障模型下保存。

```mermaid
sequenceDiagram
  participant A as Request A
  participant B as Request B
  participant DB as Database
  A->>DB: BEGIN; read pending
  B->>DB: BEGIN; read pending
  A->>DB: update where status='pending'
  DB-->>A: affected 1
  B->>DB: update where status='pending'
  DB-->>B: affected 0
  A->>DB: COMMIT
```

条件更新把“检查＋修改”变成数据库内的单个竞争点。若先 SELECT、在应用判断、再无条件 UPDATE，两个请求都可能通过旧检查。

### 隔离级别不是越高越好

读已提交通常避免脏读，但同一事务两次查询可能不同；可重复读提供更稳定快照，但不同数据库实现细节不同；串行化尽量让结果等价于某个串行顺序，代价是冲突重试和更低并发。不要背名称后假设行为一致，要根据数据库官方文档和实验验证。

事务不要跨慢网络调用：持锁等待支付/模型一分钟，会增加冲突、阻塞和故障恢复难度。常见做法是本地事务先记录意图/状态，再通过 outbox 或工作流协调外部动作；跨系统无法自动共享一个本地 ACID 事务。

### 死锁与重试

两个事务按不同顺序锁订单和账户可能互相等待。数据库会检测并终止其中一个；应用要把它视为可重试的事务冲突，但重试必须有限、带抖动，且外部副作用不能重复。统一锁顺序和缩短事务通常比盲目增加重试更有效。

## 索引：为读取建旁路，同时给写入加税

B-tree 索引维护有序键，适合等值、范围和排序；复合索引遵循列顺序与查询模式。索引让查询少扫数据页，却增加存储和每次写入维护成本。不是“查询慢就给每列加索引”。

```sql
select id, status, created_at
from tasks
where workspace_id = $1 and status = 'pending'
order by created_at desc, id desc
limit 50;
```

候选索引可为 `(workspace_id, status, created_at desc, id desc)`。但是否使用取决于数据分布和统计信息：如果 95% 都是 pending，`status` 选择性低；若只查少量活跃任务，部分索引可能更合适。使用 `EXPLAIN (ANALYZE, BUFFERS)` 比“索引看起来对”可靠，同时注意它会真实执行查询。

索引失效的常见原因包括对列做函数、隐式类型转换、前导模糊匹配、排序不匹配或返回行太多。优化前先看总耗时、行数估计与实际偏差、读取页数和锁等待。

## 迁移：代码与数据不会在同一瞬间切换

线上滚动发布期间，新旧代码会同时运行。安全迁移常用 expand–migrate–contract：

```text
1. Expand：新增可空列/新表/兼容索引，不破坏旧代码
2. Deploy：新代码双读或回退读，开始写新格式
3. Backfill：小批量补历史数据，限速并可恢复
4. Verify：核对数量、校验和、业务指标
5. Switch：读路径切到新字段，保留回退窗口
6. Contract：确认无旧代码后删除旧列/约束
```

在大表上直接加带默认值的非空列、重写全表或长时间建索引可能锁表/放大 I/O。具体行为依数据库版本而异，迁移必须在接近生产规模的数据上演练。回滚代码也不一定能回滚数据：已写入新格式后，旧代码是否还能读？很多数据迁移应设计前滚修复，而不是幻想一键回退。

## 贯穿案例：重复创建任务与零停机加优先级

第一阶段，两个相同请求同时到达。应用先查“是否存在”再插入，仍可能竞态；用 `(workspace_id,idempotency_key)` 唯一约束让数据库裁决，冲突后查询已有任务并返回同一结果。

第二阶段新增 `priority`：

1. 新增可空列，不立即设置全表默认；
2. 新代码读取 `coalesce(priority, 0)`，创建时写值；
3. 后台按主键小批回填，记录进度和失败；
4. 验证 null 数量为零、分布合理、队列行为未变；
5. 加 default/check/not null；
6. 一个发布窗口后移除兼容读取。

整个过程保留旧实例兼容，避免迁移和发布绑定成不可拆的大爆炸。

## 决策与权衡

| 选择 | 适合 | 代价/边界 |
|---|---|---|
| 数据库约束 | 所有写入口都必须遵守的不变量 | 错误需映射；复杂跨行规则要事务/触发器 |
| 应用校验 | 友好反馈、上下文权限 | 并发下不能单独守住最终事实 |
| 乐观并发版本 | 冲突少、用户编辑 | 冲突时需合并/重试 |
| 悲观锁 | 冲突高、临界区短 | 阻塞、死锁、吞吐下降 |
| 强隔离 | 正确性要求高 | 重试与协调成本 |

## 会死在哪里

- 无约束重复数据：并发穿透“先查后写”；最终唯一性放数据库。
- 长事务持锁：外部调用/批处理放在事务内；拆阶段并缩短边界。
- 索引泛滥：写延迟和存储上涨；按查询计划与使用统计治理。
- 迁移锁表：小数据测试没暴露；在真实量级演练并监控锁/I/O。
- 时区与浮点错误：账目差一分、日期跨天；明确单位与绝对时间。
- 软删除破坏唯一性：被删除行仍占键；明确部分唯一索引或归档策略。

```text
请先把需求翻译成数据不变量，再生成 SQL：
- 列出事实源、主键、外键、唯一性、状态集合、单位与时区；

- 对关键查询给候选索引，同时说明写放大和验证用的 EXPLAIN；
- 把迁移拆成 expand/backfill/verify/switch/contract；
- 写出旧代码与新 schema、新代码与旧 schema 的兼容矩阵；
- 标出不可安全回滚的数据变化和前滚修复方案。
```

## 练习：用并发证明约束

建任务表并实现幂等创建。启动两个并发事务用同一键插入，先在无唯一约束时观察重复，再加约束验证只有一条。对任务列表生成至少 100,000 行有偏分布的数据，比较无索引/候选索引的计划与时间。最后写一个优先级字段的 expand–contract 迁移，在“旧代码仍运行”条件下完成演练。

## 常见误区

ORM 模型等于数据模型；所有规则只写应用；事务越大越安全；隔离级别越高越专业；索引越多越快；开发库毫秒级迁移就代表线上安全；代码回滚等于数据回滚；把软删除、时区和金额当实现细节。

## 本章小结

- 建模先找事实与不变量，再决定表和 ORM；数据库约束是并发下的最终防线。
- 事务定义本地原子边界，外部网络调用通常不应持有数据库事务。
- 隔离是正确性与并发的权衡，具体语义必须以数据库实现和实验为准。
- 索引用空间和写成本换读取路径，判断依赖查询计划、数据分布与实际测量。
- 迁移是新旧代码并存的协议演进，安全路线通常是扩展、回填、验证、切换、收缩。
