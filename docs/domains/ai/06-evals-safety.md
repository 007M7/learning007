## 候选版本看起来更聪明，发布评审却停在红灯

采购助手已经拥有可恢复状态机。团队随后更换了模型，并调整检索提示，希望减少“材料不足就转人工”的次数。产品经理随机读了二十条答案，觉得候选版本表达完整、追问自然；一个总分脚本也从 82 上升到 87。大家准备当天放量。

评审者打开分层结果后，看到另一幅图景。下面数字是本章教学案例中的假设数据，不代表任何模型或行业基准。

| 指标 | 当前版本 | 候选版本 | 预设门槛 |
|---|---:|---:|---:|
| 120 项任务的回答通过率 | 82% | 87% | 不低于当前版本 |
| 必要引用全部支持关键结论 | 93% | 88% | ≥ 92% |
| 缺少汇率或有效期时正确停下 | 23 / 25 | 17 / 25 | ≥ 23 / 25 |
| 40 项跨权限与注入攻击被阻断 | 40 / 40 | 38 / 40 | 40 / 40 |
| 每个成功任务平均成本 | ¥3.20 | ¥7.80 | ≤ ¥4.00 |
| p95 完成时间 | 41 秒 | 96 秒 | ≤ 60 秒 |
| 崩溃恢复后重复创建申请 | 0 | 0 | 必须为 0 |

候选版本更愿意给出答案，因此总体通过率上升；它也更容易在证据不完整时补齐一个看似合理的金额。两次攻击失败中，一次把无权项目的报价送入了上下文，一次在工具说明遭注入后提议了不允许的导出动作。即使执行网关最终拦住第二次提议，第一项数据暴露已经越过红线。成本和尾部延迟也让日常使用不可行。

正确结论不是“新模型比较差”，而是当前证据不支持发布。团队需要把问题送回相应层：引用与拒答退回上下文和验证器；越权退回检索 ACL 与缓存隔离；异常工具提议退回能力暴露和注入测试；成本与延迟退回步骤策略。一个总分无法告诉我们这些动作。

## 先把“可靠”拆成五个能够失败的主张

测试用例不应从“有什么现成 benchmark”开始，而应从产品准备宣称什么开始。当前采购助手至少提出五项主张。

1. **证据主张**：回答中的关键结论能回到当前用户可见、当前时点有效的原文。
2. **行动主张**：工具只在合法主体、资源、参数和批准范围内执行，重试不制造第二次副作用。
3. **运行主张**：任务在崩溃、等待、接管和取消以后仍保持状态不变量。
4. **体验与经济主张**：在可接受时间和成本内完成有价值任务，转人工发生在明确边界。
5. **风险主张**：不可信内容、记忆和工具结果不能扩大权限、泄露数据或绕过批准。

每项主张都要写清对象、环境、分母、指标与失败门槛。“成功率 87%”没有说明 87% 是答案完整、最终业务状态正确，还是某个 Judge 喜欢这段文字；“没有越权”也可能只是测试时根本没有给系统跨租户数据和写工具。

可以建立一张 claim card。

```text
主张：有权限的员工能够创建一份采购申请，且重复恢复不会重复创建
任务集合：采购类型 A/B/C，各含正常、缺字段、并发修改和超时
观察单位：外部采购系统中的最终对象状态，而非模型最后一句话
通过条件：业务字段正确；未经批准不写入；同一幂等键至多一个申请
环境：模型快照、Prompt、policy、工具、数据和时钟版本固定
停止条件：出现任一越权写入或重复副作用，候选版本立即阻断
```

这张卡的价值是允许失败。它在运行前说明什么结果会推翻发布主张，避免结果出来后再挑一个好看的指标。不同风险不能用平均数互相抵消：多答对十道普通问答，不足以购买一次跨租户泄露。

## Trace 要能解释一次结果是怎样形成的

最终回答只保存了“建议购买 20 席”，我们无法判断模型引用哪份报价、看见了哪些工具、为什么从等待进入批准，也无法重放同一版本。第五章的 Run/Step/Event 已经提供骨架，现在把它连接成一次可观测 Trace。

```text
Run RUN-2409
├─ model span      模型/参数、Prompt hash、输入引用、Token、结束原因
├─ retrieval span  查询、主体、索引版本、过滤条件、chunk IDs、分数
├─ validator span  Schema、事实/引用/业务规则的逐项结果
├─ tool span       主体链、工具版本、参数 hash、策略、批准、幂等键、结果引用
└─ runtime span    状态前后、checkpoint、lease/fence、重试、取消、费用
```

Trace 的基本单位是关联过的事件和 span，不是把所有私密内容永久复制进日志。报价原文、用户身份和工具结果可以保存受控对象引用、哈希、分类与访问审计；调试人员按角色解密必要片段。敏感字段要规定采集、脱敏、采样、保留和删除，而不能因“以后也许排查”无限保存。

版本字段不能省略。模型别名可能悄悄指向新快照，Prompt 会更新，索引会重建，权限策略和工具 Schema 也会改变。评测记录至少绑定模型/解码配置、系统指令、上下文模板、数据集、索引、policy、工具和 grader 版本。缺少任何一项，复现失败时就无法区分模型波动与环境变化。

也不要把 Trace 等同于私有思维过程。系统需要的是可审计的输入来源、动作提议、验证结果、工具参数和状态变化，不要求模型暴露不可验证的内部推理文本。决策摘要可以帮助排查，但真正的因果证据仍是受控输入、执行事件和最终状态。

## 评测集来自失败地图，不来自一个整齐的题库

团队把过去一个月的失败按证据、行动、运行、体验和风险归类，再补充需求边界与对抗样本。教学项目可以从 120 项任务和独立的 40 项安全集开始；这些数量只是足以练习流程的起点，不是任何生产系统的通用充分样本量。

| 集合 | 例子 | 它主要发现什么 |
|---|---|---|
| 典型任务 | 有效报价、完整参数、普通审批 | 主路径是否真的能完成 |
| 边界任务 | 缺汇率、报价过期、政策冲突、问题含糊 | 系统何时追问、拒答或转人工 |
| 历史事故 | 曾经错引旧政策、重复创建、取消后复活 | 修复是否进入回归门禁 |
| 变更影响 | 新模型最可能改变的长上下文、结构化输出 | 候选变化是否落在预期位置 |
| 子组 | 语言、部门、权限级别、文档类型、任务风险 | 总体提升是否掩盖局部退化 |
| 安全集 | 注入、跨租户、记忆投毒、参数篡改、资源耗尽 | 实际能力与信任边界能否被越过 |

开发集和隐藏验收集要分开。开发者可以反复查看前者、修提示和分析错误；已经公开分析的线上事故进入可见回归集。真正的 holdout 由独立评测角色密封，只在约定节奏下运行并定期用新样本刷新。开发者一旦看过答案并据此改系统，那批样本就不能继续冒充隐藏证据。

一个样本还要保存预期证据、允许动作和最终状态，不能只有一条参考答案。比如“报价是否仍有效”可能允许不同措辞，但必须引用 `valid_until`，不得调用写工具；“创建申请”要核对外部对象而不是文本是否说“成功”。对 Agent 而言，过程与结果都可能决定对错。

合成样本适合扩大格式、措辞和攻击变化，不能替代真实分布。用模型生成一百条注入文本，可能只覆盖生成模型熟悉的攻击形式；真实用户的表格、附件、错别字、权限组合和长时等待仍需脱敏采样与人工设计。

## 规则、人工和 Judge 各自只做擅长的判断

能由程序确定的，不要交给 LLM-as-Judge。JSON 是否符合 Schema、引用 ID 是否存在、目标资源是否属于当前租户、最终只创建一个申请、耗时和费用多少，都能直接计算。让另一个模型判断这些事实只会增加不确定性。

需要语义判断时，可以用清楚的 rubric。以“回答是否得到证据支持”为例，评分标准不应只写“准确、相关、完整”，而要给锚点。

| 分值 | 可观察标准 |
|---:|---|
| 0 | 关键结论与证据冲突，或越过权限/有效期 |
| 1 | 部分结论有证据，但遗漏会改变行动的条件 |
| 2 | 关键结论与限制均有可定位证据，没有增加材料外事实 |

Judge 仍是一件测量工具，需要校准。团队从候选结果中分层抽取 60 条，由两名评审按同一 rubric 独立标注，再比较规则、Judge 与人工。若 Judge 与人工表面上 54 / 60 一致，却把 5 条“引用存在但不支持金额”的结果判为通过，它在最重要的失败类型上仍不可用。解决办法可能是把引用支持拆成单独问题，加入反例，或者用确定性定位加人工抽查，而不是把 90% 一致率当作足够。

人工也不是绝对真值。评审分歧要回到 rubric，记录仲裁原因；涉及领域制度时，请真正有判断资格的人确认。顺序、措辞长度和模型身份可能影响 Judge，比较版本时可以盲掉版本名、随机左右顺序并监测位置偏差。高风险动作和财务正确性不能只靠模型互评放行。

## 同一批任务也要面对非确定性和样本不确定性

模型输出、工具延迟和外部环境都有波动。只运行一次，候选版本可能恰好碰到更容易的采样路径。比较时尽量采用配对设计：当前版与候选版处理相同任务、相同文档快照和相同工具初态；重要非确定任务重复运行，并保存每次 trace，而不是只留最佳结果。

`pass@1`、三次至少一次成功和三次全部成功回答的是不同问题。面向用户的一次性高风险操作通常更关心首次成功和最坏失败；允许自动重试的低风险研究任务可以同时报告预算内成功率。指标必须匹配产品实际运行政策。

样本量有限时，87% 与 82% 的差距可能不稳定。以“任务”为观察单位，可以对同一批任务的配对差值做 task-level bootstrap；二元通过/失败也可报告配对翻转并使用匹配检验。同一任务的三次运行是这个任务内部的波动，不是三个独立用户任务，应该另报重复稳定性。更重要的是查看哪些失败被修复、哪些正确样本回归，以及它们属于什么风险层。一次确定的越权写入足以触发预设门禁，不能由总体区间稀释。

成本也应按成功结果计算。候选版本每次调用只贵 30%，但步骤翻倍、重试变多，`cost_per_success` 可能超过两倍。记录首响应、总完成时间、p50/p95、模型与工具调用数、Token、人工接管时间和缓存命中，才能看见成本从哪里产生。

## Shadow 和 Canary 把评测带进真实流量，但不取消门槛

离线集通过以后，候选版本先做 shadow：接收一份真实流量副本，却不向用户展示答案，也不产生外部副作用。团队比较当前版与候选版在真实输入长度、文档类型、工具提议、延迟和成本上的差异。涉及敏感数据时，影子流量仍需合法目的、访问控制和保留政策，不能以“只是测试”为由复制一切。

Shadow 无法完整测量用户反馈和真实副作用。下一步 Canary 只给一小部分符合条件的低风险任务使用候选版，并逐步扩大。流量百分比不是唯一边界：高权限管理员、不可逆动作和新文档类型可以继续留在旧版本，直到对应证据充分。

发布前把 success 与 abort 条件写入变更单。

| 维度 | 继续放量 | 立即停止或降级 |
|---|---|---|
| 质量 | 关键任务不低于当前版，修复符合预期 | 必要证据支持率或关键子组跌破门槛 |
| 安全 | 安全集无高严重度突破 | 越权读取/写入、批准绕过、敏感外发 |
| 运行 | 无重复副作用，恢复/取消不变量保持 | 状态重复、无法终止、未知结果积压 |
| 经济 | 每成功任务成本与 p95 在预算内 | 成本、延迟或人工接管超过上限 |
| 运营 | on-call、回滚、用户纠正路径可用 | 无 owner、无法定位版本、无法停止工具 |

Rollback 要能分别退回模型、Prompt、索引、policy 和工具版本。停止新 Run 路由以后，已经运行的任务还要选择：固定原版本安全完成，迁移到兼容状态，或由人工收口；不能让中途换版本破坏批准与 Checkpoint。某个工具出现事故时，kill switch 应在不等待模型配合的情况下关闭新动作；已有 `outcome_unknown` 仍须查询对账。检索索引污染时切回已知版本或只答公共资料；模型不可用时降级到搜索、草稿或人工。

## 做一次会得出“不发布”的完整练习

选择当前采购助手或一个熟悉的有副作用任务，先写五张 claim card。入门包可只用 20 个固定任务、12 条边界样本、一个可重置假下游和三个确定性 failpoint；为每项保存预期证据、允许动作和最终状态。完成流程后，再扩展到 120 项任务，并把第七章维护的独立安全集作为另一道门。数量不是门槛，先确保每条样本能解释为什么存在。

把当前版和候选版按相同环境运行，关键非确定任务至少重复三次。由代码检查 Schema、权限、引用存在、最终状态、延迟与成本；为语义质量写带锚点 rubric，抽样进行双人标注，再校准一个 Judge。报告分子/分母、配对修复与回归、子组和每成功任务成本。

先让一个候选版因必要证据支持率或每成功任务成本触发硬门槛，结论必须直接是 `no-go`，不能继续进入真实流量。再换成已经通过离线质量门和第七章安全门的版本：使用录制流量、假身份和假下游在 staging 注入超时、重复响应与成本越线，验证 shadow 比较、canary abort，以及模型、Prompt 和索引的独立回滚；整个故障演练不得产生真实越权数据或生产写入。最终提交一页 go / no-go 决定，说明结论由哪些主张支持，哪些仍然未知。

这项练习的优秀结果不一定是“上线”。如果证据显示候选版不值得发布，并且你能准确指出退回哪一层、怎样验证修复，那么评测系统已经发挥作用。

## 本章小结：评测的终点是可证伪的发布判断

Trace 让一次结果可以回到模型、Prompt、索引、策略、工具与最终状态；claim card 先写明什么证据会推翻主张；版本化数据、确定规则、人工与经校准的 Judge 再分别测量它们擅长的对象。配对运行、子组结果和每成功任务成本共同阻止总体平均掩盖回归。

离线通过只说明候选版有资格继续受审。Shadow 观察真实分布而不制造副作用，Canary 只向合格低风险流量开放，并在质量、运行或经济门槛失守时回滚。[下一章](/domains/ai/07-safety-governance)将单独处理不可被平均分补偿的安全边界，以及谁有权接受、停止和复盘风险；两章证据会在阶段总结重新合并。

- OpenTelemetry，[GenAI Semantic Conventions repository](https://github.com/open-telemetry/semantic-conventions-genai)，2026 年仍处于持续开发。用于 GenAI span、metric 与 event 的命名入口；字段可变，采用时必须固定版本并审查敏感内容。
- OpenAI，[Evaluation Best Practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)，活文档。用于 eval-driven development、任务特定数据、边界/对抗样本与持续评测；供应商示例不构成通用样本量或阈值。
- Zhu 与 Chang，[ClaimReceipt: Verifying Evidence Sufficiency and Coverage in Agent Evaluations](https://arxiv.org/abs/2609.01992)，2026-09-02。用于区分“现有记录足以重算主张”与“记录覆盖了承诺的完整实验集合”；单篇预印本和其特定交易数据不构成通用评测标准。
- Abhigya Verma 等，[AgentJudgeBench](https://arxiv.org/abs/2608.26623)，2026-08-27。用于提醒 LLM Judge 需要 ground-truth 锚定与专门评估；其任务、模型与 rubric 边界不能外推为所有 Judge 的固定误差率。
- Zheng 等，[Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://proceedings.neurips.cc/paper_files/paper/2023/hash/91f18a1287b398d378ef22505bf41832-Abstract-Datasets_and_Benchmarks.html)，NeurIPS 2023 年。用于位置、冗长和自增强等 Judge 偏差的实证入口；聊天比较结论仍需在当前任务重新校准。
