# AI 应用与 Agent 系统

> 这条路线不教你追逐每周出现的新框架。它训练一个更稳定的能力：把概率模型放进有证据、有权限、可恢复、可评测的系统，并知道什么时候不该继续增加自治。

## 这条路线适合解决什么

你可能已经能调用模型 API，也能让 AI 写出一个 RAG 或工具 Agent Demo。真正困难的是下一步：如何判断输出是否稳定，引用是否真的支持结论，工具有没有越权，超时后是否重复写入，模型升级以后又凭什么发布。

七章沿用的是**同一条控制链**，不是一组互不相干的 Demo：模型候选先经过调用合同，再接受版本化证据约束；写动作经过身份、权限、批准与幂等门；长任务把这些决定写入可恢复状态；发布层最后用 Trace 和分层评测审理版本，再以安全门、责任人与回滚能力限制真实后果。案例会从员工制度答复推进到受控申请，以便暴露真实副作用和跨日等待，但后一章必须继承前一章的版本、失败状态、权限和验收器，不能重新从“能跑”开始。

三篇阶段总结故意更换业务对象，用陌生场景检验迁移，不接管正文主线。第一阶段的供应商准入样本通过后进入一组**平行回归集**：它以后用于检查结构门、证据门和注入边界是否回归，却不会被悄悄混入正文项目、训练集或当前业务统计。这样既保留连续的工程积累，也避免只会复述同一个年假案例。

这条路线适合：

- 想从模型调用走向真实 AI 产品的开发者、产品经理和独立创作者；
- 已经做出 Demo，却无法解释可靠性、安全、成本和维护边界的人；
- 希望系统学习 RAG、Tool Calling、Runtime 与评测，而不是收集框架名的人。

如果你还没有写过函数、JSON、HTTP 请求或基础测试，先学习软件与系统工程的程序、API、状态和权限部分，再回来会更顺畅。课程不会要求你先训练大模型，也不以高等数学作为入门门槛。

## 三个阶段会留下什么

| 阶段 | 核心问题 | 主要产物 | 完成以后仍未解决 |
|---|---|---|---|
| 一 · 模型行为与调用合同 | 怎样让一次概率输出成为可验证接口 | 行为剖面、调用合同、Schema、语义验证与回归集 | 外部事实和真实动作 |
| 二 · 证据与行动 | 回答凭什么成立，动作凭什么执行 | 语料清单、必要证据集、检索报告、工具合同、授权与幂等测试 | 跨天任务和系统发布 |
| 三 · 运行、评测与治理 | 任务怎样恢复，版本怎样被放行或停止 | 状态机、故障日志、记忆政策、Trace、评测与 canary/回滚证据 | 模型训练和前沿 Agent 研究 |

每阶段都有独立总结。总结不是把术语再列一遍，而是换一个场景重新组装产物，加入故障，并用 basic / proficient 标准决定是否继续。

## 真实投入与学习方式

完整核心路线按 **66 个标准回合**核算，每回合 45 分钟，共 49.5 小时：七章正文 39 回合，三次阶段迁移 22 回合，首次环境搭建 2 回合，三个阶段各一次延时复测 3 回合。原第六章的 8 回合按知识依赖拆成 Trace/评测 5 回合与安全/治理 3 回合，因此总投入没有增加。正文回合已包含该章的小型环境调整、运行和报告，不再另加“隐形作业”。按每周 4～5 回合约需 14～17 周；日历只用于安排，产物和复测才决定完成。

精力不足时，可以把 30 条样本缩成 10 条，把多工具缩成一读一写，把真实系统替换成可复位沙箱。不要删除版本、权限、失败分支和验收，因为这些正是学习目标。

每次学习建议保持三个动作：

1. 先预测案例为什么失败，再读正文；
2. 跟着同一对象重做一次最小实验，并保留逐样本结果；
3. 换一个小场景做变式，把无法解释的地方写入复习清单。

## 最小贯穿项目

建立一个低风险的“内部知识—申请助手”。第一阶段先让它输出结构化回答并明确证据不足；第二阶段接入版本化资料和一个“创建草稿”工具；第三阶段把同一控制链放进可等待、可恢复的申请任务，并完成一次 no-go 或 canary 发布决定。阶段总结使用供应商、采购或报销等陌生对象做迁移证据，但不会抹掉正文项目的父链。

项目最终不以 UI 漂亮或回答流畅验收，而以一份可交接证据包验收：行为剖面、调用合同、语料与工具版本、故障测试、状态机、评测结果、发布与回滚记录。另一位不了解项目的人应能从它复述系统边界并重新运行关键测试。

::: warning 最容易走错的方向
如果任务、数据来源和权限还不清楚，不要先做多 Agent；如果固定工作流已经够用，不要为了“智能”改成开放循环；如果没有独立评测集，不要把换模型、微调或 GraphRAG 当作改进证据。
:::
