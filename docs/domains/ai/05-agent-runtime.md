# 05 · 一项任务跨过三天以后，Agent 靠什么继续

> 单次工具调用只要处理“现在要不要做”。长任务还要面对等待、崩溃、重复执行、并发接管和用户反悔。真正的 Agent Runtime，不是把模型放进一个无限循环，而是让每一次决定都有状态、边界和恢复路径。

## 采购申请没有结束，它只是开始等待

上一阶段用一个最终快照推演过采购助手怎样创建申请。本章把时间轴退回提交之前：申请人林清准备为项目 P-17 购买 20 个日志平台账号，系统已经能引用有效制度并生成受控草稿，却还没有真正调用 `create_purchase_request`。如果演示只从“材料齐全”直接跳到“创建成功”，中间跨天等待与恢复的难题都会被藏起来。

安全负责人补充了一条意见：供应商处理的日志可能包含个人数据，需要先确认数据驻留区域。财务要求把美元报价换算成人民币，并使用审批当天的公司汇率。供应商第二天才回复数据驻留说明，项目负责人第三天才批准预算。任务中间还可能发生四件事：服务进程重启，用户把席位从 20 改为 15，另一个 worker 接管同一任务，或者负责人直接取消采购。

这时，“继续把对话发给模型”不再是一种完整设计。任务恢复以后，模型无法只凭聊天记录判断采购申请是否已经在远端创建，无法证明昨天的批准仍然覆盖今天的参数，也没有权威依据判断哪个 worker 才能继续。上下文里即使保存了所有文字，它仍然缺少可以被程序裁决的任务状态。

团队先把这项工作写成一条业务路径。

```text
收集需求
   │
   ├─ 缺少报价或安全材料 ──> 等待补充 ──┐
   │                                    │
   └─ 材料齐全 <────────────────────────┘
          │
          ▼
生成计划 ──> 确定性校验 ──> 等待批准 ──> 创建申请
   ▲                         │               │
   └──── 参数变化，旧批准失效 ┘               ├─ 已创建
                                             ├─ 已拒绝
                                             └─ 结果未知
```

箭头是业务允许发生的状态变化，不是模型临场编出来的故事。模型可以帮助识别缺少什么材料、怎样解释差异、下一步适合调用哪个窄工具；“是否有权提交”“批准是否仍有效”“是否已经写入”仍由程序和权威系统回答。

## 先把确定的部分拿回程序里

是否使用 Agent，不应从“模型能不能规划”开始，而应从任务路径是否真的无法提前写出开始。

如果一项任务只有固定的三步，错误分支也能枚举，那么普通工作流通常更便宜、更容易测试。采购申请的身份校验、金额计算、审批链、状态查询和最终写入都属于这类确定部分。让模型反复决定“要不要检查权限”不会增加价值，只会增加漏检概率。

模型决策适合放在另一类节点：供应商回复的文档格式不固定，需要判断是否回答了数据驻留问题；多份安全材料互相冲突，需要决定继续检索哪一类证据；用户给出模糊变更，需要先澄清席位、期限还是预算。这些路径依赖开放输入，无法把每一种文本写成 `if/else`，但可把模型选择限制在一小组允许动作中。

```text
确定程序负责：状态转移、身份、权限、预算、截止时间、批准、幂等与最终写入
模型负责：     在当前状态下提出候选判断、候选计划或下一项允许动作
验证器负责：   检查提议是否满足结构、业务规则、证据和授权
人负责：       补充意图、处理无法自动裁决的冲突、批准高影响动作
```

这给“工作流”和“Agent”一个可操作的区别。工作流的下一步由预先写好的规则决定；Agent 的某些下一步由模型根据当前观察选择。二者可以共存在同一系统里。Agent 并不意味着整个过程都由模型控制，现实中更可靠的设计往往是确定性骨架包住少数模型决策点。

使用更大决策空间前，应先写出它带来的可测收益。例如固定检索顺序在 100 个任务中有 18 个因为材料类型未知而失败；允许模型从三个查询动作中选择后，完成率上升，同时步骤、成本和错误调用仍在门禁内。如果没有这种对照，只因流程图画起来“不够智能”而加入 Agent，就没有承担新增复杂度的理由。

## Runtime 保存的不是聊天，而是一份正在履行的合同

采购任务需要一个稳定的 `run_id`。它把目标、当前状态、预算、所依据的策略和产生的材料连接起来。一次模型调用或工具调用只是其中一个 `step`，不能代表整个任务。

| 对象 | 当前任务里保存什么 | 为什么不能只留在 Prompt |
|---|---|---|
| `Run` | 主体、目标、状态、策略版本、预算、截止时间、取消状态 | 进程退出后仍要知道这项任务是谁的、是否还能继续 |
| `Step` | 输入引用、动作提议、模型/工具版本、开始与结果状态、费用 | 需要定位失败发生在哪一步，并阻止盲目重做 |
| `Checkpoint` | 已确认事实、待处理动作、批准引用、版本号 | 恢复时要从一个完整边界继续，而不是猜测聊天做到哪里 |
| `Artifact` | 报价、计算表、计划、申请号及哈希 | 大对象独立版本化，避免摘要替代证据 |
| `Event` | 用户修改、审批、超时、接管、取消等不可变记录 | 当前状态要能追溯由哪些事实演变而来 |

以 `PR-8820` 为例，运行状态可以明确写成：

```json
{
  "run_id": "RUN-2409",
  "owner": "E-1042",
  "goal": "为 P-17 创建日志平台采购申请",
  "status": "waiting_supplier_evidence",
  "policy_version": "procurement-v4",
  "input_version": 3,
  "step_count": 6,
  "budget": { "max_steps": 20, "max_minutes": 4320, "max_cost_cny": 12 },
  "pending": "request_data_residency_statement",
  "approval_id": null,
  "last_event": "EV-1908"
}
```

`status` 不能只用 `running / done / failed`。长任务至少要区分等待用户、等待外部事件、等待批准、正在执行、结果未知、成功、拒绝、取消和预算耗尽。等待是一个可持久化的业务状态，不是让线程阻塞三天。外部回复到达后，事件唤醒运行；恢复逻辑再次检查任务版本、权限和截止时间，再决定是否推进。

每个状态还要列允许离开的边。例如 `waiting_approval` 只能因批准、拒绝、过期、输入改变或用户取消而离开。模型输出“已经批准”不在允许事件中。状态机因此成为一道控制边界：自然语言可以提出变化，只有受信事件能真正改变状态。

本地状态改变还需要一个原子边界。状态版本、对应 Event 和“下一步待调度消息”应在同一数据库事务中提交，或者通过 transaction outbox 让消息最终可靠发出；不能先改状态、进程崩溃后永远丢掉下一步。外部采购系统不在这笔本地事务里，它的副作用仍由幂等键、结果查询和补偿处理。本章所说的 Checkpoint 是供应商无关的课程抽象；具体工作流引擎可能依据事件历史确定性重放，而不是保存一份任意进程快照。

## 崩溃最喜欢发生在“已经做了，但还没记下来”之间

第三天，系统调用采购服务创建申请。下游已经写入 `PR-8820`，但当前 worker 在保存成功结果前崩溃。新 worker 读取到的最后记录仍是 `executing`。这就是典型的未知结果窗口：外部世界可能已经改变，本地却没有最终证据。

不能用一笔本地数据库事务包住网络另一端的系统。更可行的办法是组合几项边界：

1. 执行前持久化动作意图、批准快照和稳定幂等键；键至少限定租户、操作与业务意图；
2. 下游把幂等键与业务效果原子保存，同键同参数返回原结果，同键不同参数明确冲突，保留期覆盖最长恢复窗口；
3. 超时或崩溃后先查询，不把“没收到响应”写成“没有执行”；
4. 只有确认未执行、批准仍有效且预算允许时，才发起有限重试；
5. 成功结果以外部对象 ID 和哈希写回 Step，再推进状态。

```text
checkpoint C7: approved
        │  保存 action_intent + key
        ▼
step S8: executing ──请求──> 采购系统
        │                       │
        │ worker 崩溃            └─ 已创建 PR-8820
        ▼
新 worker 读取 S8=executing
        │
        └─ 按 key 查询 ──> 得到 PR-8820 ──> 记录 succeeded ──> checkpoint C8
```

这里的 **checkpoint** 不是每生成一句文字就复制整个上下文，而是一个可以安全恢复的边界。它引用已经落盘的事实、产物和待执行动作。检查点过密会增加写放大，过疏又会让昂贵步骤重复；划分原则是副作用、人工等待、长计算和重要阶段转换前后必须落点。

重试也要按错误类型决定。只有能够证明请求尚未发出时，网络连接失败才可直接退避重试；一旦请求可能抵达服务端，就进入 `outcome_unknown`，使用原幂等键查询或对账，确认未执行后才有限重试。参数不合法、没有权限、批准过期属于确定失败，重复调用不会变好；供应商仍未回复则继续等待。把所有异常都扔进同一个自动重试队列，会把业务拒绝变成流量风暴。

## 两个 worker 都醒来时，只能有一个拥有现在

长任务可能由多个 worker 执行。旧 worker 暂时卡顿，调度器认为它失联，于是把 `RUN-2409` 交给新 worker。几秒后旧 worker 又恢复，两者都以为自己有权推进。仅靠“先抢到一把会过期的锁”还不够：旧执行者可能在锁过期以后带着迟到结果回来。

Runtime 可以为运行分配短期 **lease**，并在每次接管时递增 **fencing token**。

```text
worker A 获得 lease，fence=41
lease 到期
worker B 接管，fence=42
worker A 迟到写入 fence=41  ──> 存储/工具网关拒绝
worker B 写入 fence=42       ──> 接受
```

租约回答“在一段时间里谁负责”，fencing token 回答“哪个执行者的提交仍然有效”。关键存储和有副作用的工具必须参与比较 token；否则 token 只是日志里的装饰。它不会让旧 worker 立刻停止运行，也撤不回外部系统已经接受的效果，后者仍需幂等与对账。模型不需要知道这一并发协议，它得到的是当前可执行动作集合。

同一运行还需要乐观版本检查。林清在 worker 生成计划后把席位改成 15，`input_version` 从 3 变成 4。旧 worker 即使仍持有网络响应，也不能把针对 20 席的结果覆盖新版本。批准、检查点和动作意图都要绑定输入版本或内容哈希。

## 取消不是把页面上的按钮变灰

用户在等待供应商回复时点击取消，前端显示“已取消”很容易；难的是把取消传播到已经排队的模型调用、正在运行的浏览器和即将提交的工具。Runtime 要把取消写成持久事件，并规定每类步骤怎样响应。界面可依次呈现 `cancel_requested`、`cancelling`、`cancelled`；若外部效果已经发生，则进入 `cancelled_with_effect` 或 `compensation_pending`，不能在结果尚未对账时假装一切已撤销。

- 尚未开始的步骤不再领取；
- 可中断的模型、下载和计算收到取消信号并停止；
- 已经开始的外部写入进入查询，不能假装被撤回；
- 不可逆动作完成后，把事实展示给用户，并启动明确的补偿流程；
- 迟到结果可以保存为审计证据，但不能把已取消 Run 改回运行中。

**Compensation** 不是让时间倒流。采购申请已经进入审批系统，可以再调用“撤回申请”；邮件已经送达，只能发更正；付款已经结算，可能需要退款和人工处理。补偿本身是新的业务动作，也会失败，也要有权限、幂等和状态。

停止条件不应只包含用户取消。当前 Runtime 还要在成功验收、最大步骤、最大费用、截止时间、重复动作、连续无进展和安全策略拒绝时结束或转人工。一个常用的无进展信号是：连续三步没有新增权威证据、没有改变业务状态，只是在重写相同计划。它不是通用真理，应通过任务数据调节；重要的是 Runtime 而不是模型拥有最终停止权。

## 记忆从“以后可能有用”变成一项数据责任

供应商回复：“中国客户默认使用新加坡区域；若要中国大陆存储，需要签署企业附录。”模型很想把这句话写进长期记忆，下次遇到同一供应商就直接使用。问题是这条信息来自哪份邮件、适用于哪个产品版本、何时失效、哪些项目有权看到？没有这些边界，记忆会把一次任务里的局部陈述升级成全公司的事实。

Runtime 状态与长期记忆要分开。

| 信息层 | 当前例子 | 生命周期与裁决 |
|---|---|---|
| 工作状态 | 正在等待安全负责人、剩余预算、下一动作 | 只属于 `RUN-2409`，由状态机更新 |
| 任务产物 | 报价、数据驻留回复、计算表、批准记录 | 与任务和版本绑定，可审计、可归档 |
| 情节记忆 | “这类申请常缺数据驻留证明” | 作为候选经验，需统计或人工确认后复用 |
| 长期知识 | 某产品的正式数据驻留政策 | 必须指向权威来源、适用范围、owner 和有效期 |
| 用户偏好 | 林清希望金额同时显示人民币与美元 | 由用户确认，可查看、更正与删除 |

一条可用记忆至少带 `subject`、`source_ref`、`scope`、`valid_from/to`、`sensitivity`、`verified_by` 和 `supersedes`。检索时还要按当前主体和目的重新授权。把另一个项目的安全例外召回到本项目，或者把管理员曾经看到的内容从共享缓存交给普通用户，都不是“召回效果不好”，而是权限事故。

记忆也不能成为授权来源。假设摘要错误写下“林清拥有所有采购审批权”，下一次 Agent 若据此开放付款工具，就出现了授权漂白：一条模型生成记录把从未发生的权限变成了可执行能力。权限必须回到身份系统和可验证事件；记忆最多帮助查找，不得自行授予、延长或撤销权力。

删除和修正要进入生命周期。原政策被新版替代时，旧记忆不应静默消失到无法审计，也不能继续参与当前答案。可以保留版本关系和历史引用，同时让查询默认只返回当前有效项。涉及个人偏好或敏感信息时，还要提供用户可见的更正、导出与删除路径，并按实际法规和组织政策确定保留。

## 用三个故障点验收，而不是看它能否跑完一次

最小练习继续使用采购助手，也可以迁移到“读取 issue、生成修复计划、经批准创建任务”。建议分三次完成。

第一次先画状态机，不调用模型。可以用 SQLite、一个只支持“创建/按幂等键查询”的假采购服务，以及 `after_model`、`before_send`、`after_remote_commit` 三个确定性 failpoint。先准备 12 个固定任务，列出状态、允许事件、终止条件与预算；实现 `Run / Step / Checkpoint / Artifact / Event` 最小 Schema，证明等待状态不会占住进程。

第二次加入模型选择，但只允许它在三个窄动作中提议：请求缺失材料、读取已有证据、生成计划。程序验证动作集合和前置条件。在模型返回但提议未落盘、动作意图落盘但尚未发送、外部写入成功但本地结果未落盘三个位置分别终止进程。第一次可以生成新 attempt，后两次必须按状态和幂等键恢复，最终只能出现一个外部对象。

第三次加入并发、取消与记忆。让两个 worker 竞争同一 Run，旧 fencing token 的写入必须失败；在等待、执行和结果未知三个状态发出取消；让模型提出一条长期记忆，系统必须展示来源、范围和有效期，并由用户确认。再植入一条伪造权限记忆，执行网关应完全忽略它。

交付物不是一段“运行成功”的录屏，而是状态图、Schema、三个 failpoint 的恢复日志、一个并发接管记录、取消/补偿表和记忆治理记录。反馈模板逐项记录初始状态、注入点、预期不变量、实际终态和外部对象数量；评审者应能从任意终态沿事件回到原始批准与工具结果。完成入门包后，再把任务扩展到真实工作流和更长等待。

## 本章小结：可恢复运行不等于可发布

这一章留下了一套可恢复运行包：状态机、Run/Step/Checkpoint、终止与预算、崩溃恢复、并发接管、取消补偿和记忆策略。采购助手现在能够跨三天继续，不代表它已经值得上线。它可能稳定地执行错误计划，也可能只在我们看过的五个例子里表现良好。

下一章会把运行事件变成 Trace，把“回答更好”“工具更可靠”“风险可接受”改写成可以被数据证伪的发布主张。没有本章的稳定状态和版本，评测无法重放；没有下一章的评测与安全门禁，本章的恢复能力只会让错误执行得更持久。

## 参考资料

- Yao 等，[ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629)，ICLR 2023 年。用于理解推理、动作与环境观察的交替；论文轨迹不是完整的生产 Runtime，也不提供授权、恢复和并发语义。
- Temporal，[Workflow Execution](https://docs.temporal.io/workflow-execution)，活文档。用于 durable execution、事件历史与恢复的工程参考；具体保证依赖其平台实现，本章的数据模型是供应商无关抽象。
- Amazon Builders' Library，[Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)。用于客户端请求标识、幂等与重试边界；它不能让不可逆业务动作自动回滚。
- Packer 等，[MemGPT: Towards LLMs as Operating Systems](https://arxiv.org/abs/2310.08560)，2023 年。用于分层上下文与外部记忆的研究起点；OS 类比不证明某种记忆产品适合所有任务。
- Cerruti 等，[Agent Memory Is a Surface for Endogenous Authorization Laundering](https://arxiv.org/abs/2609.01836)，2026-09-01。用于说明持久记忆可能错误保存权限并影响后续动作；论文中的比例来自特定模型与三个实验领域，不能作为当前系统常数。
- Burrows，[The Chubby Lock Service for Loosely-Coupled Distributed Systems](https://research.google/pubs/the-chubby-lock-service-for-loosely-coupled-distributed-systems/)，2006 年。用于理解锁服务、sequencer 与迟到执行者边界；具体 fencing 仍要求下游存储或服务参与验证。
- IETF，[RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html)，2022 年。用于区分网络方法语义与业务效果；跨系统写入仍需应用级幂等键、状态查询和补偿。
