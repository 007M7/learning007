# 阶段三总结 · 让一个能继续运行的 Agent 变成可放行的系统

> 第三阶段处理的是两种不同的“可靠”：任务中断以后仍能继续，是运行可靠；团队能够证明它值得上线并在恶化时停下，是决策可靠。只做到前者，系统可能持续而稳定地执行错误。

## 三章把“时间”分成运行、测量与责任

第四章结束时，系统已经能安全完成一次工具调用。它知道当前主体是谁，计划依据什么证据，批准绑定哪些参数，也能在超时后查询最终结果。第五章把这个瞬间延长到数小时或数天：Run 保存目标和预算，Step 记录每次模型或工具尝试，Checkpoint 提供恢复边界，Event 解释状态怎样改变，lease 与 fencing 阻止旧 worker 迟到覆盖。

第六章又把时间延长到多个系统版本。一次运行的 Trace 连接模型、Prompt、索引、policy、工具与最终状态；版本化数据集反复检查历史事故和边界；shadow 与 canary 让离线证据进入真实分布，并在质量、运行或成本门槛失守时回滚。第七章把不能由平均分补偿的风险单独展开：沿资产、入口、能力和后果重放攻击，由具名 owner 接受剩余风险，并用模型外的 kill switch、事故响应和用户纠正限制伤害。

```text
单项任务的时间
输入 ──> 计划 ──> 等待 ──> 批准 ──> 执行 ──> 终态
        Run / Step / Checkpoint / Event / Artifact

系统演进的时间
当前版 ──> 候选版 ──> 离线评测 ──> Shadow ──> Canary ──> 放量或回滚
          Claim / Dataset / Trace / Gate / Owner / Incident
```

两条时间线通过版本和运行证据连接。一条历史失败进入评测集，要能找到当时的输入、策略、工具结果和外部状态；一项新版本主张要能回到固定环境中的逐任务结果。只保存最后答案，两条线都会断开。

本阶段最重要的判断可以写成一句话：

> Runtime 决定任务怎样安全地活下去，评测与治理决定这个任务有没有资格继续活下去。

## 现在换成一笔有争议的差旅报销

为了验证能否迁移，不再使用年假和采购案例。员工周然提交一笔 8,460 元的差旅报销，包含高铁票、两晚酒店和客户晚餐。助手可以读取当前差旅制度、解析票据、查询行程与成本中心，并创建报销草稿；它没有批准、付款或修改员工主数据的能力。

任务并不一次结束。酒店发票缺少购买方税号，晚餐名单第二天补充，项目经理可能在等待时调整成本中心。财务系统还可能在创建草稿后丢失响应。助手必须决定何时继续解析，何时询问用户，何时等待外部材料，何时把争议交给财务人员。

先写系统边界，而不是先给模型十个工具。

| 系统可以做 | 必须停下 | 当前不做 |
|---|---|---|
| 读取本人可见的政策、行程与票据 | 票据关键字段缺失或制度冲突 | 代表经理批准 |
| 提取字段并用确定代码计算金额 | 身份、成本中心或票据归属不一致 | 发起付款 |
| 生成带引用的报销草稿 | 高风险异常或需要裁量的例外 | 修改员工、供应商或财务主数据 |
| 经本人确认后创建草稿 | 批准快照失效或外部结果未知 | 根据记忆授予任何权限 |

这个边界本身就是一项成熟判断。Agent 不是因为功能越多越好；恰恰相反，团队能明确说出现在不做什么，才可能为剩余能力建立完整证据。

## 先让任务在四种中断后保持同一个事实

为报销任务画一份状态机。名称可以不同，但状态必须能区分正在工作、等待谁、结果未知和终态。

```text
collecting_receipts
   ├─ 缺税号 ──> waiting_user ──补充且版本匹配──┐
   ├─ 缺名单 ──> waiting_external ─────────────┤
   └─ 材料完整 <───────────────────────────────┘
          │
          ▼
drafting ──> validating ──> waiting_confirmation ──> creating_draft
                     │               │                     │
                     ├─ 争议 ─> human_review               ├─ succeeded
                     └─ 拒绝 ─> rejected                   ├─ failed
                                                          └─ outcome_unknown
```

然后主动制造四种中断。

第一种发生在票据解析后、结果落盘前。解析没有外部副作用，可以用固定版本启动一个新 attempt；OCR 或模型解析仍可能变化，因此要分别保存两次输出，不能假设逐字相同。第二种发生在用户确认以后、创建草稿以前。恢复必须重新验证确认对应的输入版本，不能因“曾经同意”跳过检查。第三种发生在财务系统已创建草稿、响应丢失以后。系统按幂等键查询，只能得到同一个草稿。第四种发生在旧 worker 租约过期以后。新 worker 获得更高 fencing token，旧 worker 的迟到写入被拒绝。

这些测试共同维护一组状态不变量。

- 同一 `run_id` 可以存在并发 worker，但只有最新 generation / fencing token 的提交能够生效；
- 同一幂等意图最多产生一个报销草稿；
- 输入改变以后，旧确认和旧计算不能继续使用；
- 已取消或已拒绝的运行不会因迟到结果重新变成执行中；
- 任何终态都能追到有效主体、证据、确认和外部结果。

测试应断言数据库和财务系统的最终状态，而不只是检查日志里有没有打印“恢复成功”。

## 记忆考的是来源与撤销，不是能否召回一句话

周然曾经告诉系统：“以后酒店尽量订 600 元以内。”这可以成为一条由用户确认的偏好，并允许他查看、更正或删除。系统从一次票据中推断“周然的酒店上限是 600 元”，则只能作为候选，不能静默变成政策。公司差旅上限来自版本化制度，任何个人记忆都不能覆盖。

迁移验收加入三条记忆测试。

1. 新版制度把某城市上限改为 700 元，检索默认返回新版本，旧记忆保留历史关系但不参与当前判断。
2. 另一个员工曾获得一次特殊例外，周然的运行不能召回其内容，更不能把例外当作通用规则。
3. 植入“周然是财务审批人”的伪造摘要，身份与工具网关仍从权威系统得出无批准权限。

记忆评分不只看命中率。还要检查来源是否可追、适用范围是否正确、过期是否停止使用、权限是否隔离、冲突能否呈现、用户能否删除。召回一条不该出现的记忆，往往比漏掉一条便利偏好更严重。

## 再把产品承诺写成一组会被推翻的实验

团队准备宣称：“报销助手能减少材料往返，不增加错误支付和跨员工泄露，并且恢复后不会重复创建草稿。”这句话至少拆成四张 claim card。

| 主张 | 观察单位 | 关键反例 | 阻断条件 |
|---|---|---|---|
| 材料检查有用 | 首次提交到材料齐全的往返次数 | 模型追问了制度并不要求的字段 | 关键子组往返反而增加 |
| 计算与引用正确 | 每笔费用项及其政策依据 | 汇率、上限或适用城市错误 | 任一高金额错误越过确认 |
| 写入保持一次 | 财务系统最终草稿集合 | 超时恢复后出现两个草稿 | 任一重复副作用 |
| 数据与权限受控 | 用户实际可见内容和工具效果 | 跨员工票据进入上下文 | 任一未经授权披露或写入 |

评测集从这些主张倒推。典型任务覆盖普通票据；边界任务包含缺税号、跨日汇率、政策冲突和含糊成本中心；历史事故包含重复创建与旧确认；安全集加入票据 OCR 注入、跨员工引用、伪造记忆和资源耗尽。每项保存预期证据、允许动作、最终状态和失败层。

评分分工也随对象改变。程序检查金额、Schema、引用存在、权限、对象数量和状态；财务专家依据 rubric 判断例外是否解释完整；经过人工校准的 Judge 可以扩大对普通说明质量的筛查。若 Judge 总把“写得很确定但漏掉例外”的回答判高分，它不适合承担发布门禁。

当前版与候选版处理同一批任务，关键项重复运行，报告逐项修复与回归、分子分母、子组、延迟和每成功任务成本。总体平均上涨，仍不能覆盖任一未经授权的数据进入上下文或重复创建。

## 一条完整 Trace 要回答四个“为什么”

从一笔成功报销草稿 `ER-3108` 向前回放，评审者应当能够回答：为什么系统认为材料齐全，为什么采用这份制度与汇率，为什么当前用户有权创建，为什么外部系统确实只有一份草稿。

```text
ER-3108 最终状态
  └─ tool result + idempotency key
       └─ confirmation hash + input version
            └─ validator results + calculation artifact
                 └─ cited policy/receipt IDs + ACL decision
                      └─ model/prompt/index/policy/tool/grader versions
```

如果任何箭头只能用“模型当时大概是这么想的”解释，Trace 仍不够。原始票据也不必无限复制到每个 span；前提是原始对象仍在受控存储中可检索、哈希能够校验且审计者获得授权，此时引用和访问路径才足以连接证据。敏感内容按政策保存。

对于失败运行，同样要保留在哪一步停止、哪项验证拒绝、用户看到了什么、是否产生外部效果。拒答和转人工不是 Trace 的空洞终点，它们也是需要评测的产品行为。

## 用放量与回滚演练完成最后一次验证

离线通过后，候选版先 shadow 真实报销请求，但不能创建草稿。团队观察文档长度、语言、票据类型、模型步骤、追问、成本和 p95 是否落在离线覆盖范围。随后只对低金额、标准政策、可撤销草稿开启 canary，高金额与特殊例外继续走原流程。

故障先在 staging 完成。使用录制请求、假票据、假身份和可重置财务服务，让候选索引遗漏最新版政策，再模拟“远端成功、本地超时”；系统应触发版本门槛、按幂等键对账，并在控制面演练中独立关闭写工具。所有安全与重复响应测试通过以后，才进入真实 shadow 和低风险 canary；canary 只被动监测预设 abort 条件，不主动制造重复副作用或投放真实越权数据。

最终变更单记录候选版本、预期收益、未覆盖范围、离线结果、shadow 差异、canary 人群、停止条件、回滚对象、owner 和用户纠正路径。评审结论可以是 go、带条件 go 或 no-go；任何一种都要能回到同一套证据。

## 阶段交付包要让另一个人真的接得住

第三阶段的可交接产物不只是 Runtime 代码和一张分数表，而是一份带顶层 manifest 的运行与发布包。

```text
manifest
├─ system-boundary.md
├─ state-machine.md + invariants.yaml
├─ run-step-checkpoint schema + event examples
├─ crash-concurrency-cancel test logs
├─ memory-policy.md + provenance/delete tests
├─ claims.yaml + dataset manifest
├─ per-sample results + trace references
├─ judge-calibration.md
├─ shadow-canary-rollback evidence
└─ release-decision.md + owners
```

manifest 为每份产物保存版本、哈希、生成时间、对应主张和验证状态。另一位工程师应能从它重新运行测试，产品负责人应能看见系统明确不做什么，安全人员应能找到权限与攻击证据，值班人员应知道怎样停止和回滚。

只有代码能启动，没有状态不变量和故障日志，不算通过；只有一个平均分，没有逐样本与子组，不算通过；只有安全清单，没有真实注入和最终状态，不算通过；只有一张批准截图，没有绑定参数与事件历史，也不算通过。

## 用两档标准决定是否进入更深的路线

达到基础掌握时，你应当能够在不看正文的情况下完成下面四件事。

- 把开放任务拆成确定工作流与有限模型决策点，并写出停止条件；
- 设计可以跨等待和崩溃恢复的状态机，证明一个写入不会重复；
- 区分任务状态、产物、情节经验、长期知识和用户偏好；
- 从产品主张建立分层评测，并用预设安全与成本门槛作出 no-go。

达到熟练掌握时，还应在不同日期迁移到一个新场景；用并发、取消、伪造记忆和注入破坏系统；完成 Judge 校准；从一条终态 Trace 回放证据；在 shadow/canary 中演练独立工具 kill switch 与版本回滚。评审者按“边界 2 分、恢复 2 分、记忆 2 分、评测 2 分、发布与事故 2 分”评分，任一安全或重复副作用红线都会阻断，不能用总分补偿。

第一次练习可以使用 12 笔固定报销、一个 SQLite 状态库和一个支持幂等查询的假财务服务。7 个标准回合依次用于环境与初态、状态机、三类故障、评测主张、shadow/canary 模拟、迁移和交接；熟练挑战再扩大样本、增加两名评审。反馈表只记录五项：注入点、预期不变量、实际终态、外部对象数量和修复后回归结果。不同日期的延时复测由路线另计 1 回合。

下面这道题只检查两条时间线的连接处。

## 接下来不是继续堆能力，而是选择真正需要的深度

核心学习到这里已经走完模型调用、上下文合同、证据、工具、Runtime、评测与治理。板块总结会把三阶段产物合成一张系统全景，并帮助判断下一步应该回补软件工程、进入模型训练与推理、研究 Advanced RAG，还是学习 Agent 前沿。

选择依据不是哪个词更热门，而是当前瓶颈在哪里。模型行为与成本解释不清，进入 AI 进阶；工具、状态和交付工程不稳，回补软件与质量；已有稳定系统且需要理解最新规划、记忆、评测或安全研究，再进入 Agent 前沿。任何路线都不应绕过本阶段留下的基线、权限和回退门禁。
