# 05 · 可观测性、SLO 与故障恢复

<div class="lesson-meta"><span>Q12—Q14</span><span>必修核心</span><span>预计 3 × 60 分钟</span><span>前置：Q10—Q11</span></div>

## 本章可观察目标

你能用日志、指标与追踪回答生产问题；为用户旅程定义 SLI/SLO；区分备份、恢复、故障转移和事故复盘，并实际完成一次恢复演练。

## Q12 · 可观测性不是“多打日志”

| 信号 | 最适合回答 | 设计要点 |
|---|---|---|
| 日志 | 某个离散事件发生了什么 | 结构化字段、级别、request/run/trace ID；不泄密 |
| 指标 | 系统整体趋势是否异常 | 低基数维度；速率、错误、持续时间、饱和度 |
| Trace | 一次请求跨服务花在哪里 | 上下文传播、span 边界、采样、错误属性 |

先从问题反推遥测：能否按 `run_id` 找全生命周期？能否区分用户错误和系统错误？能否知道模型、数据库、队列各耗时？日志文本不是稳定 Schema 时，查询与告警会变脆弱。

## Q13 · SLI、SLO 与告警

SLI 是观测指标，例如“成功创建任务的比例”；SLO 是目标，例如 30 天窗口达到 99.9%。错误预算允许在可靠性和发布速度之间作显式取舍。只对可行动、影响用户的信号报警；CPU 高但用户无影响通常先进入看板，不应凌晨叫醒人。

延迟看分位数而非只有平均值。可用性分母必须定义清楚：计划维护、无效请求、依赖失败是否计入？

## Q14 · 备份、恢复与事故

RPO 表示可接受丢失多少数据，RTO 表示可接受多久恢复。备份只有成功恢复过才算证据。至少验证：备份完整、加密与访问控制、异地/不同故障域、保留周期、恢复步骤、恢复后业务一致性。

事故过程：检测 → 分级 → 负责人/沟通 → 止损 → 恢复 → 验证 → 无责复盘 → 跟踪行动。复盘关注系统条件与防线缺口，不只写“操作人员粗心”。

## 练习：注入一次故障

在测试环境杀死执行中的 worker：观察任务是否重新获得租约、是否重复副作用、何时告警、trace 是否连续。然后从备份恢复数据库到新实例，记录实际 RPO/RTO 与差异校验。

常见误区：高基数用户 ID 直接作为指标标签；在日志打印 Token/Prompt 全文；没有跨服务 trace ID；告警没有 owner/runbook；备份与主库同账户同区域；复盘行动无负责人和期限。

## 本章完成标准

用单个 `run_id` 从入口追到 worker 与模型调用；定义两个用户导向 SLO；提交一次恢复演练记录，包含实际时间、数据差异和改进行动。
