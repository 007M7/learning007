# 04 · CI/CD、迁移、发布与回滚

<div class="lesson-meta"><span>Q10—Q11</span><span>必修核心</span><span>预计 2 × 60 分钟</span><span>前置：Q03—Q09</span></div>

## 本章可观察目标

你能设计从提交到生产的门禁；让同一制品逐环境晋升；为代码、配置和数据库变化定义发布、观察、停止和恢复动作。

## Q10 · CI 是持续证据

每次合并前自动运行可重复检查；失败阻止合并且报告可诊断。流水线应最小权限、固定第三方 Action 版本、缓存可失效、密钥只给需要的 job。并发提交可取消旧流水线，但发布 job 不应被随意中断在危险步骤。

```text
提交 → 格式/类型/单元 → 集成/合同 → 构建一次
                                   ↓
                    制品 + SBOM/provenance
                                   ↓
                  staging 验收 → production 晋升
```

## Q11 · CD 与安全变化

部署先定义：

- **入口条件**：哪些测试、审批、备份和容量检查完成；
- **策略**：滚动、蓝绿、金丝雀或停机发布；
- **观察窗**：错误率、延迟、关键业务指标；
- **停止条件**：达到什么阈值自动停止；
- **恢复动作**：回退制品、关闭特性、流量切换、前向修复；
- **数据库**：迁移与旧版本是否兼容。

Feature flag 把部署与启用分开，但旗标是临时代码分支，需要 owner、默认值、过期时间和清理任务。回滚不是口号：数据库不可逆写入、外部消息和副作用可能只能补偿。

## 练习：发布计划

为一次新增 `priority` 非空字段写完整计划：Schema expand、应用兼容、后台回填、验证、启用、contract；明确每步指标、停止条件和恢复路径。再把它写成流水线 job 与人工 runbook。

常见误区：每个环境重新构建；部署前才临时改配置；共享长期管理员密钥；健康检查只看 200；发布和迁移同时不可逆；没有观察窗就宣布成功。

## 本章完成标准

从一个提交追踪到生产制品；在测试环境完成一次失败部署并按 runbook 恢复；证明迁移期间新旧应用至少一个发布窗口兼容。
