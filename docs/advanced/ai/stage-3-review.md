## 一台设备和十二座场站提出了两种问题

以下风机、编号、数据和门槛都属于教学 fixture，不提供现实设备操作建议。系统只能生成调查草稿和引用，不能复位设备、改控制参数或下发维修动作。任何涉及人员安全的结论都由有资质的工程师确认。

沿海风电场的一台设备 `WT-17` 报出故障码 `F-48`。维修人员问，这台设备是否适用 2026 年发布的变流器公告，接线图上应检查哪个端子。材料分散在资产清单、序列号与硬件修订映射、供应商公告、扫描接线图和一份维护记录里。公告只写适用于 `Rev-C`，资产清单只写序列号，端子编号则藏在图纸右下角。

这个请求主要是一条有先后依赖的证据链。先确定设备和硬件修订，随后才能选公告，最后才能读取对应图纸。四个 Agent 同时搜索不会打破依赖，单执行者加受控检索更合适。

一个月后，供应商扩大公告范围。负责人要在下午完成十二座场站的影响排查，各场站资产清单彼此独立，有些维护记录只向当地值班组开放。十二条分支可以并行，权限也需要隔离。多 Agent 由此获得候选资格，仍须与确定并行工作流和单 Agent 同预算比较。

先把两项决定分开写进 ADR。

| 决定 | 先问什么 | 允许的结果 |
|---|---|---|
| 检索路线 | 普通混合检索究竟漏了哪种必要证据 | 保持基础、增加分解、增加图、增加视觉分支 |
| 协作路线 | 子任务能否并行，权限是否需要独立，收益能否覆盖协调 | 固定工作流、单 Agent、受限多 Agent |

选择图检索不自动要求多个 Agent。十二个并行分支也可能只需要普通数据库查询。两张决定单分别通过，系统才组合它们。

## 先用简单检索把失败钉在具体层

冻结 30 道迁移题、文档快照、生成器和评分器。题目包含 14 道单段文字、10 道序列号到公告的关系题、6 道接线图或曲线图题。每道题先标必要证据集合，集合里任何必需项缺失都应拒答。

```text
WT-17 的必要证据集合
asset-WT17#serial
serial-map-v6#Rev-C
bulletin-2026-14#scope
wiring-RevC#page=12&bbox=x1,y1,x2,y2
maintenance-WT17#event-88
```

先跑 `BM25 + dense + rerank`。如果 14 道文本题仍大量失败，优先修解析、版本、切块和重排；当前阶段不能用图掩盖基础错误。关系题若在扩大候选后已经找到全部材料，只需改善重排或上下文组装。图纸题若结构化资产库已经保存端子号，确定查询比视觉模型可靠。

只有两种残余失败解锁复杂检索。关系题的后续查询确实依赖前一跳得到的 `Rev-C`，或者页面证据在 OCR 后丢掉位置、连线和图例。为它们建立分路候选，单段文本仍走旧路径。

一张迁移记分牌至少保留这些行。

| 层 | 可观察分母 | 基础与候选怎样比较 | 硬失败 |
|---|---|---|---|
| 实体 | 序列号、型号、修订号提及 | 正确链接、歧义拒绝、错链放行 | 错设备进入答案 |
| 关系召回 | 每题必要来源集合 | 完整集合题数与逐跳召回 | 缺跳仍自动回答 |
| 页面召回 | 页面、图例和 bbox | 命中原页及正确区域 | OCR 数字未经原图复核 |
| 引用 | 最终可核主张 | 支持与完整性分别报告 | 引用不支持安全结论 |
| 成本 | 成功任务 | 索引、模型调用、p95 与人工复核 | 超预算仍继续搜索 |

实验只改变一个检索部件。查询分解先与基础方案对照；分解仍因实体别名失效，再试最小关系图；视觉分支只处理需要页面的六题。若 `WT-17` 与 `WT-I7` 无法消歧，系统展示候选并停止。若公告范围与维护记录冲突，系统保留两份来源并交给工程师。

## 图、页面和原始来源必须一起撤销

最小图只容纳当前问题需要的实体和关系。边保存来源根、版本、有效期、ACL、抽取器和验证状态。模型抽到的 `WT-17 has_revision Rev-C` 在资产记录验证以前只能作候选；供应商公告换版时，旧范围边进入历史状态，依赖它的路径缓存随之失效。

图纸索引保存 OCR、布局树和页面视觉向量。最终引用落在原图页码和区域，端子号再由确定规则或人工核对。视觉模型给出高相似度只能帮助定位页面，不能批准维修动作。删除一份图纸时，页面向量、OCR chunk、派生描述和答案缓存都要从依赖图中找到。

完成检索候选后做三次破坏。把两个相似序列号故意合并，错链门禁应阻断；删除公告源文件，相关边和答案应失效；让 OCR 把 `TB-8` 读成 `TB-B`，视觉与文字冲突应进入人工复核。每次只改一个因素，保存预期、实际与失败层。

若复杂候选只让答案更长，必要证据集合和引用没有改善，ADR 应拒绝它。若它修复关系题却让普通文本题变慢，路由范围缩到关系切片。阶段能力体现在这份采用边界上。

## 全场排查先画任务 DAG，再考虑角色

十二座场站的任务可以先用确定并行工作流实现。每个分支读取获准资产清单，按同一公告范围检查设备，写出结构化 finding。若材料字段固定、查询路径可枚举，普通 worker 已经够用。

某些场站的维护记录格式不同，worker 需要沿新发现的工单、旧型号别名和图纸引用继续搜索。此时给分支一个有限 Agent 循环。协调器只负责分配和汇总，不能读取所有本地原始记录。场站 Agent 使用当地只读身份，只把获准字段、证据引用和完成状态写回共享板。

```text
RUN-fleet-audit
  ├─ T-policy-scope              先完成公告范围
  ├─ T-site-01..T-site-12        范围完成后并行，可各自继续窄搜索
  ├─ T-citation-validate         等待场站产物
  └─ T-merge                     只接收验证通过或明确 partial 的产物
```

父 Run 固定 Token、工具调用、墙钟、fan-out 和委派深度。创建子任务先预留预算，结束后归还未用额度。任务板记录 owner、lease generation、输入版本、依赖、artifact 和终态；自然语言“已经检查完”没有提交效力。旧 worker 迟到时，产物入口拒绝旧 generation。

故障合并保留原语义。一个场站因权限被拒绝，最终报告写“未评估”，不能写“未受影响”；某分支超时可由同一 task ID 接管，已验证 artifact 不必重做；公告范围冲突会阻断全部受影响分支；用户取消以后不再领取新任务。高风险必需分支缺失时，协调器只能提交 partial 或拒绝。

## 十二份报告可能只来自一张公告

全场排查最容易把报告数当成证据数。十二个 Agent 都会引用供应商公告 `B-2026-14`，这些 findings 对“公告写了什么”拥有共同祖先。它们可能各自增加设备状态观察，却没有产生十二份独立公告。

为每个 finding 保存两类根。`policy_root` 指公告或手册，`observation_root` 指独立场站资产记录或维护事件。合并器按主张查看祖先。公告范围由一份政策根支持，某型号在多个场站出现则可以拥有多个独立观察根。文字聚类不能可靠恢复这个区别。

注入一组 Epistemic Sybil 故障。让三个 Agent 读取同一公告，再分别改写成技术摘要、清单和问答。合并器应保留三次抽取，公告根数仍为 1。随后加入第二份真正独立且获准的供应商签发记录，根数才增加。若 ancestry 缺失，系统采用保守权重并标出不确定，不能靠多数投票放行。

这里沿用的是 2026 年预印本提出的 no-minting 边界。论文的受控合成世界和相关误差模型没有覆盖风电维修，也没有给出通用聚合权重。阶段作业只把来源祖先变成强制字段，具体置信与发布门槛仍由本地数据校准。

## 用同预算对照决定十二条分支怎么跑

确定工作流、单 Agent 和多 Agent 使用同一公告、场站集合、生成器、检索版本与验收器。总上限保持一致。报告实际 Token 和工具调用，也报告 wall-clock、任务成功、逐站必要证据、重复读取、人工合并与权限事件。

运行前写出采用门槛。一个教学例子可以要求多 Agent 至少多完成两个场站，墙钟降低 25%，总预算不增加，无越权 finding，且所有通过结论都能追到政策根与场站观察根。门槛数字只服务当前 fixture，换设备数量、人工成本或安全等级就要重算。

结果可能形成四种组合。

| 高级检索 | 多 Agent | 合法决定 |
|---|---|---|
| 无收益 | 无收益 | 保留基础检索和确定工作流 |
| 有收益 | 无收益 | 只给关系/页面题启用高级检索 |
| 无收益 | 有收益 | 并行普通查询，不建图或视觉索引 |
| 有收益 | 有收益 | 在受限任务路由中组合，并分别保留回退 |

这张表防止一次成功演示捆绑两个变化。检索候选失败时，多 Agent 不能用更多搜索掩盖；协调候选失败时，高级检索仍可以由单执行者使用。最终 ADR 为每项复杂度写收益、适用切片、版本、预算、故障、owner、停止条件与回退对象。

## 交付包要让另一组人重跑坏路径

建议把六个 45 分钟回合分给基线、检索候选、协调候选、故障注入、同预算对照和评审。没有图数据库、视觉模型或并行运行环境时，使用不超过 30 题的 JSON fixture、固定检索输出和两个本地进程，仍然保留实体错链、页面坐标、祖先和预算断言。

交付目录可以这样组织。

```text
stage-3-wind-audit/
  task-and-safety-boundary.md
  evidence-sets.jsonl
  baseline-and-routed-results.jsonl
  entity-edge-page-ledger.jsonl
  task-dag-and-permissions.yaml
  ancestry-and-budget-events.jsonl
  failure-injection/
  comparison.ipynb
  complexity-adr.md
```

评审者先抽三道题，从答案回到必要证据和原页；再重算实体正确率、完整集合召回和每成功题成本。随后杀掉一个 worker，复制一份同源报告，触发一次权限拒绝，并核对终态。任何汇总无法回到逐题或逐任务记录，当前维度不得得分。

### Basic 与 proficient rubric

每个维度 0 至 2 分，共 10 分。1 分表示有产物但缺少对照或边界，2 分表示可重放、故障成立且回退明确。

| 维度 | 2 分证据 |
|---|---|
| 失败归因 | 基础失败按实体、必要证据、页面或生成分层，复杂度只进入对应切片 |
| 检索验证 | 图边与页面都可回原件，实体/召回/引用/成本能由逐题结果重算 |
| 协调设计 | DAG、共享状态、权限、预算和终止均有可执行字段 |
| 祖先与故障 | 同源报告不能增发证据根，崩溃、拒绝和 partial 保持语义 |
| 决策与回退 | 三方案同预算比较，两项复杂度分别采用或拒绝 |

达到 **Basic** 需要至少 7 分，失败归因和决策与回退均不得为 0。学习者还要在不看正文时解释多跳、多来源与多 Agent 的区别，并运行一次集合或祖先断言。选择保持简单可以通过，前提是对照证据完整。

达到 **Proficient** 需要间隔至少 7 天，把方法迁移到软件供应链公告、合同尽调或另一种有图文材料的任务。最近两次作业平均至少 8.5 分，第二次必须出现会改变采用结论的变式，包含权限或祖先故障，并由他人从原始记录重算三个指标。

## 下一步由真实瓶颈决定

阶段出口是一份可以拒绝 GraphRAG、视觉检索或多 Agent 的复杂度 ADR。它连接必要证据、来源祖先、任务依赖、权限、总预算和故障终态，也保留基础方案作为回退。

接下来回到 [AI 进阶路线入口](/advanced/ai/)，用当前瓶颈选择继续方向。若问题仍在基础解析、引用或 Runtime，先回补对应核心章节；复杂方案已经有稳定基线和开放研究问题时，再进入 [Agent 前沿](/frontier/agents/)。研究论文可以提出新候选，采用决定仍由本地对照和可撤销证据承担。

## 参考资料

- Nandan Thakur 等，[BEIR 异构检索基准](https://openreview.net/forum?id=wCu6T5xFjeJ)，2021 年。用于建立多类检索基线；公开任务平均值不能替代设备文档切片。
- Harsh Trivedi 等，[IRCoT 交替检索研究](https://aclanthology.org/2023.acl-long.557/)，ACL 2023 年。用于多跳检索的依赖机制；迁移作业采用类型化槽位，不要求暴露自然语言思维过程。
- Darren Edge 等，[GraphRAG 局部与全局研究](https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/)，TMLR 2024 年。用于图与社区报告的研究依据；风机精确查询仍须逐边、逐页验证。
- Manuel Faysse 等，[ColPali 视觉文档检索](https://arxiv.org/abs/2407.01449)，2024 年。用于页面视觉检索候选；视觉命中不提供设备操作授权或数字真值。
- Anthropic，[多 Agent 研究系统工程复盘](https://www.anthropic.com/engineering/multi-agent-research-system)，2025 年。用于并行研究的工程与成本边界；供应商内部结果不能作为本作业收益门槛。
- Marc Bara，[Epistemic Sybil Resistance](https://arxiv.org/abs/2609.01873)，2026-09-01 预印本。用于来源祖先与相关报告边界；受控合成证据结果不能直接外推到风电材料。
- OpenTelemetry，[Tracing API 规范](https://opentelemetry.io/docs/specs/otel/trace/api/)，官方活规范，本课程核验于 2026-09-04。用于连接父子任务和跨分支 trace；技术 trace 仍需显式关联业务证据根。
