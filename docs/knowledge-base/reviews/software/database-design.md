# 数据库设计阅读综述

数据库设计不是先建一张尽可能宽的表。教材先识别业务对象、关系和约束，再把概念模型映射到关系模式。函数依赖解释为什么某些表会产生更新异常，规范化给出拆分方法，SQL 则检验模型能否回答真实问题。设计完成后还要面对事务、权限、迁移和生命周期。

读完以后，读者应能从“需求与业务规则”追到“规范化与无损分解”，说明中间的机制、代价和失败边界，并用“用一个真实系统复原《Database Design, 2nd Edition》的判断过程”完成一次可复查的应用。

## 先建立数据与接口模型

### 需求与业务规则

全书先用“需求与业务规则”固定分析对象。业务规则说明对象、关系、唯一性、时间和允许的状态变化。这一定义决定后文能够讨论哪些状态、操作和保证。

用实例和反例与领域人员确认，再决定哪些规则进入数据库约束。沿数据从产生、编码、传输或存储到读取的过程检查语义。每次转换都可能改变顺序、唯一性、精度与可见时间。

在“用一个真实系统复原《Database Design, 2nd Edition》的判断过程”中验证这项知识时，应留下一张数据或协议状态图和一组边界输入。字段清单不能代替语义，相同名称在不同上下文可能含义不同。带着这项限制进入“实体关系模型”，后面的结论才有清楚前提。

### 实体关系模型

“实体关系模型”承接前面已经建立的对象关系。实体表示可识别对象，关系表达对象之间的基数和参与约束。这里新增的规则会改变后续能够作出的判断。

先画概念模型，与业务语言对齐后再映射表结构。接口应同时说明成功结果和失败后的状态。超时、重复、事务中断与版本变化都会迫使调用方作出选择。

实践记录需要说明“实体关系模型”在正常条件下产生什么结果，并主动加入一个边界条件。ER 图不表达全部时间规则、跨记录计算和事务过程。若结果随之改变，就把差异带到“键与参照完整性”继续处理。

### 键与参照完整性

到了“键与参照完整性”，原书开始处理上一环尚未解决的困难。候选键唯一标识事实，外键保证引用目标存在。理解它需要同时保留前一节的输入与限制。

选择稳定且最小的业务键或代理键，并明确删除与更新策略。静态结构只能说明一部分问题。还要画出状态转换和时间顺序，才能判断约束、重试与恢复是否一致。

这一节适合产出一张数据或协议状态图和一组边界输入，让另一位读者能够复查选择。存在性约束不能证明引用在业务时间上仍然有效。尚未覆盖的输入、状态与环境，应在进入“关系模型和映射”时继续保留。

### 关系模型和映射

接下来要处理“关系模型和映射”。关系由属性和元组构成，表只是其实现形式，映射把实体关系转为键。这一步把先前的局部结论送进更完整的执行或验证过程。

检查多值属性、多对多关系和继承在表中的表示。沿数据从产生、编码、传输或存储到读取的过程检查语义。每次转换都可能改变顺序、唯一性、精度与可见时间。

把“关系模型和映射”用于当前项目时，先写明成立条件，再保留能够推翻结论的反例。对象模型与关系模型的边界需要显式转换，不能靠 ORM 自动消失。下一节“函数依赖”要接住这项未解决的问题。

## 再沿状态变化处理失败和演进

### 函数依赖

原书随后把视线转向“函数依赖”。函数依赖描述一组属性如何唯一决定另一组属性。它补上的关系，正是后一部分能够继续推理的前提。

从业务语义推导依赖，用它识别重复事实与异常。接口应同时说明成功结果和失败后的状态。超时、重复、事务中断与版本变化都会迫使调用方作出选择。

在“用一个真实系统复原《Database Design, 2nd Edition》的判断过程”中验证这项知识时，应留下一张数据或协议状态图和一组边界输入。样本数据暂时唯一不能证明依赖成立，依赖来自规则。带着这项限制进入“规范化与无损分解”，后面的结论才有清楚前提。

### 规范化与无损分解

“规范化与无损分解”承接前面已经建立的对象关系。规范化按依赖拆分关系，减少插入、更新和删除异常。这里新增的规则会改变后续能够作出的判断。

验证分解无损并尽量保持依赖，再结合事务与查询成本。静态结构只能说明一部分问题。还要画出状态转换和时间顺序，才能判断约束、重试与恢复是否一致。

实践记录需要说明“规范化与无损分解”在正常条件下产生什么结果，并主动加入一个边界条件。高范式不是普遍终点，受控冗余要配套一致性维护。若结果随之改变，就把差异带到“SQL 查询和视图”继续处理。

### SQL 查询和视图

到了“SQL 查询和视图”，原书开始处理上一环尚未解决的困难。SQL 用声明式关系操作表达筛选、连接、聚合和更新，视图封装派生关系。理解它需要同时保留前一节的输入与限制。

通过代表性查询检验模式，并查看执行计划与索引影响。沿数据从产生、编码、传输或存储到读取的过程检查语义。每次转换都可能改变顺序、唯一性、精度与可见时间。

这一节适合产出一张数据或协议状态图和一组边界输入，让另一位读者能够复查选择。查询正确不代表并发下事务正确，NULL 语义也需单独理解。尚未覆盖的输入、状态与环境，应在进入“事务、权限与演进”时继续保留。

### 事务、权限与演进

接下来要处理“事务、权限与演进”。事务提供原子边界，权限限制主体行为，迁移让模式随产品演进。这一步把先前的局部结论送进更完整的执行或验证过程。

把隔离级别、回滚、最小权限和向后兼容写进变更计划。接口应同时说明成功结果和失败后的状态。超时、重复、事务中断与版本变化都会迫使调用方作出选择。

把“事务、权限与演进”用于当前项目时，先写明成立条件，再保留能够推翻结论的反例。数据库事务无法自动覆盖外部服务，零停机迁移需要多版本共存。下一节“整本书的最终判断”要接住这项未解决的问题。

## 跟随一次数据交换走完全程

选择一个确实运行过的服务，先写出用户任务、关键状态与不可接受的失败。随后沿“需求与业务规则、实体关系模型、键与参照完整性、关系模型和映射、函数依赖、规范化与无损分解、SQL 查询和视图、事务、权限与演进”恢复原书的推理次序。进入每一层时，记录它接收什么输入、改变什么状态、向下一层交付什么证据。讨论需求与业务规则时先固定问题边界，进入函数依赖时检查机制怎样兑现承诺，最后用事务、权限与演进处理故障、演进或责任。再主动改变一次负载、版本或故障条件，观察原判断从哪里开始失效。

这个案例需要同时写正常路径和失败路径。正常路径说明“需求与业务规则”怎样经过中间机制到达“事务、权限与演进”。失败路径则改变一个前提，观察保证在哪里停止、哪个信号先出现、谁应采取动作。把两条路径放在一起，教材中的抽象才能进入工程判断。

## 容易读错的地方

1. 只记住“需求与业务规则”的名称，没有画出它处理的对象和状态
2. 直接抄用“函数依赖”的结论，遗漏原书给出的前提
3. 只验证正常路径，没有用“事务、权限与演进”检查失败后的状态
4. 把《Database Design, 2nd Edition》中的教学规模、历史条件或组织背景直接当成当前项目条件

这些错误都能用本书自己的对象关系纠正。看到“只记住“需求与业务规则”的名称，没有画出它处理的对象和状态”时，返回“需求与业务规则”重建问题；出现“把《Database Design, 2nd Edition》中的教学规模、历史条件或组织背景直接当成当前项目条件”时，沿案例检查被省略的运行或组织条件。误解被定位到具体章节后，补学范围会更小，也更容易验证。

## 怎样进入网络与数据库学习

这本书在软件与系统工程路线中承担“沿业务规则、概念模型、关系模式、规范化和 SQL 完成可维护的数据设计”这一学习任务。正式学习先建立概念和机制，产物可以是最小实现、证明、数据模型、协议轨迹或架构决定。进阶学习再改变规模、并发、故障、安全或团队条件，比较原方案是否仍然成立。

最值得保留的判断包括以下内容。

- 需求与业务规则负责业务规则说明对象、关系、唯一性、时间和允许的状态变化。；实践中应当用实例和反例与领域人员确认，再决定哪些规则进入数据库约束。
- 实体关系模型负责实体表示可识别对象，关系表达对象之间的基数和参与约束。；实践中应当先画概念模型，与业务语言对齐后再映射表结构。
- 键与参照完整性负责候选键唯一标识事实，外键保证引用目标存在。；实践中应当选择稳定且最小的业务键或代理键，并明确删除与更新策略。
- 关系模型和映射负责关系由属性和元组构成，表只是其实现形式，映射把实体关系转为键。；实践中应当检查多值属性、多对多关系和继承在表中的表示。
- 函数依赖负责函数依赖描述一组属性如何唯一决定另一组属性。；实践中应当从业务语义推导依赖，用它识别重复事实与异常。
- 规范化与无损分解负责规范化按依赖拆分关系，减少插入、更新和删除异常。；实践中应当验证分解无损并尽量保持依赖，再结合事务与查询成本。

列表中的每项判断都应连接一份证据。以“需求与业务规则负责业务规则说明对象、关系、唯一性、时间和允许的状态变化。；实践中应当用实例和反例与领域人员确认，再决定哪些规则进入数据库约束。”为例，证据可以来自原书章节、自己的最小实验和项目中的一次应用。三者各司其职。原文说明概念从哪里来，实验检查机制，本地应用确认条件是否匹配。

## 模型和协议不能替你决定什么

教材为了讲清“需求与业务规则”和“事务、权限与演进”，会控制示例规模，也可能省略认证、治理、兼容、极端负载或长期运营。数据库事务无法自动覆盖外部服务，零停机迁移需要多版本共存。。采用书中方案以前，应核对当前版本、项目约束和依赖环境。

开放正文也会更新。笔记中应保存访问日期、章节标题和采用的具体结论。版本变化时先比较定义、接口与边界，随后重跑与“用一个真实系统复原《Database Design, 2nd Edition》的判断过程”相关的练习。单看页面更新时间无法判断现有实现是否受影响。

## 三遍阅读怎样形成学习产物

第一遍沿“沿《Database Design, 2nd Edition》的论证次序建立知识地图”建立问题地图，只记录每个节点解决的困难。第二遍带着“用一个真实系统复原《Database Design, 2nd Edition》的判断过程”进入关键章节，把对象、状态和选择画出来。第三遍完成一个最小实现或评审，主动触发“数据库事务无法自动覆盖外部服务，零停机迁移需要多版本共存。”所描述的边界，再保存结果。

《Database Design, 2nd Edition》的学习产物应当符合它处理的对象。围绕“需求与业务规则”建立的记录，需要一路支持到“事务、权限与演进”。算法类结论要有证明和复杂度实验，系统类结论要有执行轨迹与资源测量，架构案例要保存驱动因素和备选方案，工程著作则要形成目标、规则和运行证据。摘抄只能保存信息，无法代替这些判断材料。

一周后重新完成案例，改动一个关键条件。读者若仍能选择方案、解释机制并提出验证办法，知识已经开始迁移。若只能回忆章节标题，就回到改动条件所在的小节补一次练习，无需继续扩大阅读清单。
