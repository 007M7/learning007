# 软件基础与程序证明阅读综述

程序测试只能观察选中的输入，形式化证明试图覆盖定义允许的全部情况。《Software Foundations》的第一卷让读者在 Coq 中同时写程序、命题和证明。自然数加法、列表反转和小型命令式语言都很简单，重点在于看见定义怎样产生可证明结构，归纳假设怎样匹配递归调用，证明脚本又怎样被内核逐步检查。

读完以后，读者应能从“Coq 中的函数与数据”追到“命令式语言与 Hoare 逻辑”，说明中间的机制、代价和失败边界，并用“证明一次列表反转保持长度并恢复原列表”完成一次可复查的应用。

## 全书怎样从程序走到证明

可执行定义 → 归纳结构 → 定理陈述 → 证明策略 → 机器检查 → 程序性质

原书路线可以压缩为下面这些节点。

| 学习节点 | 这一层处理什么 | 为什么在此时出现 |
| --- | --- | --- |
| Coq 中的函数与数据 | 用归纳类型和模式匹配写出可计算定义 | 让程序对象进入证明环境 |
| 等式证明 | 通过化简、改写和分类讨论处理具体命题 | 理解证明状态怎样变化 |
| 结构归纳 | 沿自然数、列表等归纳定义建立证明步骤 | 覆盖递归数据的全部构造方式 |
| 逻辑与命题 | 把合取、析取、否定、存在和全称量词写成可检查对象 | 连接程序性质与逻辑推理 |
| 关系和归纳命题 | 用推导规则定义可达性与行为 | 表达函数不便描述的系统关系 |
| 命令式语言与 Hoare 逻辑 | 为状态变化定义操作语义、前置条件和后置条件 | 把局部证明连接到程序正确性 |

这条路线从“Coq 中的函数与数据”开始。作者先建立对象和问题，再逐步加入“逻辑与命题”等约束，最后用“命令式语言与 Hoare 逻辑”处理完整结果。顺序值得保留，因为后一层往往在修复前一层已经暴露的限制。

## 先让命题和程序拥有共同语言

### 归纳数据与递归函数

全书先用“归纳数据与递归函数”固定分析对象。归纳类型列出数据的全部构造方式，递归函数按同一结构消解输入。这一定义决定后文能够讨论哪些状态、操作和保证。

让函数定义与后续归纳证明保持结构一致。这里要观察的是定义、目标与证明状态如何对应。每一步都应能指出当前假设来自哪里，以及内核最终检查了什么。

在“证明一次列表反转保持长度并恢复原列表”中验证这项知识时，应留下一段可检查定义、一条定理和完整证明状态。终止检查保证结构递归结束，却不说明结果满足业务性质。带着这项限制进入“证明状态与策略”，后面的结论才有清楚前提。

### 证明状态与策略

“证明状态与策略”承接前面已经建立的对象关系。目标和上下文描述当前需要证明什么，策略把一个目标变成更小的子目标。这里新增的规则会改变后续能够作出的判断。

逐步观察策略前后的证明状态，不把自动化当成魔法。阅读时可以把证明写成一棵树。父节点记录待证命题，子节点记录策略生成的义务，叶节点必须由已有定理或构造规则关闭。

实践记录需要说明“证明状态与策略”在正常条件下产生什么结果，并主动加入一个边界条件。策略成功依赖当前定义和库，内核检查才是最终可信边界。若结果随之改变，就把差异带到“改写与等式推理”继续处理。

### 改写与等式推理

到了“改写与等式推理”，原书开始处理上一环尚未解决的困难。已证明等式可以在目标或假设中替换相同表达式。理解它需要同时保留前一节的输入与限制。

先找表达式形状，再选择展开、化简或改写。形式推导的力量来自前提清楚。定义漏掉现实状态时，证明越完整，得到的也只是简化模型内部的结论。

这一节适合产出一段可检查定义、一条定理和完整证明状态，让另一位读者能够复查选择。表达式不匹配时盲目增加自动化会掩盖缺失引理。尚未覆盖的输入、状态与环境，应在进入“结构归纳”时继续保留。

### 结构归纳

接下来要处理“结构归纳”。归纳步骤假设较小结构上的命题成立，再证明新增构造仍然保持性质。这一步把先前的局部结论送进更完整的执行或验证过程。

让归纳对象与递归定义所减少的参数一致。这里要观察的是定义、目标与证明状态如何对应。每一步都应能指出当前假设来自哪里，以及内核最终检查了什么。

把“结构归纳”用于当前项目时，先写明成立条件，再保留能够推翻结论的反例。选错归纳变量会得到过弱假设，定理可能需要先泛化。下一节“命题即类型”要接住这项未解决的问题。

## 再把证明变成能够检查的工程产物

### 命题即类型

原书随后把视线转向“命题即类型”。命题可以表示为类型，证明项就是该类型的可检查构造。它补上的关系，正是后一部分能够继续推理的前提。

用构造子理解合取、析取、存在和归纳命题。阅读时可以把证明写成一棵树。父节点记录待证命题，子节点记录策略生成的义务，叶节点必须由已有定理或构造规则关闭。

在“证明一次列表反转保持长度并恢复原列表”中验证这项知识时，应留下一段可检查定义、一条定理和完整证明状态。逻辑编码能保证形式推导，前提是否符合现实仍由建模负责。带着这项限制进入“关系与操作语义”，后面的结论才有清楚前提。

### 关系与操作语义

“关系与操作语义”承接前面已经建立的对象关系。关系可以描述程序状态之间的合法转移，推导规则规定一步或多步执行。这里新增的规则会改变后续能够作出的判断。

画出状态和规则，再证明确定性、保持性或可达性质。形式推导的力量来自前提清楚。定义漏掉现实状态时，证明越完整，得到的也只是简化模型内部的结论。

实践记录需要说明“关系与操作语义”在正常条件下产生什么结果，并主动加入一个边界条件。小步和大步语义回答的问题不同，异常与并发需要扩展模型。若结果随之改变，就把差异带到“Hoare 三元组”继续处理。

### Hoare 三元组

到了“Hoare 三元组”，原书开始处理上一环尚未解决的困难。前置条件、命令和后置条件共同表达在何种初态下执行会得到何种结果。理解它需要同时保留前一节的输入与限制。

从赋值规则、顺序组合、分支和循环不变量构造证明。这里要观察的是定义、目标与证明状态如何对应。每一步都应能指出当前假设来自哪里，以及内核最终检查了什么。

这一节适合产出一段可检查定义、一条定理和完整证明状态，让另一位读者能够复查选择。部分正确性不自动保证终止，外部输入和资源也不在简单模型内。尚未覆盖的输入、状态与环境，应在进入“整本书的最终判断”时继续保留。

单独理解“归纳数据与递归函数”只能得到全书的入口。它规定归纳类型列出数据的全部构造方式，递归函数按同一结构消解输入，随后“结构归纳”把问题推进到归纳步骤假设较小结构上的命题成立，再证明新增构造仍然保持性质。最后的“Hoare 三元组”继续处理前置条件、命令和后置条件共同表达在何种初态下执行会得到何种结果。三者合在一起，才能说明这本书如何从对象定义走到完整结果，也能解释为什么章节次序不能随意打乱。

复述这条主线时，应把一段可检查定义、一条定理和完整证明状态放在旁边。读者需要指出前一环产生了什么，后一环怎样使用，以及哪个条件变化会使传递中断。若“结构归纳”无法读取“归纳数据与递归函数”留下的信息，说明中间还缺接口、状态或证据；若“Hoare 三元组”没有接住“结构归纳”暴露的限制，阅读就停在了局部技巧。

这条主线也提供了删减标准。与“归纳数据与递归函数”到“Hoare 三元组”无关的细节可以稍后查阅，会改变这条因果关系的定义、机制和反例则应当精读。这样安排既能保留《Software Foundations Logical Foundations》的专业密度，也能避免第一次阅读被所有章节和术语同时淹没。

## 用一个函数与定理串起学习路线

先在 Coq 中定义列表与反转函数，再陈述反转后长度不变。化简只能处理空列表，非空分支需要对尾部使用归纳假设。继续证明反转两次得到原列表时，读者会发现现有假设不够，必须先证明反转与追加之间的辅助引理。这个过程解释了证明为何会推动 API 和定理结构重新安排。若把列表换成带权限、时间或外部状态的业务对象，模型还要补充相应关系，原证明不会自动覆盖这些现实条件。

这个案例需要同时写正常路径和失败路径。正常路径说明“归纳数据与递归函数”怎样经过中间机制到达“Hoare 三元组”。失败路径则改变一个前提，观察保证在哪里停止、哪个信号先出现、谁应采取动作。把两条路径放在一起，教材中的抽象才能进入工程判断。

## 做选择时怎样使用这些知识

| 情境 | 建议检查或采用的方向 | 选择依据 |
| --- | --- | --- |
| 函数按递归数据定义 | 优先尝试结构归纳 | 证明步骤可以对应数据构造和递归调用 |
| 主定理缺少可用归纳假设 | 先寻找辅助引理或泛化命题 | 增强中间关系比堆叠自动策略更稳定 |
| 行为由多种规则产生 | 使用归纳关系表达 | 比返回单一结果的函数更适合描述推导 |
| 需要证明循环程序 | 设计循环不变量 | 连接每次迭代与最终后置条件 |

表中每一行都要回到当前系统验证。以“函数按递归数据定义”为例，团队可以先按“优先尝试结构归纳”建立最小方案，再用“证明步骤可以对应数据构造和递归调用”检查选择理由。若规模、失败后果或维护方式变化，原来的推荐也要重新评估。

## 容易读错的地方

1. 把 Coq 策略记成命令表，却看不懂目标怎样变化
2. 认为测试通过与定理证明提供同一种证据
3. 归纳时只机械拆构造，没有匹配递归结构
4. 定理在简化模型中成立后，直接宣称生产系统已经正确

这些错误都能用本书自己的对象关系纠正。看到“把 Coq 策略记成命令表，却看不懂目标怎样变化”时，返回“归纳数据与递归函数”重建问题；出现“定理在简化模型中成立后，直接宣称生产系统已经正确”时，沿案例检查被省略的运行或组织条件。误解被定位到具体章节后，补学范围会更小，也更容易验证。

## 怎样进入软件正确性学习

这本书在软件与系统工程路线中承担“用 Coq 把函数式程序、归纳定义、逻辑命题和机器检查连成一条程序证明路线”这一学习任务。正式学习先建立概念和机制，产物可以是最小实现、证明、数据模型、协议轨迹或架构决定。进阶学习再改变规模、并发、故障、安全或团队条件，比较原方案是否仍然成立。

最值得保留的判断包括以下内容。

- 定义的结构决定可用证明方法
- 归纳假设需要对应递归下降方向
- 辅助引理会暴露主定理缺少的中间关系
- 证明脚本由内核检查，自动策略仍应保持可解释
- 程序性质取决于建模边界
- Hoare 逻辑把状态变化与前后条件连接起来

列表中的每项判断都应连接一份证据。以“定义的结构决定可用证明方法”为例，证据可以来自原书章节、自己的最小实验和项目中的一次应用。三者各司其职。原文说明概念从哪里来，实验检查机制，本地应用确认条件是否匹配。

## 形式化证明能够保证到哪里

教材为了讲清“归纳数据与递归函数”和“Hoare 三元组”，会控制示例规模，也可能省略认证、治理、兼容、极端负载或长期运营。部分正确性不自动保证终止，外部输入和资源也不在简单模型内。采用书中方案以前，应核对当前版本、项目约束和依赖环境。

开放正文也会更新。笔记中应保存访问日期、章节标题和采用的具体结论。版本变化时先比较定义、接口与边界，随后重跑与“证明一次列表反转保持长度并恢复原列表”相关的练习。单看页面更新时间无法判断现有实现是否受影响。

## 三遍阅读怎样形成学习产物

第一遍沿“从可执行函数走到程序逻辑”建立问题地图，只记录每个节点解决的困难。第二遍带着“证明一次列表反转保持长度并恢复原列表”进入关键章节，把对象、状态和选择画出来。第三遍完成一个最小实现或评审，主动触发“部分正确性不自动保证终止，外部输入和资源也不在简单模型内”所描述的边界，再保存结果。

《Software Foundations Logical Foundations》的学习产物应当符合它处理的对象。围绕“归纳数据与递归函数”建立的记录，需要一路支持到“Hoare 三元组”。算法类结论要有证明和复杂度实验，系统类结论要有执行轨迹与资源测量，架构案例要保存驱动因素和备选方案，工程著作则要形成目标、规则和运行证据。摘抄只能保存信息，无法代替这些判断材料。

一周后重新完成案例，改动一个关键条件。读者若仍能选择方案、解释机制并提出验证办法，知识已经开始迁移。若只能回忆章节标题，就回到改动条件所在的小节补一次练习，无需继续扩大阅读清单。
