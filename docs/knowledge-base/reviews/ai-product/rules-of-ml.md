# Rules of Machine Learning 阅读综述

这份材料由 Martin Zinkevich 根据 Google 的机器学习工程实践整理。它没有从模型公式讲起，而是沿产品成熟过程给出规则。先判断现在是否该用机器学习，再建立可运行的第一条流水线，随后增加特征，最后处理收益放缓。

[阅读 Google 官方在线正文](https://developers.google.com/machine-learning/guides/rules-of-ml){target="_blank" rel="noopener noreferrer"}

## 全文的时间顺序

```text
规则和指标还不稳定
        ↓
建立第一条端到端流水线
        ↓
用可理解特征快速迭代
        ↓
增长放缓后再增加复杂模型
```

这条顺序解释了文中许多看起来保守的建议。简单模型、可观察目标和独立测试基础设施服务于早期学习速度。系统进入平台期以后，团队才有足够数据判断复杂方法是否带来真实收益。

## 使用机器学习以前先准备指标

第一条规则允许产品不用机器学习启动。启发式规则能快速验证用户流程，也能产生后续训练数据。团队还不清楚什么结果有价值时，模型只会更快地优化一个含糊目标。

指标应在模型之前进入系统。早期埋点可以建立历史基线，观察哪些行为稳定、哪些变化敏感。产品经理需要区分优化目标、报告指标和护栏指标。推荐系统可能优化点击，同时观察长期留存、隐藏内容和投诉。一个数字不能代表全部产品质量。

复杂启发式开始互相覆盖、维护成本上升时，机器学习通常更合适。此时历史规则还可以成为特征或政策层。模型负责排序，政策层处理合规、安全和无法由平均收益抵消的限制。

## 第一条流水线先保证端到端可靠

文中反复要求团队保持流水线完整。数据进入训练、模型导出、在线服务和指标回传都要能跑通。第一个模型可以简单，因为早期最大风险经常来自基础设施。

Google 建议独立测试数据进入算法和模型进入服务的过程。训练环境与服务环境对同一输入应给出一致结果。丢弃数据、默认值变化、时区和特征计算差异都可能让离线高分在上线后消失。

监控也从第一版开始。特征新鲜度、缺失比例、取值范围和模型导出失败需要在用户发现前报警。每个特征应有负责人和说明，否则数据源变化以后很难判断谁来处理。

## 第一项目标要简单、可观察、可归因

早期不必寻找理论上完美的目标。团队需要一个可以稳定计算、与产品行为接近的指标。用户点击很容易观察，却可能鼓励耸动内容。长期满意度更接近价值，却反馈慢且受多种因素影响。

可行做法是先选一个短期目标，同时设置长期和风险护栏。模型输出与最终政策分开。垃圾内容过滤、安全限制和商业规则由政策层处理，质量模型在允许集合中排序。这样团队可以分别追踪模型改进和政策改变。

可解释模型在早期有额外价值。它帮助团队发现数据泄漏、错误特征和目标偏差。等流水线稳定，复杂模型的收益才更容易被正确测量。

## 特征工程阶段追求可重复迭代

第二阶段从直接观察和人工可理解的特征开始。内容长度、近期行为和明确类别通常比一开始引入复杂嵌入更容易调试。具体特征可以在已知场景中带来收益，跨场景特征则帮助泛化，两者需要组合。

团队应预期持续上线。训练配置、特征代码和服务代码要支持比较新旧版本。特征数量增加以后，文档、所有权和删除机制变得重要。一个长期没有增益却继续消耗计算的特征会变成系统债务。

规则还提醒团队注意数据随策略变化。模型改变排序，用户行为随之改变，新数据已经受到旧模型影响。离线重放不能完整模拟这种反馈，需要在线实验和分群监控。

## 训练与服务偏差为何危险

训练时计算特征的一套代码与线上服务使用的代码不同，会产生 training-serving skew。时间窗口、缺失值、词表和归一化中的细小差异，都可能改变预测。

团队应在同一批样本上比较两端特征与预测，记录差异分布。可共享的变换尽量复用，无法共享的部分建立契约测试。只有检查整体平均值不够，少数关键群体可能承受更大偏差。

产品经理需要把一致性写进发布门槛。新模型离线指标提高，但训练服务偏差扩大，不应直接上线。

## 收益放缓以后再研究复杂度

系统进入平台期后，继续增加相似特征的收益会减少。团队可以考虑非线性模型、表示学习、多任务学习和更精细的目标。复杂度增加必须由在线收益、维护成本和风险共同评估。

平台期也可能说明目标已经接近上限，或当前指标无法感知真正价值。团队先检查数据、评测和产品约束，再扩大模型。更复杂的算法无法修复错误标签和错位目标。

## 对 AI 产品经理最有用的判断

| 产品阶段 | 主要问题 | 合理产物 |
| --- | --- | --- |
| ML 之前 | 用户流程和指标是否稳定 | 启发式基线与历史指标 |
| 第一条流水线 | 端到端能否可靠运行 | 简单模型、独立测试和监控 |
| 快速迭代 | 哪些信号稳定增加价值 | 特征实验与版本记录 |
| 平台期 | 复杂度是否值得 | 在线收益、成本和风险比较 |

产品路线图可以沿这四个阶段安排。这样，研究新模型不会挤掉指标、数据和基础设施工作。

## 把规则转化成四次发布评审

推荐团队发现点击率停滞，准备直接更换复杂模型。按 Rules of ML，第一步应核对目标、数据和流水线。若训练样本由旧排序产生，离线改进可能只是在复现旧策略；若线上特征晚到十分钟，模型能力再强也无法使用训练时的信号。团队先保留启发式基线，验证端到端特征一致和监控，再用在线实验判断复杂模型的增益是否超过延迟、算力和维护成本。

这个场景的阅读方法，是先定位系统正在替谁完成什么任务，再识别输出会触发哪一步行动。模型指标只描述能力的一部分。用户理解、数据来源、组织责任、失败恢复和部署后的反馈共同决定产品是否可用。每个判断都应落到可以复查的产物，避免把原则停留在口号。

## 阅读后应当留下的产品工件

| 工件 | 至少包含的内容 |
| --- | --- |
| 启发式基线 | 给模型效果、故障降级和数据生成提供参照 |
| 指标树 | 分开优化目标、报告指标、长期指标和风险护栏 |
| 特征契约 | 记录定义、时间点、负责人、缺失处理和线上可用性 |
| 训练服务一致性测试 | 用同一批对象比较两端特征和预测 |
| 版本比较表 | 同时记录离线、在线、成本和分群结果 |
| 退出方案 | 规定模型服务失败或供应商变化时如何回退 |

工件之间需要能互相追溯。需求中写出的高后果失败，应在评测集里出现，在发布门槛中有判断，在监控与事件响应中有负责人。某份表格独立存在，无法说明风险已经被处理。

## 这份材料要求团队公开哪些取舍

| 选择 | 可能获得的价值 | 同时承担的代价 |
| --- | --- | --- |
| 更复杂模型 | 可能提高离线指标 | 增加延迟、成本和调试难度 |
| 更多特征 | 扩大可学习信号 | 增加依赖和训练服务偏差 |
| 快速发布 | 加快学习 | 需要完整监控和可回滚性 |
| 优化短期行为 | 反馈快 | 可能损害长期价值 |

取舍不能被压成一个平均总分。严重但低频的伤害、特定群体承担的错误和不可逆行动，需要单独设置边界。产品评审的输出应包含采用方案、替代方案、支持证据、未知问题和复评条件。

## 与其他资料配合时的位置

这份材料负责提供一类主要视角。人机交互资料帮助理解用户如何形成期待和控制系统，机器学习系统资料解释数据、模型与基础设施的约束，风险框架负责角色、证据和持续治理，行业文件补充具体后果与专业责任。它们有交集，却不能互相替代。

这份规则产生于生成式 AI 大规模应用之前。它对指标、流水线、一致性和阶段化复杂度的判断仍有效，但提示、检索、工具权限、开放输出安全和供应商漂移需要新的评测与治理补充。

## 产品能力必须由数据、模型和运行系统共同兑现

模型离线得分只是候选能力。它进入产品以后，要在规定时间取得同样定义的数据，经过一致的预处理，在可接受成本内完成推理，再由政策和界面转化为行动。任一环节失效，用户都不会得到离线报告中的效果。产品规格因此要同时写任务质量、系统质量、业务结果和风险护栏。

任务质量描述答案或预测本身，系统质量包含延迟、吞吐、可用性和费用，业务结果观察行为是否改善，护栏负责防止短期收益压过长期损害。四层指标的时间窗口不同。延迟可以实时观察，转化需要几天，留存和伤害可能数月后出现。路线图必须为慢反馈保留评估办法，不能因它难测就只优化最快的数字。

数据也不是一次性交付。采集由旧产品和旧政策决定，模型上线后又会改变曝光与行动，随后产生的新标签已带有反馈。团队应保存事件时间、决策时间、特征可用时间和结果窗口，避免未来信息泄漏；还要记录哪些对象从未获得旧政策下的行动，以免把选择性标签误当完整事实。

发布流程应允许比较和退出。候选模型与基线在同一任务集和在线实验中比较，分群检查尾部与高风险情况，灰度期间保留版本、输入和决定日志。供应商模型升级、费用变化或接口失效时，系统要能降级到受限能力或旧版本。采购外部 API 改变了实现位置，没有取消产品责任。

## 用一次反向检查识别虚假的完成

从最终上线决定向前追踪。这个决定引用了哪些测试和用户证据，证据对应哪个系统版本和使用场景，测试覆盖了哪些已知失败，失败又来自需求中的哪项风险。任何一处断开，都说明团队拥有文档却没有形成证据链。再从事故或用户投诉向后追踪，确认它能否进入负责人、修复、回归测试和下一轮产品决定。

学习这类材料的完成标准，也应采用相同方法。能背出框架名称只是识别；能为一个真实功能建立工件并解释取舍属于应用；更换人群、权限、模型或后果以后，能够重新判断哪些结论失效，才算形成可迁移能力。

## 怎样读材料中的证据与建议

先区分四种内容。原则说明希望保护的价值，过程说明团队应完成的活动，技术证据描述系统在特定条件下的表现，治理证据说明责任和控制确实存在。原则相同，不代表实施动作相同；完成了过程，也不代表结果达标。阅读时可在段落旁标出它属于哪一层，避免把倡议性语言误当成已经验证的产品结论。

再检查证据适用范围。测试使用了什么数据和版本，参与研究的是哪类用户，运行环境与目标市场是否一致，结论观察了多长时间。官方机构或知名公司可以提高来源可信度，不能自动解决本地适用性。引用材料时应写清它支持哪项判断，又不能推出什么。

最后把建议改写成可以失败的检查。与其写“确保透明”，不如检查用户能否说出系统使用了哪些信息、是否知道输出会触发什么行动、发现错误后能否纠正。与其写“加强监控”，不如规定监控对象、窗口、阈值、负责人和处置。只有可能被证据否定的要求，才真正进入产品验收。

完成评审后应保留两份短清单。一份记录当前已经有证据支持的结论，注明版本、场景和日期；另一份记录仍未知或只能依赖假设的部分，注明补证方法和复评时点。把未知明确留下，比用完整表格制造确定感更专业。上线只是证据来源发生变化的节点，真实使用结果会继续修正发布前判断。

下一次产品版本应先回看这两份清单，确认新增能力有没有越过原来的用途、数据和权限边界，并关闭已经取得证据的问题。

## 版本边界

这份指南形成于深度学习和大语言模型大规模产品化之前。它没有系统讨论提示、检索增强、工具调用、生成式评测和 Agent 权限。流水线、指标、训练服务一致性、反馈回路和简单起步的原则仍然适用。

生成式 AI 产品还要补充开放式输出评测、安全策略、供应商版本变化和人工评审。模型由外部 API 提供时，团队仍然需要自己的任务集、监控和退出方案。

## 读完以后应当能够回答

1. 什么条件下启发式基线比立即训练模型更合适。
2. 为什么指标和数据流水线要早于复杂模型。
3. 优化目标、报告指标和政策层分别承担什么责任。
4. 怎样检测训练与服务偏差。
5. 模型改变用户行为以后，离线数据为何不再中立。
6. 收益平台期出现时，应先检查哪些系统条件。
