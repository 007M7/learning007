# 人机交互十八条准则阅读综述

AI 产品的交互难点来自行为不稳定。相同功能会因数据、上下文和模型版本产生不同结果。传统界面只要说明按钮会做什么，AI 界面还要帮助用户形成预期、识别不确定性并修正系统。

微软研究团队从二十多年的人机交互研究中整理候选原则，经过专家评审和多轮验证，最终形成十八条准则。它们按照交互发生的时间组织，比一张没有顺序的设计清单更容易使用。

[阅读微软官方准则](https://www.microsoft.com/en-us/haxtoolkit/ai-guidelines){target="_blank" rel="noopener noreferrer"}

## 四个时段构成完整体验

```text
第一次见到系统        日常共同完成任务
能力与预期             上下文、控制与反馈
       ↓                      ↓
系统给错或做不到       多次使用以后
发现、修正与退出       记忆、适应与更新
```

十八条准则分别进入这四个时段。产品团队若只优化中间的正常交互，会漏掉首次预期和失败恢复。即使平均结果尚可，用户也可能在第一次被夸大的能力误导，或在一次错误后找不到恢复办法，随后放弃产品。

## 初次交互先校准承诺

第一组准则要求系统说明能做什么，并说明当前表现的合理范围。用户第一次看到产品时，会根据名称、宣传语、默认示例和输入框提示推断能力。

“智能医生”会引出诊断与责任期待。“根据这份体检报告整理复诊问题”把任务范围压到可核对的辅助工作。两种命名调用的可能是同一模型，用户采取的行动完全不同。

产品还应在相关时刻说明输出可能变化。这里不需要用大段免责条款破坏体验。可以通过任务示例、来源范围、置信信息和清晰的人工复核提示建立预期。关键在于承诺必须与真实评测一致。

## 正常交互要让上下文和控制权可见

第二组准则关注系统怎样结合当前情境、怎样展示与任务有关的信息，以及用户能否影响结果。AI 需要使用上下文才能提供个性化帮助，过度推断又会越过隐私和控制边界。

邮件助手可以根据当前邮件给出回复，不应悄悄调用用户没有预期的其他私人内容。推荐系统可以利用近期选择，同时要允许用户关闭某类信号。上下文来源越多，产品越需要说明何时使用、怎样修改和如何清除。

交互中的控制权也不能只剩一个取消按钮。用户需要调整目标、约束输出、选择替代方案和纠正误解。系统若能执行外部动作，确认点应随可逆性变化。草拟日程可以自动进行，真正发送邀请需要用户确认。

## 系统出错时，重点是恢复

第三组准则要求支持有效调用、容易纠正和在能力不足时缩小服务范围。模型错误常常看起来像合理答案，产品不能把发现责任全部交给用户。

设计可以展示来源、突出低置信部分、要求用户核对关键字段，或在高风险任务中采用双重确认。用户指出错误以后，系统应保留正确部分并允许局部修改。每次都让用户重写完整输入，会把 AI 节省的时间重新花掉。

系统无法完成任务时，可以提供受支持的替代路径。报销助手无法判断某张模糊发票，应让用户补拍、手动录入或转给财务。继续生成一个猜测值会把技术不确定性变成业务错误。

## 长期使用会产生新的责任

第四组准则讨论系统怎样从行为学习、怎样更新以及如何保持用户控制。个性化会改变结果，用户需要知道系统记住了什么，并能查看、修改或清除。

长期适应还包括行为变化。模型更新可能改变语气、排序和错误分布。用户依靠旧行为建立了工作习惯，产品要为重要变化提供说明和回退。只写“体验升级”无法帮助用户重新判断风险。

系统可以根据反馈调整，但不能让一次偶然操作永久塑造用户画像。适应速度、证据数量和可撤销性都需要设计。高影响偏好适合显式确认，低风险排序可以允许快速纠正。

## 十八条准则怎样进入产品流程

准则适合在概念设计阶段使用。团队先写用户任务和失败代价，再挑出最相关的准则。所有项目一次实现十八条，容易得到一张没有优先级的待办清单。

可以按三项因素排序。

| 因素 | 评审问题 |
| --- | --- |
| 发生概率 | 这种交互或失败出现得多不多 |
| 后果 | 出错会浪费时间、造成经济损失还是伤害用户 |
| 恢复成本 | 用户能否发现、撤销和转人工 |

高概率、高后果、难恢复的项目先进入设计。每条准则随后转成可观察行为和验收证据。比如“支持高效纠正”可以转成用户能在保留其余内容的情况下修改一个错误字段，并在下一次输出中看到更改。

## 准则之间会发生取舍

提供更多解释可能增加认知负担。使用更多上下文可能提高相关性，也会增加隐私风险。个性化可以减少重复操作，同时使不同用户得到难以比较的结果。

准则没有替团队消除这些取舍。团队需要根据任务风险、用户能力、可逆性和监管要求决定实现强度。医疗建议中的人工监督会比娱乐推荐严格，两个场景仍然可以使用同一条原则。

## 常见误用

第一种误用是把准则当作发布前打勾表。准则应在需求和原型阶段改变设计，最后才检查实现。

第二种误用是用界面文案代替能力治理。提示用户“AI 可能出错”，无法弥补没有评测、没有来源和无法撤销。

第三种误用是把信任当成越高越好。目标是适当依赖。系统可靠时用户愿意使用，系统不确定时用户会核对或拒绝。

## 十八条准则要按时间与失败成本使用

写作助手在首次使用时若承诺‘帮你写出完美文章’，用户会把建议当成确定答案。更合适的首屏说明它擅长改写和提纲，不保证事实。交互中显示当前使用的文档范围，让用户能撤销和纠正；系统无法完成时说明缺少什么，而非输出貌似合理的内容。长期使用后，还要让用户看到个性化依据并能清除。四个时间段共同决定信任，不能只在错误弹窗里补一句免责声明。

这个场景的阅读方法，是先定位系统正在替谁完成什么任务，再识别输出会触发哪一步行动。模型指标只描述能力的一部分。用户理解、数据来源、组织责任、失败恢复和部署后的反馈共同决定产品是否可用。每个判断都应落到可以复查的产物，避免把原则停留在口号。

## 阅读后应当留下的产品工件

| 工件 | 至少包含的内容 |
| --- | --- |
| 准则适用矩阵 | 把十八条准则映射到首次、常规、失败和长期交互 |
| 失败模式清单 | 按发生概率、用户后果和可恢复性排序 |
| 界面状态图 | 覆盖加载、无结果、低置信、冲突、拒答和降级 |
| 控制权检查 | 确认用户能预览、撤销、覆盖和退出自动化 |
| 信任校准测试 | 检验用户是否准确理解能力与限制 |
| 长期适应记录 | 说明系统学到了什么以及如何重置 |

工件之间需要能互相追溯。需求中写出的高后果失败，应在评测集里出现，在发布门槛中有判断，在监控与事件响应中有负责人。某份表格独立存在，无法说明风险已经被处理。

## 这份材料要求团队公开哪些取舍

| 选择 | 可能获得的价值 | 同时承担的代价 |
| --- | --- | --- |
| 提前解释限制 | 减少错误期待 | 过多说明会阻断首次体验 |
| 主动执行 | 提高效率 | 压缩用户确认机会 |
| 一致行为 | 便于形成心智模型 | 难以适应情境变化 |
| 个性化记忆 | 降低重复输入 | 增加隐私和过度依赖 |

取舍不能被压成一个平均总分。严重但低频的伤害、特定群体承担的错误和不可逆行动，需要单独设置边界。产品评审的输出应包含采用方案、替代方案、支持证据、未知问题和复评条件。

## 与其他资料配合时的位置

这份材料负责提供一类主要视角。人机交互资料帮助理解用户如何形成期待和控制系统，机器学习系统资料解释数据、模型与基础设施的约束，风险框架负责角色、证据和持续治理，行业文件补充具体后果与专业责任。它们有交集，却不能互相替代。

准则是启发式检查，不是每条都必须出现在每个界面。团队需要根据任务、风险和用户能力选择优先级，再用研究验证。满足十八条也不能证明产品安全、公平或有效。

## 从界面可用继续走到依赖是否恰当

人机交互设计的目标并非让用户始终相信 AI。合理结果是用户能准确判断什么时候可以依赖，什么时候需要核查，以及出错后如何恢复。首次体验负责建立能力范围，日常交互负责提供上下文和控制，失败状态负责降低损失，长期使用还要处理习惯、个性化和能力变化。

验证时不能只问用户是否喜欢界面。研究任务应检查用户能否预测系统行为，是否知道输出依据，能否发现明显错误，是否会在高后果动作前停下来，以及纠正反馈能否到达真正负责的环节。完成率提高可能来自用户盲目接受，解释点击率低也可能因为解释与行动无关。定量指标需要和访谈、行为观察、错误恢复测试一起解释。

自动化程度最好按任务拆分。同一流程中，检索资料可以自动完成，生成草稿可以默认建议，发送、审批或资金操作则保留确认。决定依据包含错误严重度、可逆性、时间压力、用户专业能力和系统置信证据。给整个产品贴上“辅助”或“自动”标签，会掩盖不同动作的风险差异。

长期反馈还会改变产品。用户可能为了迎合系统调整输入，运营人员可能绕开难用步骤，个性化可能让行为越来越难以比较。团队要同时观察建议、实际行动、结果和纠正，才能判断系统在帮助用户，还是让用户承担了更多核查工作。

## 用一次反向检查识别虚假的完成

从最终上线决定向前追踪。这个决定引用了哪些测试和用户证据，证据对应哪个系统版本和使用场景，测试覆盖了哪些已知失败，失败又来自需求中的哪项风险。任何一处断开，都说明团队拥有文档却没有形成证据链。再从事故或用户投诉向后追踪，确认它能否进入负责人、修复、回归测试和下一轮产品决定。

学习这类材料的完成标准，也应采用相同方法。能背出框架名称只是识别；能为一个真实功能建立工件并解释取舍属于应用；更换人群、权限、模型或后果以后，能够重新判断哪些结论失效，才算形成可迁移能力。

## 怎样读材料中的证据与建议

先区分四种内容。原则说明希望保护的价值，过程说明团队应完成的活动，技术证据描述系统在特定条件下的表现，治理证据说明责任和控制确实存在。原则相同，不代表实施动作相同；完成了过程，也不代表结果达标。阅读时可在段落旁标出它属于哪一层，避免把倡议性语言误当成已经验证的产品结论。

再检查证据适用范围。测试使用了什么数据和版本，参与研究的是哪类用户，运行环境与目标市场是否一致，结论观察了多长时间。官方机构或知名公司可以提高来源可信度，不能自动解决本地适用性。引用材料时应写清它支持哪项判断，又不能推出什么。

最后把建议改写成可以失败的检查。与其写“确保透明”，不如检查用户能否说出系统使用了哪些信息、是否知道输出会触发什么行动、发现错误后能否纠正。与其写“加强监控”，不如规定监控对象、窗口、阈值、负责人和处置。只有可能被证据否定的要求，才真正进入产品验收。

完成评审后应保留两份短清单。一份记录当前已经有证据支持的结论，注明版本、场景和日期；另一份记录仍未知或只能依赖假设的部分，注明补证方法和复评时点。把未知明确留下，比用完整表格制造确定感更专业。上线只是证据来源发生变化的节点，真实使用结果会继续修正发布前判断。

下一次产品版本应先回看这两份清单，确认新增能力有没有越过原来的用途、数据和权限边界，并关闭已经取得证据的问题。

## 读完以后应当能够回答

1. 当前功能在四个交互时段分别有哪些风险。
2. 首次使用怎样建立准确预期。
3. 上下文使用和用户控制怎样共同设计。
4. 用户怎样发现并局部修正错误。
5. 系统记忆和个性化如何查看、修改和撤销。
6. 哪些准则应先实现，优先级依据是什么。
