# Machine Learning Systems 阅读综述

一个模型文件不能独立创造产品价值。它需要数据进入，需要计算资源完成训练，需要服务接住请求，还要在数据和用户变化以后被监测、更新和治理。《Machine Learning Systems》把视野从算法扩大到这条完整过程。

本书由 Harvard CS249r 团队维护，开放在线阅读。第一卷围绕机器学习系统基础展开，第二卷继续讨论生成式 AI 系统。本综述以第一卷为主。

这条过程说明模型准确率只是系统质量的一部分。延迟、吞吐、能耗、内存、隐私、可靠性和公平会共同决定产品能否运行。

## 第一部分建立系统视角

开篇先区分机器学习模型和机器学习系统。模型把输入映射到输出，系统负责产生输入、调用模型、解释输出并把结果送入业务流程。系统还包含数据管道、特征处理、训练基础设施、服务接口、监控和人工角色。

同一模型放进不同系统会产生不同结果。图像分类器在实验室处理清晰图片，上线后可能遇到压缩、弱光、设备差异和未知类别。系统设计要把这些条件写进需求，不能默认线上世界会服从训练数据。

机器学习工作流从问题定义开始，随后经历数据、模型、评价、部署和运维。各阶段会反向影响前面的决定。部署设备内存不足，模型结构需要改变。反馈数据受旧模型影响，下一轮训练要重新判断采样偏差。

## 数据选择决定可学到什么

数据工程章节处理采集、清洗、标注、存储和版本。数据选择章节进一步追问哪些样本值得进入训练。更多数据会增加覆盖，也会带来冗余、质量差异和计算成本。

产品经理应关注数据单位、时间范围、群体覆盖和标签形成方式。一个异常检测系统用已处理工单作标签，只看见被发现并进入流程的问题。未被记录的异常不会自动成为负样本。系统需要把数据生成过程和业务流程一起建模。

数据版本必须与模型版本绑定。没有训练快照、转换代码和标签规则，团队无法解释一次性能变化来自哪里。数据文档还要记录许可、隐私和允许用途，这些条件会限制产品可以服务的人群和场景。

## 训练系统把算法变成计算过程

训练章节从优化目标走向批处理、并行计算和资源调度。框架提供自动微分、张量运算、设备管理和分布式执行。它降低实现成本，也隐藏了内存移动、同步和数值精度等系统行为。

神经网络计算并非只有浮点运算数量。数据从内存搬到处理器可能比计算更慢。批大小影响吞吐、显存和收敛。混合精度可以提高速度并降低内存，数值范围处理不当又会让训练不稳定。

产品计划中的训练成本要包含实验次数、失败重跑、数据处理和超参数搜索。只按最终一次训练报价，会低估研发预算。

## 模型压缩改变的是质量组合

剪枝、量化、知识蒸馏和低秩方法减少模型大小或计算量。它们适合资源受限设备和高并发服务。压缩不是免费优化，精度、校准、群体表现和可调试性可能变化。

量化把高精度数值映射到较少位宽，通常提高吞吐并降低内存。少数异常通道可能承受更大误差。蒸馏让小模型学习大模型输出，学生模型会继承教师的行为和偏差，也可能在教师不确定的区域表现得更差。

压缩后要重新执行任务评测和风险切片。原模型通过不代表压缩版本自动通过。

## 硬件和基准测试怎样进入产品判断

硬件加速章节介绍 CPU、GPU 和专用加速器的并行结构。硬件选择影响延迟、吞吐、能耗、成本和可部署地点。边缘设备强调功耗与内存，云端批处理强调吞吐，实时交互强调尾延迟。

基准测试必须接近真实工作负载。平均延迟掩盖高峰和长尾，离线吞吐无法代表多租户服务。团队要固定模型、批大小、精度、硬件、并发和输入长度，报告结果才可比较。

对于生成式产品，输入和输出长度会显著改变时延与费用。单次演示的首字延迟不能代替完整会话中的资源消耗。

## 服务系统要处理现实流量

模型服务连接请求路由、预处理、推理、后处理和返回。在线服务关注低延迟，批处理关注吞吐，流式服务还要处理部分结果、中断和背压。

扩缩容不能只看请求数。输入大小、模型版本和硬件占用会改变每个请求成本。缓存可以减少重复计算，也会带来过期、隐私和一致性问题。多模型系统需要记录路由规则，否则用户问题难以回放。

上线策略可采用影子流量、灰度和金丝雀。新模型先接收真实输入但不影响用户，随后只服务少量流量。团队同时比较质量、延迟、错误和业务指标，满足门槛再扩大。

## MLOps 维持长期可控

MLOps 把数据、代码、模型、配置和基础设施放进可重复流程。持续训练不意味着每次有新数据就自动发布。系统要先验证数据和模型，通过后再进入部署。

监控至少覆盖输入、输出、服务和业务反馈。输入漂移说明用户或环境变化，输出分布变化可能来自模型或数据，服务指标发现超时和错误，业务反馈判断结果是否仍有用。没有延迟标签时，代理指标可以提前告警，最终仍要回到真实结果。

事故处理需要版本回退、流量切换和证据保存。模型事故常横跨数据、代码和业务流程，单看应用日志很难定位。

## 责任工程贯穿系统

责任工程章节没有把伦理放在最后做声明。公平、隐私、安全、透明和环境影响会改变数据、模型、硬件和部署选择。

隐私限制数据收集和日志保存，公平要求按群体切片评测，安全要求建立攻击面和权限边界，环境影响进入训练与服务成本。责任要求需要负责人、证据和停止条件，才能进入工程流程。

## 产品经理怎样使用这本书

先选一个真实功能，把它画成系统图。标出数据来源、训练、模型仓库、服务、用户行动和反馈。随后为每条连接补上质量属性。

| 系统位置 | 主要问题 |
| --- | --- |
| 数据入口 | 新鲜度、代表性、许可和标签质量 |
| 训练 | 可重复性、预算、数值稳定和版本 |
| 推理 | 延迟、吞吐、成本和降级 |
| 业务动作 | 可逆性、权限和人工监督 |
| 反馈 | 延迟、偏差、隐私和污染 |

这张图能帮助产品路线图同时容纳用户功能和系统工作。没有数据版本、监控和回退的功能，完成度不应写成百分之百。

## 从模型指标走向完整系统预算

视觉质检模型离线准确率提高两个百分点，上线后却因相机变化、边缘设备算力和网络中断频繁失效。系统视角会把数据采集、标注、训练、压缩、硬件、部署和监控放进同一个设计。产品经理需要明确每个设备的延迟和能耗预算，定义无法判断时的人工回退，监控输入漂移和设备版本，并计算更新模型带来的停机与带宽成本。

这个场景的阅读方法，是先定位系统正在替谁完成什么任务，再识别输出会触发哪一步行动。模型指标只描述能力的一部分。用户理解、数据来源、组织责任、失败恢复和部署后的反馈共同决定产品是否可用。每个判断都应落到可以复查的产物，避免把原则停留在口号。

## 这份材料要求团队公开哪些取舍

| 选择 | 可能获得的价值 | 同时承担的代价 |
| --- | --- | --- |
| 模型质量 | 改善任务结果 | 通常增加算力或响应时间 |
| 端侧推理 | 低延迟与隐私 | 受内存、功耗和更新能力限制 |
| 统一模型 | 降低运维复杂度 | 可能无法适应设备和人群差异 |
| 频繁更新 | 快速吸收数据 | 扩大兼容和回归风险 |

取舍不能被压成一个平均总分。严重但低频的伤害、特定群体承担的错误和不可逆行动，需要单独设置边界。产品评审的输出应包含采用方案、替代方案、支持证据、未知问题和复评条件。

## 与其他资料配合时的位置

这份材料负责提供一类主要视角。人机交互资料帮助理解用户如何形成期待和控制系统，机器学习系统资料解释数据、模型与基础设施的约束，风险框架负责角色、证据和持续治理，行业文件补充具体后果与专业责任。它们有交集，却不能互相替代。

系统教材提供技术全景，不会替具体产品确定价值目标。基准结果只在指定硬件、负载和数据下成立。采购模型或 API 也没有移除系统责任，只是把部分实现移到供应商边界。

## 产品能力必须由数据、模型和运行系统共同兑现

模型离线得分只是候选能力。它进入产品以后，要在规定时间取得同样定义的数据，经过一致的预处理，在可接受成本内完成推理，再由政策和界面转化为行动。任一环节失效，用户都不会得到离线报告中的效果。产品规格因此要同时写任务质量、系统质量、业务结果和风险护栏。

任务质量描述答案或预测本身，系统质量包含延迟、吞吐、可用性和费用，业务结果观察行为是否改善，护栏负责防止短期收益压过长期损害。四层指标的时间窗口不同。延迟可以实时观察，转化需要几天，留存和伤害可能数月后出现。路线图必须为慢反馈保留评估办法，不能因它难测就只优化最快的数字。

数据也不是一次性交付。采集由旧产品和旧政策决定，模型上线后又会改变曝光与行动，随后产生的新标签已带有反馈。团队应保存事件时间、决策时间、特征可用时间和结果窗口，避免未来信息泄漏；还要记录哪些对象从未获得旧政策下的行动，以免把选择性标签误当完整事实。

发布流程应允许比较和退出。候选模型与基线在同一任务集和在线实验中比较，分群检查尾部与高风险情况，灰度期间保留版本、输入和决定日志。供应商模型升级、费用变化或接口失效时，系统要能降级到受限能力或旧版本。采购外部 API 改变了实现位置，没有取消产品责任。

## 用一次反向检查识别虚假的完成

从最终上线决定向前追踪。这个决定引用了哪些测试和用户证据，证据对应哪个系统版本和使用场景，测试覆盖了哪些已知失败，失败又来自需求中的哪项风险。任何一处断开，都说明团队拥有文档却没有形成证据链。再从事故或用户投诉向后追踪，确认它能否进入负责人、修复、回归测试和下一轮产品决定。

学习这类材料的完成标准，也应采用相同方法。能背出框架名称只是识别；能为一个真实功能建立工件并解释取舍属于应用；更换人群、权限、模型或后果以后，能够重新判断哪些结论失效，才算形成可迁移能力。

## 怎样读材料中的证据与建议

先区分四种内容。原则说明希望保护的价值，过程说明团队应完成的活动，技术证据描述系统在特定条件下的表现，治理证据说明责任和控制确实存在。原则相同，不代表实施动作相同；完成了过程，也不代表结果达标。阅读时可在段落旁标出它属于哪一层，避免把倡议性语言误当成已经验证的产品结论。

再检查证据适用范围。测试使用了什么数据和版本，参与研究的是哪类用户，运行环境与目标市场是否一致，结论观察了多长时间。官方机构或知名公司可以提高来源可信度，不能自动解决本地适用性。引用材料时应写清它支持哪项判断，又不能推出什么。

最后把建议改写成可以失败的检查。与其写“确保透明”，不如检查用户能否说出系统使用了哪些信息、是否知道输出会触发什么行动、发现错误后能否纠正。与其写“加强监控”，不如规定监控对象、窗口、阈值、负责人和处置。只有可能被证据否定的要求，才真正进入产品验收。

完成评审后应保留两份短清单。一份记录当前已经有证据支持的结论，注明版本、场景和日期；另一份记录仍未知或只能依赖假设的部分，注明补证方法和复评时点。把未知明确留下，比用完整表格制造确定感更专业。上线只是证据来源发生变化的节点，真实使用结果会继续修正发布前判断。

下一次产品版本应先回看这两份清单，确认新增能力有没有越过原来的用途、数据和权限边界，并关闭已经取得证据的问题。

## 阅读边界

本书技术密度较高，硬件与训练部分对只做 API 集成的团队可以选读。外部模型服务减少训练工作，没有消除任务评测、路由、监控、隐私和供应商风险。

第一卷的核心是机器学习系统。Agent 权限、检索增强、长上下文和生成式安全需要结合第二卷与近期论文。具体硬件性能也会快速变化，比较时应使用当前基准。

## 读完以后应当能够回答

1. 模型和机器学习系统的边界在哪里。
2. 数据生成过程怎样限制模型结论。

5. 在线服务应怎样灰度、监控和回退。
6. 责任要求怎样进入数据、评测和运维工作。

## 在深度学习模块中进一步读这本书

同一本书进入不同学习模块，承担的任务会发生变化。下面几节补足它与深度学习路线的连接，不重复前文书目信息，也不把原书章节改写成资料清单。每节都从一个可以判断的问题出发，并给出对应练习与边界。阅读时可以在纸上保留三栏，依次记录原书结论、本地例子和失败条件。这样增加的内容会回到具体判断，不会成为另一组悬空术语。

### 为什么模型必须作为系统交付

用户接触的是包含数据入口、特征处理、模型、服务、权限和反馈的完整产品。这一部分应与原书对应章节一起读，先确定作者处理的对象，再查看它怎样进入计算或实验。

离线模型质量只覆盖其中一个组件，任何接口错误或分布变化都会改变最终结果。可以用一份小数据把过程从输入走到输出，记录每个中间结果。若只能复述结论，却无法指出数据在哪里变化，理解仍然停在术语层。

系统验收需要同时验证端到端任务和各组件中间量。把这条限制写进笔记，随后设计一个会触发它的反例。反例能帮助读者区分方法自身能力、数据覆盖和工程实现，后续读论文时也知道新工作究竟修正了哪一项。

### 数据、训练和服务版本怎样共同变化

训练数据、代码、参数、依赖和服务配置共同决定一个可运行版本。这一部分应与原书对应章节一起读，先确定作者处理的对象，再查看它怎样进入计算或实验。

只保存权重无法复现预处理，也无法解释线上输出来自哪批数据。可以用一份小数据把过程从输入走到输出，记录每个中间结果。若只能复述结论，却无法指出数据在哪里变化，理解仍然停在术语层。

注册、血缘和可回滚发布让错误能够定位到具体变化。把这条限制写进笔记，随后设计一个会触发它的反例。反例能帮助读者区分方法自身能力、数据覆盖和工程实现，后续读论文时也知道新工作究竟修正了哪一项。
