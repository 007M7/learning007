# OECD AI 系统分类框架阅读综述

团队说“我们在做一个大模型产品”，信息仍然很少。模型服务谁，在哪种行业运行，使用什么数据，输出进入哪个决定，失败影响谁，这些条件共同决定系统性质。OECD 分类框架提供五个维度，让政策制定者和产品团队用一致方式描述 AI 系统。

[阅读 OECD 官方正文](https://www.oecd.org/en/publications/oecd-framework-for-the-classification-of-ai-systems_cb6d9eca-en.html){target="_blank" rel="noopener noreferrer"}

## 分类框架要解决的沟通问题

AI 系统跨行业、技术和用途。只按算法分类，无法解释社会影响。只按高风险或低风险分类，又会过早压缩细节。

OECD 采用五个相互关联的维度。

```text
人员与地球
谁受影响，影响怎样分布
        ↕
经济情境
系统用于哪个行业、组织和商业环境
        ↕
数据与输入 → AI 模型 → 任务与输出
```

这五个维度共同形成系统画像。分类不是给系统贴一个永久标签，系统用途、数据和用户改变后，画像也要更新。

## 人员与地球维度先看影响

这一维度描述直接用户、间接受影响者、规模、选择权和环境影响。系统可能服务一位专业人员，也可能影响没有直接使用产品的公众。

招聘筛选工具的使用者是招聘团队，候选人承担主要影响。内容推荐的直接用户可以选择退出，内容创作者和社会信息环境仍可能受到影响。产品经理要把这些角色分开。

影响范围还包括集体和环境。模型训练与服务使用能源，推荐系统可能改变信息分布。分类框架提醒团队不要把用户界面范围当成系统影响范围。

## 经济情境决定约束

经济维度描述行业、业务功能、组织规模、关键性和部署环境。相同模型进入医疗、制造和娱乐，会面对不同容错、数据和监管条件。

组织采用方式也重要。系统由内部团队构建、外部采购或多家供应商组合，责任和可见性不同。平台规模扩大后，一个小错误可能影响大量用户。

产品需求可以在这里记录业务目标、替代流程、资源预算和依赖。模型是否提高效率，要与新增审核、培训、集成和事故成本一起计算。

## 数据与输入维度描述系统看见什么

数据可以由人、传感器、软件或其他系统产生，也可以是结构化、非结构化、静态或动态。来源、采集方式、权利和质量会限制模型行为。

团队要说明输入是否包含个人或敏感信息，是否实时变化，标签怎样形成，哪些群体缺失。生成式系统还会接收用户提示、检索内容和工具返回，它们都属于系统输入。

输入变化会改变风险。原本只处理公开文档的助手接入内部邮件后，隐私与权限边界需要重做。

## 模型维度记录技术特征

模型维度包括模型类型、学习方式、训练方式、目标和可解释程度。框架不要求把所有算法细节放进政策讨论，只保留会改变能力和风险的技术特征。

模型是固定还是持续更新，会影响验证方式。集中训练和联邦训练有不同数据路径。通用模型经过微调、提示或检索进入产品，部署方仍要记录自己的系统层改造。

自主程度不能只用“Agent”判断。产品应描述系统能选择哪些动作、调用什么工具、需要哪些确认和怎样停止。

## 任务与输出维度连接真实行动

任务可能是识别、预测、推荐、生成或自动执行。输出可以是分数、标签、内容、排序和物理动作。输出进入哪项决定，决定了错误后果。

同一个风险分数可以供专家参考，也可以自动拒绝申请。模型不变，系统自主程度和申诉需求已经变化。产品经理要把模型输出与业务动作分开描述。

输出频率、时间约束和可逆性同样重要。每天批量生成报告与实时驾驶控制需要不同可靠性和恢复设计。

## 五个维度怎样用于需求评审

团队可以为一个功能填写系统卡。

| 维度 | 必须回答的问题 |
| --- | --- |
| 人员与地球 | 谁使用，谁受影响，能否退出，环境代价怎样 |
| 经济情境 | 在什么行业和组织流程中运行，替代方案是什么 |
| 数据与输入 | 数据从哪里来，代表谁，权限和更新怎样处理 |
| 模型 | 能力怎样获得，版本如何变化，有哪些已知限制 |
| 任务与输出 | 系统产生什么，进入哪个行动，能否撤销和申诉 |

五个维度填完以后，团队再做风险分级和评测。跳过描述直接判断“低风险”，很难留下可复核依据。

## 分类可以支持哪些工作

政策团队可以比较不同系统，确定哪些条件触发额外义务。采购团队可以用同一字段比较供应商。评测团队根据用户、输入和输出设计任务切片。事故团队可以判断变化发生在哪个维度。

框架也支持版本管理。模型没有改变，数据来源和业务动作改变，系统画像仍要更新。这样风险评审不会只盯着模型版本号。

## 容易发生的误用

第一种误用是把五维表填成系统介绍。每项应记录会改变评测、控制和责任的条件。

第二种误用是把分类当作风险结论。框架帮助描述系统，具体风险仍需结合影响和证据判断。

第三种误用是只描述开发者意图。真实用户可能扩展用途，监控要观察系统实际进入了哪些任务。

## 五个维度把‘一个 AI’还原成具体系统

两个产品都使用同一基础模型。一个在公开网站回答旅游问题，另一个在企业内部评估员工。模型名称相同，受影响人群、数据敏感性、行动后果、监管环境和申诉权完全不同。OECD 分类框架让团队分别描述人员与地球、经济情境、数据输入、模型特征、任务与输出，从而避免用模型品牌代替系统分析。

这个场景的阅读方法，是先定位系统正在替谁完成什么任务，再识别输出会触发哪一步行动。模型指标只描述能力的一部分。用户理解、数据来源、组织责任、失败恢复和部署后的反馈共同决定产品是否可用。每个判断都应落到可以复查的产物，避免把原则停留在口号。

## 阅读后应当留下的产品工件

| 工件 | 至少包含的内容 |
| --- | --- |
| 五维系统卡 | 逐项记录影响情境、输入、模型和输出 |
| 相关方地图 | 包含使用者、被影响者、运营者和第三方 |
| 行动链 | 说明输出怎样被人或系统转化为现实决定 |
| 环境与规模记录 | 写出行业、地区、部署范围和资源影响 |
| 版本差异 | 系统用途、数据或模型变化时重新分类 |
| 比较矩阵 | 用共同维度比较多个候选系统 |

工件之间需要能互相追溯。需求中写出的高后果失败，应在评测集里出现，在发布门槛中有判断，在监控与事件响应中有负责人。某份表格独立存在，无法说明风险已经被处理。

## 这份材料要求团队公开哪些取舍

| 选择 | 可能获得的价值 | 同时承担的代价 |
| --- | --- | --- |
| 分类简洁 | 便于沟通 | 会压缩重要情境 |
| 技术粒度 | 支持工程分析 | 可能遮住社会后果 |
| 统一维度 | 便于跨系统比较 | 行业术语仍需补充 |
| 一次登记 | 成本较低 | 无法反映持续演进 |

取舍不能被压成一个平均总分。严重但低频的伤害、特定群体承担的错误和不可逆行动，需要单独设置边界。产品评审的输出应包含采用方案、替代方案、支持证据、未知问题和复评条件。

## 与其他资料配合时的位置

这份材料负责提供一类主要视角。人机交互资料帮助理解用户如何形成期待和控制系统，机器学习系统资料解释数据、模型与基础设施的约束，风险框架负责角色、证据和持续治理，行业文件补充具体后果与专业责任。它们有交集，却不能互相替代。

分类描述系统，不直接判定风险高低、合规或伦理正当。它适合成为治理与需求评审的共同入口，后续仍要进行影响评估和领域审查。

## 治理的基本单位是可追溯决定

风险框架常被误用成问题清单。真正治理需要把系统情境、风险判断、证据、处置、负责人和复评条件连成一条记录。系统为什么存在，谁会受到影响，错误通过什么行动造成后果，当前证据覆盖哪些群体和环境，组织接受了多少剩余风险，都应能够从最终决定追溯。

风险登记册中的一行至少包含风险事件、触发条件、受影响对象、严重度与可恢复性、现有控制、支持证据、剩余缺口和所有者。写“模型可能产生偏见”无法指导行动；写明“夜班环境的低照度图像使某类缺陷漏检，并导致人工抽检减少”，才可能安排数据补充、分群测试、界面提示和人工保底。

测量不应追求单一总分。准确、公平、隐私、安全、透明与稳健可能相互制约，且证据强度不同。团队需要同时保留定量测试、用户研究、专家评审、供应商材料和运行事件，标明样本、版本、环境与不确定性。没有证据的“已满足”应改成假设或待办，外部认证也不能替代本地用途验证。

治理要随变化重开。用途扩大、数据来源变化、模型更新、工具权限增加、法律环境改变或出现事故，都可能使旧判断失效。复评触发器和停止条件应在上线前确定。遇到不可逆且证据不足的风险，合理动作可能是限制范围、增加人工审核或暂缓发布，而不只是继续优化指标。

## 用一次反向检查识别虚假的完成

从最终上线决定向前追踪。这个决定引用了哪些测试和用户证据，证据对应哪个系统版本和使用场景，测试覆盖了哪些已知失败，失败又来自需求中的哪项风险。任何一处断开，都说明团队拥有文档却没有形成证据链。再从事故或用户投诉向后追踪，确认它能否进入负责人、修复、回归测试和下一轮产品决定。

学习这类材料的完成标准，也应采用相同方法。能背出框架名称只是识别；能为一个真实功能建立工件并解释取舍属于应用；更换人群、权限、模型或后果以后，能够重新判断哪些结论失效，才算形成可迁移能力。

## 怎样读材料中的证据与建议

先区分四种内容。原则说明希望保护的价值，过程说明团队应完成的活动，技术证据描述系统在特定条件下的表现，治理证据说明责任和控制确实存在。原则相同，不代表实施动作相同；完成了过程，也不代表结果达标。阅读时可在段落旁标出它属于哪一层，避免把倡议性语言误当成已经验证的产品结论。

再检查证据适用范围。测试使用了什么数据和版本，参与研究的是哪类用户，运行环境与目标市场是否一致，结论观察了多长时间。官方机构或知名公司可以提高来源可信度，不能自动解决本地适用性。引用材料时应写清它支持哪项判断，又不能推出什么。

最后把建议改写成可以失败的检查。与其写“确保透明”，不如检查用户能否说出系统使用了哪些信息、是否知道输出会触发什么行动、发现错误后能否纠正。与其写“加强监控”，不如规定监控对象、窗口、阈值、负责人和处置。只有可能被证据否定的要求，才真正进入产品验收。

完成评审后应保留两份短清单。一份记录当前已经有证据支持的结论，注明版本、场景和日期；另一份记录仍未知或只能依赖假设的部分，注明补证方法和复评时点。把未知明确留下，比用完整表格制造确定感更专业。上线只是证据来源发生变化的节点，真实使用结果会继续修正发布前判断。

下一次产品版本应先回看这两份清单，确认新增能力有没有越过原来的用途、数据和权限边界，并关闭已经取得证据的问题。

## 内容边界

OECD 框架面向跨领域沟通，技术实现和风险测试不够细。它可以成为系统登记和评审入口，不能替代 NIST AI RMF、行业标准或本地法律。

生成式 AI 和 Agent 快速发展后，输入来源、组件依赖和自主动作需要写得更细。框架本身允许扩展，团队应保持稳定字段并补充新风险。

## 读完以后应当能够回答

1. 为什么只写模型名称无法描述一套 AI 系统。
2. 五个维度分别提供什么决策信息。
3. 直接用户和间接受影响者怎样区分。
4. 数据、模型不变时，什么产品变化仍会改变风险。
5. 模型输出与业务动作为何要分开记录。
6. 分类画像怎样连接采购、评测、治理和版本管理。
