# NIST AI RMF 1.0 阅读综述

AI 风险很难用一张通用清单处理。相同模型用于娱乐推荐和医疗分诊，影响对象、失败代价和监管要求都不同。NIST AI Risk Management Framework 1.0 提供一套共同语言，让组织在具体场景中识别、测量和管理风险。

框架自愿使用、与行业无关，也不替代法律。它强调结果和过程，允许不同组织根据情境建立 Profile。

[阅读 NIST 官方 PDF](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf){target="_blank" rel="noopener noreferrer"}

## 风险先从影响关系理解

框架把 AI 风险放在个人、群体、组织、社会和环境多个层次。风险可以短期或长期、局部或系统、高概率或低概率。收益也需要纳入管理，团队要比较采用和不采用 AI 的后果。

AI 风险有几项特殊困难。系统行为受训练数据和使用环境影响，难以完整预测。指标可能缺少统一定义，真实结果在部署后才出现。不同角色对可接受风险的判断也不同。

风险管理因此需要跨职能参与。产品、工程、数据、设计、领域专家、法务、运营、用户和受影响群体提供不同证据。没有任何单一角色能独立看见全部风险。

## 可信 AI 包含多项特征

NIST 列出若干相互关联的可信特征，包括有效可靠、安全、韧性、可问责透明、可解释、隐私增强以及管理有害偏差的公平性。

这些特征会冲突。增加日志有助于问责，也可能增加隐私风险。更严格的安全过滤可能降低部分用户的可用性。团队需要根据场景排序，并记录取舍依据。

“可信”也不是系统自身的永久标签。它取决于用途、用户、环境和管理过程。一个模型在原定任务中通过评测，被重新用于另一人群后需要重新判断。

## 生命周期和 AI 角色

框架覆盖设计、开发、部署、运行和退役。风险会在每个阶段出现，也可能由供应商和使用方共同产生。

AI 角色包括系统构建者、部署者、运营者、评估者和受影响者。组织要明确谁拥有风险决定、谁提供证据、谁有权停止系统。外购 API 不会把责任全部转给供应商。部署方仍然决定任务、数据、界面和行动。

第三方组件还会形成供应链风险。模型版本、训练信息和安全策略可能不可见。合同要覆盖变更通知、数据处理、可用性、事故支持和退出条件。

## Govern 建立长期治理能力

Govern 位于其他三项职能之外并贯穿全程。它处理政策、角色、培训、文化、文档和责任。

组织先定义风险容忍度和升级路径。高风险系统需要更强独立评估和管理层监督。团队还要建立来源清单、版本记录、例外审批和事故报告。

治理不能只由委员会存在来证明。真正证据包括明确负责人、定期评审、可执行停止权和风险进入路线图的记录。

## Map 建立情境和影响地图

Map 要求团队描述用途、用户、环境、依赖和潜在影响。它回答系统在什么条件下工作，谁获得收益，谁承担风险。

产品需求在这里被重新检查。任务目标、替代方案、利益相关者、数据来源和人机分工都要写清。团队还要考虑误用和超范围使用。一个辅助写作工具可能被用户拿去生成医疗建议，产品需要决定检测、限制和提示方式。

Map 的产物可以是一份情境说明与风险登记。风险条目包含受影响对象、触发条件、后果和当前控制。没有情境，后面的测量会变成通用指标堆积。

## Measure 把风险变成证据

Measure 选择方法评估可信特征和风险。技术测试、人工评审、用户研究、红队和影响评估可以组合。

测量要覆盖正常任务、边界、群体切片和失败条件。平均准确率不说明小群体表现，自动指标也无法替代所有人类判断。团队应记录不确定性和测量限制。

独立评估能减少开发团队的确认偏差。高影响系统还要检查测试环境与实际部署是否一致。测量结果需要版本化，模型、数据或用途改变后重新执行。

## Manage 选择、实施并监控措施

Manage 根据 Map 和 Measure 的证据排序风险，决定接受、降低、转移或避免。某些风险可以通过模型改进降低，有些需要改变界面、流程、权限或适用范围。

团队要为高优先级风险指定负责人、期限、剩余风险和监控信号。上线决定应有明确门槛。风险超过容忍度时，系统需要降级、暂停或退役。

管理是持续过程。实际使用产生新证据，团队回到 Map 和 Measure 更新判断。事故、投诉、分布变化和供应商更新都是触发器。

## Profile 把通用框架落到具体组织

Current Profile 描述当前做法和风险状态，Target Profile 描述目标状态。两者差距形成改进路线。

Profile 可以按行业、任务或组织定制。客服摘要工具与信贷审批系统不会采用同一强度。Profile 的价值在于保留共同语言，同时允许情境差异。

产品路线图可以引用 Profile 中的差距。缺少群体评测、没有供应商变更通知和回退时间过长，都可以转成可跟踪工作项。

## 用四项职能评审一个 AI 功能

| 职能 | 产品评审问题 | 产物 |
| --- | --- | --- |
| Govern | 谁负责决定与升级 | 角色、政策、审批和停止权 |
| Map | 系统在哪里影响谁 | 情境说明和风险登记 |
| Measure | 用什么证据判断风险 | 评测计划、结果和限制 |
| Manage | 怎样处理剩余风险 | 措施、监控、回退和复审 |

四项职能会循环。管理措施改变系统以后，团队需要重新测量。使用场景扩展以后，团队需要重新 Map。

## 四项职能怎样形成闭环而非四张清单

金融机构引入文档摘要功能。Govern 先确定负责人、风险容忍度和第三方采购规则；Map 描述用户、文档敏感性、错误如何进入决策以及受影响人群；Measure 设计事实一致性、隐私泄露、分群表现和人工校验；Manage 根据证据限制适用文档、设置人工确认、监控事故并决定是否上线。新用途或供应商版本变化后，团队再次回到 Map，而非沿用旧结论。

这个场景的阅读方法，是先定位系统正在替谁完成什么任务，再识别输出会触发哪一步行动。模型指标只描述能力的一部分。用户理解、数据来源、组织责任、失败恢复和部署后的反馈共同决定产品是否可用。每个判断都应落到可以复查的产物，避免把原则停留在口号。

## 阅读后应当留下的产品工件

| 工件 | 至少包含的内容 |
| --- | --- |
| 治理章程 | 明确角色、权限、升级路径和风险容忍度 |
| 情境与影响图 | 连接系统用途、相关方、依赖和可能后果 |
| 风险登记册 | 保存风险来源、证据、负责人、措施和剩余风险 |
| 测量计划 | 把可信特征改写成具体测试、指标和定性研究 |
| 处置决定 | 记录接受、缓解、转移或避免及其理由 |
| Profile | 为组织、业务线或具体用例选择适用结果与行动 |

工件之间需要能互相追溯。需求中写出的高后果失败，应在评测集里出现，在发布门槛中有判断，在监控与事件响应中有负责人。某份表格独立存在，无法说明风险已经被处理。

## 这份材料要求团队公开哪些取舍

| 选择 | 可能获得的价值 | 同时承担的代价 |
| --- | --- | --- |
| 统一治理 | 形成共同底线 | 可能忽略用例差异 |
| 广泛测量 | 增加可见性 | 成本高且指标会冲突 |
| 第三方能力 | 缩短交付 | 证据和控制力下降 |
| 发布后学习 | 获得真实反馈 | 必须先限制不可逆伤害 |

取舍不能被压成一个平均总分。严重但低频的伤害、特定群体承担的错误和不可逆行动，需要单独设置边界。产品评审的输出应包含采用方案、替代方案、支持证据、未知问题和复评条件。

## 与其他资料配合时的位置

这份材料负责提供一类主要视角。人机交互资料帮助理解用户如何形成期待和控制系统，机器学习系统资料解释数据、模型与基础设施的约束，风险框架负责角色、证据和持续治理，行业文件补充具体后果与专业责任。它们有交集，却不能互相替代。

AI RMF 是自愿、风险导向的通用框架，不是认证清单，也不会替团队设定指标阈值。不同地区和行业还需叠加适用法律、标准与专业责任。

## 治理的基本单位是可追溯决定

风险框架常被误用成问题清单。真正治理需要把系统情境、风险判断、证据、处置、负责人和复评条件连成一条记录。系统为什么存在，谁会受到影响，错误通过什么行动造成后果，当前证据覆盖哪些群体和环境，组织接受了多少剩余风险，都应能够从最终决定追溯。

风险登记册中的一行至少包含风险事件、触发条件、受影响对象、严重度与可恢复性、现有控制、支持证据、剩余缺口和所有者。写“模型可能产生偏见”无法指导行动；写明“夜班环境的低照度图像使某类缺陷漏检，并导致人工抽检减少”，才可能安排数据补充、分群测试、界面提示和人工保底。

测量不应追求单一总分。准确、公平、隐私、安全、透明与稳健可能相互制约，且证据强度不同。团队需要同时保留定量测试、用户研究、专家评审、供应商材料和运行事件，标明样本、版本、环境与不确定性。没有证据的“已满足”应改成假设或待办，外部认证也不能替代本地用途验证。

治理要随变化重开。用途扩大、数据来源变化、模型更新、工具权限增加、法律环境改变或出现事故，都可能使旧判断失效。复评触发器和停止条件应在上线前确定。遇到不可逆且证据不足的风险，合理动作可能是限制范围、增加人工审核或暂缓发布，而不只是继续优化指标。

## 用一次反向检查识别虚假的完成

从最终上线决定向前追踪。这个决定引用了哪些测试和用户证据，证据对应哪个系统版本和使用场景，测试覆盖了哪些已知失败，失败又来自需求中的哪项风险。任何一处断开，都说明团队拥有文档却没有形成证据链。再从事故或用户投诉向后追踪，确认它能否进入负责人、修复、回归测试和下一轮产品决定。

学习这类材料的完成标准，也应采用相同方法。能背出框架名称只是识别；能为一个真实功能建立工件并解释取舍属于应用；更换人群、权限、模型或后果以后，能够重新判断哪些结论失效，才算形成可迁移能力。

## 怎样读材料中的证据与建议

先区分四种内容。原则说明希望保护的价值，过程说明团队应完成的活动，技术证据描述系统在特定条件下的表现，治理证据说明责任和控制确实存在。原则相同，不代表实施动作相同；完成了过程，也不代表结果达标。阅读时可在段落旁标出它属于哪一层，避免把倡议性语言误当成已经验证的产品结论。

再检查证据适用范围。测试使用了什么数据和版本，参与研究的是哪类用户，运行环境与目标市场是否一致，结论观察了多长时间。官方机构或知名公司可以提高来源可信度，不能自动解决本地适用性。引用材料时应写清它支持哪项判断，又不能推出什么。

最后把建议改写成可以失败的检查。与其写“确保透明”，不如检查用户能否说出系统使用了哪些信息、是否知道输出会触发什么行动、发现错误后能否纠正。与其写“加强监控”，不如规定监控对象、窗口、阈值、负责人和处置。只有可能被证据否定的要求，才真正进入产品验收。

完成评审后应保留两份短清单。一份记录当前已经有证据支持的结论，注明版本、场景和日期；另一份记录仍未知或只能依赖假设的部分，注明补证方法和复评时点。把未知明确留下，比用完整表格制造确定感更专业。上线只是证据来源发生变化的节点，真实使用结果会继续修正发布前判断。

下一次产品版本应先回看这两份清单，确认新增能力有没有越过原来的用途、数据和权限边界，并关闭已经取得证据的问题。

## 框架的边界

AI RMF 给出治理骨架，不提供每个风险的统一阈值，也不构成合规证明。组织仍要结合本地法律、行业标准和任务证据。

框架覆盖通用 AI。生成式 AI 的特有风险由 NIST AI 600-1 Profile 补充。具体实施动作可以继续查看 AI RMF Playbook。

## 读完以后应当能够回答

1. AI 风险为何依赖具体情境和受影响角色。
2. 多项可信特征怎样发生取舍。
3. Govern、Map、Measure、Manage 分别留下什么证据。
4. 外部模型供应商与部署方怎样分担责任。
5. Current Profile 和 Target Profile 如何形成路线图。
6. 哪些变化会触发重新评测或停止系统。
