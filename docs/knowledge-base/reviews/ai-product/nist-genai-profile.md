# NIST 生成式 AI 风险画像阅读综述

生成式 AI 把系统输出从有限标签扩展到开放文本、图像、音频和代码。输出空间扩大以后，错误形状、滥用方式和供应链依赖也随之增加。NIST AI 600-1 在 AI RMF 1.0 基础上建立生成式 AI Profile，集中处理生成式系统新增或加剧的风险。

[阅读 NIST 官方 PDF](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf){target="_blank" rel="noopener noreferrer"}

## Profile 怎样补充通用框架

通用 AI RMF 提供 Govern、Map、Measure、Manage 四项职能。生成式 Profile 保留这套结构，增加十二类风险，并把建议行动映射回各项职能。

Profile 适用于模型开发者、系统部署者和使用方。产品由外部模型 API 构成时，团队仍需管理提示、检索、工具、界面、日志和用户行动形成的系统风险。

## 十二类风险构成产品地图

NIST 列出的风险包括化生放核信息或能力、虚构内容、危险暴力或仇恨内容、数据隐私、环境影响、有害偏差或同质化、人机配置、信息完整性、信息安全、知识产权、淫秽贬损或虐待内容，以及价值链和组件集成。

这些风险可以按产品工作分成四组理解。

| 产品位置 | 主要风险 |
| --- | --- |
| 输出内容 | 虚构、危险内容、偏差、知识产权和虐待内容 |
| 用户与交互 | 过度拟人、错误依赖、操纵和能力误解 |
| 数据与系统 | 隐私、信息安全、供应链和组件集成 |
| 外部影响 | 信息完整性、环境成本和高危能力扩散 |

分类只是索引。同一事件可能跨越多类。模型虚构一个软件包并诱导用户安装，既涉及虚构，也涉及信息安全和人机配置。

## 虚构内容需要任务化评测

Confabulation 指系统以确定语气生成错误或虚假内容。产品不能用一项通用真实性分数覆盖所有场景。客服回复关心政策和账户事实，代码助手关心接口存在与运行结果，研究助手关心来源是否支持结论。

团队先建立任务事实源，再设计可核对样本。检索增强可以减少部分错误，也会带来错误检索、来源过期和引用错配。界面应让用户查看来源，并在高风险动作前增加确认。

拒答和降级属于产品能力。系统没有足够证据时，可以说明缺口、请求更多信息或转交人工。继续生成顺畅答案会把未知伪装成完成。

## 人机配置处理依赖关系

Human-AI Configuration 关注系统与人的安排。流畅语言和拟人化设计会让用户高估理解、意图和稳定性。团队要评测用户是否在正确时机核对、接受或拒绝建议。

人工在环不自动降低风险。审核者没有时间、信息或权力时，人工环节只是在流程图中存在。产品需要说明审核对象、可见证据、允许动作和升级路径。

Agent 能调用外部工具时，可逆性决定控制强度。搜索和草拟可以采用较低摩擦，发送、购买、删除和改变权限需要更强确认与审计。

## 数据隐私与信息安全相互影响

生成式系统可能记忆训练数据，也可能从提示、检索库和日志泄露信息。攻击者还可以使用提示注入改变工具行为，或利用模型生成攻击内容。

产品数据图应覆盖输入、上下文、检索、缓存、供应商和日志。每个位置记录敏感数据类型、用途、保存期限、访问权限和删除方式。默认把完整对话永久保存，会同时增加隐私和安全风险。

安全测试要覆盖直接提示、间接提示注入、工具权限、数据外传和越权操作。内容过滤无法替代权限隔离。

## 信息完整性超出单次答案

生成式 AI 降低了批量生产和定制内容的成本。风险可能发生在传播规模、来源伪装和群体影响。水印与内容凭证能提供部分来源信息，无法证明内容真实。

平台型产品需要追踪生成、编辑、发布和传播路径。高影响内容可设置速率限制、来源标记、滥用检测和人工升级。产品指标不能只看生成成功率，还要观察举报、纠正和重复传播。

## 价值链风险要求管理外部组件

一项生成式产品可能依赖基础模型、向量数据库、内容过滤、插件、数据提供者和云服务。任何组件更新都可能改变质量和风险。

团队需要软件与模型清单、版本记录、变更通知和退出方案。供应商报告能提供信息，不能替代本地评测。相同模型在不同系统提示、检索数据和工具权限下会表现不同。

## 四项职能怎样安排工作

Govern 建立政策、角色、供应链治理和事件响应。Map 描述用途、用户、内容路径和滥用场景。Measure 运行任务集、红队、隐私安全测试和人机研究。Manage 根据证据限制用途、改设计、加强监控或暂停。

一次发布评审可以留下五份关键材料。

- 生成式 AI 风险登记及受影响角色。
- 任务评测集、人工评分规则和切片结果。
- 数据与组件清单。
- 工具权限、确认点和降级路径。
- 监控、事故、回退和供应商变更流程。

## 风险之间的取舍

更严格拒答可以降低危险内容，也可能损害正常用户。更长日志有助于调查，同时增加隐私负担。更大的模型可能提高任务质量，也增加环境和成本影响。

Profile 要求团队记录这些取舍。平均产品收益不能自动抵消少数严重伤害。不可逆和高影响风险需要单独门槛。

## 十二类风险要落到生成链和价值链

企业知识助手使用外部模型、内部检索和插件工具。虚构内容可能来自模型，也可能来自过期文档；隐私泄露可能发生在提示、日志、向量库或供应商；有害内容过滤会与业务完整性冲突；插件权限又把错误回答升级为错误行动。风险画像要求团队沿数据、模型、检索、界面、工具和供应商逐层定位，而非只做一次红队。

这个场景的阅读方法，是先定位系统正在替谁完成什么任务，再识别输出会触发哪一步行动。模型指标只描述能力的一部分。用户理解、数据来源、组织责任、失败恢复和部署后的反馈共同决定产品是否可用。每个判断都应落到可以复查的产物，避免把原则停留在口号。

## 阅读后应当留下的产品工件

| 工件 | 至少包含的内容 |
| --- | --- |
| 生成式风险地图 | 把十二类风险映射到本地组件和用户任务 |
| 来源与价值链清单 | 记录模型、数据、工具、许可证和供应商变化 |
| 任务化评测集 | 按真实任务测试事实、拒答、安全、隐私和可用性 |
| 内容来源提示 | 让用户区分生成内容、检索证据和系统行动 |
| 权限与确认规则 | 限制工具调用范围并为高后果动作保留确认 |
| 事件响应方案 | 覆盖撤回内容、禁用能力、通知和证据保存 |

工件之间需要能互相追溯。需求中写出的高后果失败，应在评测集里出现，在发布门槛中有判断，在监控与事件响应中有负责人。某份表格独立存在，无法说明风险已经被处理。

## 这份材料要求团队公开哪些取舍

| 选择 | 可能获得的价值 | 同时承担的代价 |
| --- | --- | --- |
| 开放生成 | 覆盖更多需求 | 输出空间与风险面扩大 |
| 严格过滤 | 减少有害内容 | 可能损害合法用途和群体表达 |
| 长上下文 | 提供更多信息 | 增加泄露、污染和成本 |
| 工具自主性 | 缩短任务链 | 错误会直接改变外部状态 |

取舍不能被压成一个平均总分。严重但低频的伤害、特定群体承担的错误和不可逆行动，需要单独设置边界。产品评审的输出应包含采用方案、替代方案、支持证据、未知问题和复评条件。

## 与其他资料配合时的位置

这份材料负责提供一类主要视角。人机交互资料帮助理解用户如何形成期待和控制系统，机器学习系统资料解释数据、模型与基础设施的约束，风险框架负责角色、证据和持续治理，行业文件补充具体后果与专业责任。它们有交集，却不能互相替代。

Profile 是 AI RMF 的生成式补充，不是固定测试分数。风险分类会继续演进，具体威胁和控制必须随模型、用途与供应链变化更新。

## 治理的基本单位是可追溯决定

风险框架常被误用成问题清单。真正治理需要把系统情境、风险判断、证据、处置、负责人和复评条件连成一条记录。系统为什么存在，谁会受到影响，错误通过什么行动造成后果，当前证据覆盖哪些群体和环境，组织接受了多少剩余风险，都应能够从最终决定追溯。

风险登记册中的一行至少包含风险事件、触发条件、受影响对象、严重度与可恢复性、现有控制、支持证据、剩余缺口和所有者。写“模型可能产生偏见”无法指导行动；写明“夜班环境的低照度图像使某类缺陷漏检，并导致人工抽检减少”，才可能安排数据补充、分群测试、界面提示和人工保底。

测量不应追求单一总分。准确、公平、隐私、安全、透明与稳健可能相互制约，且证据强度不同。团队需要同时保留定量测试、用户研究、专家评审、供应商材料和运行事件，标明样本、版本、环境与不确定性。没有证据的“已满足”应改成假设或待办，外部认证也不能替代本地用途验证。

治理要随变化重开。用途扩大、数据来源变化、模型更新、工具权限增加、法律环境改变或出现事故，都可能使旧判断失效。复评触发器和停止条件应在上线前确定。遇到不可逆且证据不足的风险，合理动作可能是限制范围、增加人工审核或暂缓发布，而不只是继续优化指标。

## 用一次反向检查识别虚假的完成

从最终上线决定向前追踪。这个决定引用了哪些测试和用户证据，证据对应哪个系统版本和使用场景，测试覆盖了哪些已知失败，失败又来自需求中的哪项风险。任何一处断开，都说明团队拥有文档却没有形成证据链。再从事故或用户投诉向后追踪，确认它能否进入负责人、修复、回归测试和下一轮产品决定。

学习这类材料的完成标准，也应采用相同方法。能背出框架名称只是识别；能为一个真实功能建立工件并解释取舍属于应用；更换人群、权限、模型或后果以后，能够重新判断哪些结论失效，才算形成可迁移能力。

## 怎样读材料中的证据与建议

先区分四种内容。原则说明希望保护的价值，过程说明团队应完成的活动，技术证据描述系统在特定条件下的表现，治理证据说明责任和控制确实存在。原则相同，不代表实施动作相同；完成了过程，也不代表结果达标。阅读时可在段落旁标出它属于哪一层，避免把倡议性语言误当成已经验证的产品结论。

再检查证据适用范围。测试使用了什么数据和版本，参与研究的是哪类用户，运行环境与目标市场是否一致，结论观察了多长时间。官方机构或知名公司可以提高来源可信度，不能自动解决本地适用性。引用材料时应写清它支持哪项判断，又不能推出什么。

最后把建议改写成可以失败的检查。与其写“确保透明”，不如检查用户能否说出系统使用了哪些信息、是否知道输出会触发什么行动、发现错误后能否纠正。与其写“加强监控”，不如规定监控对象、窗口、阈值、负责人和处置。只有可能被证据否定的要求，才真正进入产品验收。

完成评审后应保留两份短清单。一份记录当前已经有证据支持的结论，注明版本、场景和日期；另一份记录仍未知或只能依赖假设的部分，注明补证方法和复评时点。把未知明确留下，比用完整表格制造确定感更专业。上线只是证据来源发生变化的节点，真实使用结果会继续修正发布前判断。

下一次产品版本应先回看这两份清单，确认新增能力有没有越过原来的用途、数据和权限边界，并关闭已经取得证据的问题。

## 内容边界

Profile 给出风险类型和建议行动，不提供产品级保证。各场景需要自己的任务集、阈值和责任人。标准发布于 2024 年，模型与攻击方法持续变化，团队应结合近期独立研究和本地事故更新。

它也不替代法律分析。版权、隐私、内容责任和行业监管因地区与用途而异。

## 读完以后应当能够回答

1. 十二类风险分别发生在产品链路的哪些位置。
2. 虚构内容为何需要按任务建立事实源与评测。
3. 人工审核在什么条件下才真正有效。
4. 提示、检索、工具和日志怎样共同形成安全边界。
5. 外部模型更新为何必须触发本地重测。
6. 四项 RMF 职能如何形成生成式 AI 发布证据。
