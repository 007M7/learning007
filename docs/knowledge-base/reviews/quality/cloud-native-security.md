这一部分先改变观察对象。短生命周期实例、API 控制面和供应链扩大身份与自动化的重要性。因此，读者不能只记住“云原生改变资产和边界”这个名称，还要问它指向哪个工件、哪种状态和哪类失败。

### 开发阶段控制来源与缺陷

理解“开发阶段控制来源与缺陷”，可以从一次失败倒推。代码、依赖、构建配置和秘密需要评审与保护。若这一关系没有被表达，团队通常会在结果异常后才发现定义缺口。

## 沿一次安全评估组织证据

把一个从代码提交到多集群运行的云原生产品作为贯穿案例。团队首先依据“云原生改变资产和边界”确定问题、参与者和失败后果，然后用“开发阶段控制来源与缺陷”描述需要检查的对象。进入实施后，“分发阶段维护制品完整性”与“部署阶段执行声明与策略”分别约束工作方法和证据。最后再用“身份成为主要控制平面”与“组织责任需要产品化平台支持”判断结果能否进入下一阶段。

这个串联防止“分发阶段维护制品完整性”只在局部成立。即使某项检查执行很快，输入对象不完整时仍会产生不完整结论。即使“部署阶段执行声明与策略”符合形式要求，缺少运行反馈和处置责任时也无法支撑长期质量。评审应沿路径来回检查，确认每一步有来源、有负责人、有输出，并且输出被下一步使用。

还可以给一个从代码提交到多集群运行的云原生产品加入一次异常变化，专门挑战“身份成为主要控制平面”。变化可以来自依赖版本、流量、权限、外部超时或证据缺失。团队需要指出哪项判断失效、应该回到哪个阶段、哪些操作必须停止。变化后若能重新建立“组织责任需要产品化平台支持”所需证据，才能说明这条知识链已经掌握。
