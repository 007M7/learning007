## 超时以后，计划才开始接受检验

退款单 1042 当前有三条已确认事实。订单已经付款，资金尚未退回，用户声称没有收到货。承运商主接口第一次查询超时，客服系统里有一条三天前的缓存，内容是“正在派送”。

模型预先列出的计划很顺。

```text
查订单 → 查物流 → 判断资格 → 发起退款 → 告知用户
```

第二步没有给出答案，这条计划已经失去一个前置条件。若系统仍然把“查物流”标成完成，后面的判断会站在空处。若模型每次看到超时都整张重写计划，它可能在“再试一次”和“直接转人工”之间来回摆动。若它把旧缓存当最新事实，又会得到另一条错误路径。

规划要处理的对象因此落到一组很具体的问题。当前已知什么，下一步准备改变什么，怎样看出动作产生了预期结果，失败以后哪些动作还合法，剩余预算允许探索多久。计划文本只有进入这条控制关系，才会帮助运行。

可以把目标写成带成本的有限时域选择。

$$
\pi^*=\arg\max_\pi\;\mathbb{E}\left[
\sum_{t=0}^{T} \gamma^t r_t
-\lambda_c C_t
-\lambda_r R_t
\right]
$$

$r_t$ 表示得到可验证进展或完成任务的收益，$C_t$ 包括模型、工具和时间成本，$R_t$ 表示外部副作用与政策风险。$T$ 由最大步骤和截止时间共同限制。这个式子没有替团队决定每一项权重。它只把一个常被遗漏的事实写出来，搜索次数增加时，费用和风险也一起增加。

## ReAct 给每一步留出观察位置

ReAct 在 2022 年提出把 reasoning 与 action 交替，让模型在行动后读取外部信息，再更新后续判断。它是本章的基础材料，发表时间早于近三年窗口，因此只承担起点，不承担前沿结论。

退款任务可以用一条简化的 ReAct 轨迹表示。

```text
当前事实    订单已付款，资金未退，物流未知
行动理由    退款资格依赖最新物流状态
动作        read_carrier(order_1042)
观察        timeout，request_id c-77，未确认是否执行成功
下一判断    先读取查询任务状态，不能把超时解释成未签收
```

“行动理由”只保存足以审计决定的短理由、证据引用和未满足条件。生产日志没有必要记录模型完整的隐式思维过程，更不能把长篇自述当作证据。下一步由 `timeout`、请求编号和环境里仍然未知的物流状态共同决定。

ReAct 解决了单次生成看不见新事实的问题。它没有自动解决观察错误、权限、重复副作用和终止。模型也可能看到新观察后坚持旧假设，或者把工具报错编成业务结论。运行层仍要检查动作是否合法，verifier 仍要读取环境状态。

对线性 ReAct 最小实现，可以只保留下面这条循环。

```text
读取当前状态版本
        ↓
提出一个获准动作和预期差分
        ↓
权限与预算门禁
        ↓
执行一次动作
        ↓
读取新状态和证据
        ↓
验收进展、恢复或终止
```

每轮只执行一个有明确预期的动作。模型一次生成五个工具调用，后面的动作通常建立在尚未出现的观察上，也让执行层很难在中途拦截。

## 一张清单怎样变成可执行计划

原来的五步清单缺少状态。团队把第二步改成一个计划节点。

```yaml
id: carrier-evidence
goal: 获得退款判断所需的最新物流证据
preconditions:
  - order_status == paid
  - payment_status == not_refunded
allowed_actions:
  - read_query_status
  - read_carrier_backup
expected_diff:
  - confirmed_facts 增加一条带时间戳的物流事实
fallback:
  - request_human_review
verifier:
  - evidence.source in approved_sources
  - evidence.observed_at > cached_record.observed_at
status: blocked
```

节点拥有 `queued`、`running`、`passed`、`blocked`、`failed` 和 `skipped` 等状态。当前物流主接口超时，节点应当是 `blocked`，不能因为工具已经被调用就写成 `passed`。等待任务状态、改查备用来源和转人工都属于后续候选；直接退款没有出现在动作集合里。

计划还需要版本。`plan_version=3` 是基于状态版本 7 产生的。若人工在此期间补了一条物流结论，环境已经到版本 8，执行层要先重新读取状态，再决定旧动作是否仍然适用。这个检查能挡住一类常见并发错误，Agent 手里的计划正确，却针对一个已经改变的世界。

分解也要有停止尺度。子目标小到每一步都要模型选择，会浪费调用；子目标大到“处理退款”，又无法验收。合适的节点应当对应一次可观察状态变化，例如“获得一条获准来源的最新物流事实”或“创建且仅创建一张人工复核单”。

## 工具回执与环境反馈不是同一件事

承运商接口返回 HTTP 200，只说明服务接受或处理了请求。响应体可能来自缓存，后台任务可能尚未完成，订单状态也可能在调用后被另一个流程改写。反过来，一次网络超时也不能证明服务端没有执行。

反馈可以按证据强度分层。

| 反馈 | 能支持的判断 | 仍然缺少什么 |
|---|---|---|
| 模型自评“已完成” | 模型准备停止 | 所有外部事实 |
| 工具返回成功码 | 一次协议交互可能成功 | 业务目标状态与幂等结果 |
| 带版本的读取结果 | 某时刻观察到一组字段 | 观察之后是否又变化 |
| 环境状态差分 | 动作前后哪些字段改变 | 未被差分覆盖的质量要求 |
| 独立 verifier 断言 | 指定目标与禁行项是否满足 | 断言未建模的真实风险 |

退款系统采用两次读取。动作前记录状态版本，动作后用新读取确认变化。对只读查询，预期差分发生在本次运行的证据集合；对创建人工单，预期差分发生在工单数据库。模型摘要只能引用这些结果。

反馈本身也会错。旧缓存带有 `observed_at`，接口数据带有 `received_at`，运行层还要记录 `read_at`。三种时间混在一起，Agent 可能把刚刚读取的旧事实当成刚刚发生的新事实。若来源互相冲突，计划节点保持 `blocked`，直到得到优先级更高的来源或人工裁定。

2026 年的 AgentJudgeBench 进一步提醒了验收风险。该研究在 3,808 个工具调用 DAG 实例上比较多个生成器和 judge，发现任务变难后，judge 与程序参考的一致程度下降；结构化 rubric 能改善部分组合，却没有普遍消除差异。它是一篇 2026 年 8 月公开的预印本，虽标注为 EMNLP 2026 接收，仍需要独立复现。当前设计因此优先用程序断言核验资金、工单和禁行项，LLM judge 只处理确定规则覆盖不了的质量判断。

### 一条过时观察怎样退出计划

假设人工客服在 Agent 运行期间把订单标成“已进入争议处理”。Agent 手里仍然保存上一分钟的 `state_version=7`，旧计划准备查询备用物流，再创建普通退款复核单。工具执行层读取到当前版本 8，前置条件已经变化。

此时不能把新字段简单追加到旧摘要。运行层先把依赖版本 7 的两个节点标成 stale，取消尚未执行的动作，再读取争议流程允许的工具和停止规则。普通退款复核单可能已经不合法，新的计划只允许查询争议案件编号或交给对应人员。计划改变的依据是一条带版本的环境差分，trace 可以说明旧节点为何失效。

如果旧动作已经发出，处理方式取决于副作用。只读查询可以接受返回，再把结果标为旧分支证据；尚未提交的写动作直接取消；服务端状态未知的写动作先按幂等键查询。这个例子也给“重规划”划出边界。新观察改变了前置条件才需要改计划，模型只是想到另一种说法，不构成重规划理由。

观察版本还要进入 verifier。最终断言除了检查工单存在，还应检查它属于当前争议流程、引用版本 8 的订单，并且旧退款队列没有新增记录。系统若只验收“创建了一张单”，很可能把过时计划留下的副作用算成成功。

截至 2026 年 9 月 3 日，一项新的 Web Agent 预印本把监控目标放在可观察轨迹上。Monitoring Web Agents Without Internal Signals 使用跨步骤行为、反馈和预期状态变化来判断执行是否开始偏离，并标注第一个没有被后续纠正的关键错误。它支持本章记录状态差分和第一处失真的做法，也说明拿不到模型内部概率时仍可建立外部监控。证据来自 WebArena-Lite、Online Mind2Web 与五个 backbone，跨网站结果仍需复现，更不能把风险预测器当成动作授权器。

## 失败以后先辨认发生了什么

“重试一次”常被当作通用恢复。它只适合很窄的情形。团队先把失败分成几类，随后选择动作。

| 现象 | 可能状态 | 第一动作 | 禁止动作 |
|---|---|---|---|
| 只读查询明确限流 | 环境未改变 | 按 `retry_after` 等待后重试 | 高频立即重放 |
| 写请求超时 | 服务端可能已执行 | 用幂等键查询最终状态 | 直接再次提交 |
| 观察版本落后 | 世界已经变化 | 重新读取并废弃旧计划节点 | 继续执行旧动作 |
| 前置条件不成立 | 当前路径失效 | 标记节点 blocked，重规划 | 把失败步骤强行标成完成 |
| 权限或政策拒绝 | 动作本来就不合法 | 记录拒绝并转人工或结束 | 改写提示绕过门禁 |
| 两次没有新事实 | 轨迹陷入无进展 | 选择备用来源或停止 | 只换措辞继续思考 |

恢复动作也有差别。retry 重放同一个动作；replan 根据新状态换后续路径；backtrack 回到先前可恢复快照；compensation 用一个新动作抵消已经发生的副作用；escalation 把剩余决定交给人。对外部支付来说，删除一句计划无法撤回退款。真实回退依赖事务、快照或补偿接口。

现在让退款 Agent 处理超时。它先凭请求编号读取承运商任务状态，发现查询根本没有完成，因此可以在退避后重试一次。第二次仍然超时，预算规则关闭主接口分支。Agent 改查获准的备用物流来源，得到一条当天的“已送达前台”记录，但用户说所在楼没有前台。证据发生冲突，系统创建人工复核单并停止，资金状态保持不变。

这条轨迹没有自动退款，依然是一条成功恢复。它识别了超时的不确定性，限制重试，换了来源，也在证据无法合并时进入安全终止。verifier 可以逐项检查这些结果。

## 反思只有绑定失败证据才会留下

模型看见两次超时后，很容易写下“承运商接口不可用”。这个总结说得通，证据却只覆盖一次运行和一个订单。把它存成长期经验，下一张退款单可能直接跳过已经恢复的主接口。

可用的反思需要回答五件事。

```text
触发证据    哪个 verifier 或环境结果判定失败
适用范围    哪个工具版本、任务类型和时间窗口
建议变化    下一次具体改哪个动作或前置条件
反证条件    看见什么就撤销这条经验
有效期限    何时重新验证或自动过期
```

当前反思可以写成“承运商主接口在本次运行连续两次超时，订单 1042 改查备用来源；下一次运行仍先按健康检查决定是否使用主接口”。它没有把局部故障升级成永久事实。

2024 年的 Devil's Advocate 把反思放到行动前、行动后和整轮结束三个位置。论文在 WebArena 的特定零样本设置中报告 23.5% 成功率，较所比较的零样本方法提高 3.5 个百分点，并报告试验与计划修订数减少。这个结果支持“在动作前写风险和备用路径值得测试”，不能证明每一步都反思会普遍增益。高频反思增加 token，同一个模型同时生成和评价时还会共享错误。

行动前反思因此只用在风险较高或恢复代价较大的节点。它输出 `precondition`、`expected_diff`、`failure_signal` 和 `fallback`，动作后由真实反馈核对。普通只读查询不必每次写一篇自我检讨。

## 搜索值得购买时，分支必须隔离

线性 ReAct 一次保留一条路径。遇到多个都有可能的证据来源时，系统可以同时保留候选分支。LATS 在 2023 年把语言模型候选、价值估计、反思与环境反馈接入 Monte Carlo Tree Search，并在多个任务域报告增益。它让 test-time search 成为可复用 scaffold，也把新的问题带进系统，价值估计是否可靠，分支如何隔离，额外预算是否值得。

一种常见选择规则写成下面这样。

$$
a^*=\arg\max_a\left[
Q(s,a)+c\sqrt{\frac{\ln N(s)}{N(s,a)+\epsilon}}
\right]
$$

$Q(s,a)$ 保存已观察到的平均价值，$N(s,a)$ 是该分支被访问的次数，第二项给访问较少的动作探索机会。$c$ 增大时，系统会花更多预算探路。若 $Q$ 主要来自同一个模型的自评，这个公式会很稳定地选择高置信错误。环境分数、测试或独立规则应当尽早进入节点价值。

退款案例只允许搜索可逆、只读的证据路径。A 分支查询承运商任务状态，B 分支查询备用物流，另一路去看客服历史。各分支持有环境快照和调用预算，不能共享尚未确认的模型摘要。创建工单、发消息和退款都不进入自由探索，它们需要汇合证据以后再过门禁。

树宽和深度一起受限。宽度为 3、深度为 2，并不保证只发生 6 次调用，因为每个节点可能包含生成、执行和评价。预算账本按真实模型调用、工具调用、墙上时间和副作用计数。搜索没有在上限内增加已确认事实，就退回线性路径或人工处理。

分支评分也要避免把“接近答案”写成含糊直觉。当前案例可以先按三项可观测结果排序。新分支是否增加了带来源的事实，是否排除了一个退款资格假设，剩余工具预算是否足以走到 verifier。涉及风险的分支另设硬门禁，不允许用较高预期收益抵消未审批副作用。不同量纲若被压成一个总分，权重变化必须进入实验记录。

搜索结束后保存落选分支的终止原因。它们可能因证据重复、前置条件失效、预算不足或权限拒绝退出。只保存获胜轨迹会让团队高估规划效率，也看不见系统为一次成功支付了多少失败尝试。下一次调参时，落选轨迹还是发现价值函数偏差的重要材料。

## 未知环境先用低风险动作建立假设

计划经常默认团队已经知道环境怎样转移。现实里，新接口、网页和软件版本会改变。Agent 需要通过行动了解规则，这可以称为建立世界模型。这里的“模型”是对状态转移的可检验假设，不是一段关于世界的漂亮总结。

2026 年的 Agentic Automata Learning 提供了一个受控例子。隐藏世界是一台确定有限自动机，Agent 可以询问某个字符串是否被接受，也可以提交候选自动机接受等价检查。每个假设都有精确反例，经典自动机学习算法又提供强基线。论文发现语言模型 Agent 能完成部分交互发现，难度增大后在查询规划、证据整合和假设构造上明显变脆。

ARC-AGI-3 在 2026 年把这种问题放进未知的回合制交互环境。Agent 需要探索、推断目标与动力学，再规划动作。技术报告在其协议下给出人类与当时前沿系统的明显差距。游戏环境隔离了语言知识，也与退款系统有很大距离，不能把分数直接外推为一般业务能力。

两份材料给当前系统的共同启发很有限，也很实用。新环境先开放只读查询或可复位沙箱，每个动作写预期，观察到反例就更新假设。高权限动作等到转移规则和 verifier 足够稳定以后再开放。探索阶段也受政策约束，未知不能成为扩大权限的理由。

## 把安全和评测放进每一轮

后面的专章会系统讲 Agent evaluation 与安全治理。本章不要求那些专章先完成，最低控制已经可以写进循环。

动作前，policy gate 检查工具是否在 allowlist、参数是否越界、当前状态是否满足前置条件。外部网页和工具文本只作为观察，不能修改权限。不可逆动作要求人工审批或确定工作流提交。

动作后，verifier 读取环境状态差分，同时检查期望变化和禁止变化。trace 保存版本、来源与预算。连续无进展、重复状态、权限拒绝和预算耗尽都会终止运行。

评测时把任务完成与安全合规分开。一条退款成功但绕过审批的轨迹不能算通过，一条证据冲突后正确转人工的轨迹也不应算失败。这个双重门禁贯穿计划、恢复和搜索，后续章节只会把攻击面、统计方法和治理责任讲得更细。

## 同预算比较四种规划方式

准备二十四条可复位任务。每条任务都从同一初始状态开始，其中加入接口超时、旧缓存、写请求结果不明、证据冲突、重复申请和外部注入。所有方案使用同一模型、温度、工具、权限和最多六次模型调用、十次工具调用。

先用人工脚本逐条验证初始状态、故障注入和最终断言。某条任务连固定流程都因环境损坏而失败，就标为基础设施错误，不计入规划器失败，也不悄悄从报告中删除。

四个方案分别采用固定工作流、线性 ReAct、带计划节点与恢复规则的 ReAct，以及宽度 3、深度 2 的受限搜索。每项运行至少三个种子。搜索用完预算后不能额外请求一次“最终整理”，否则比较已经失衡。

报告至少包含安全成功率、正确拒绝率、错误副作用率、平均工具调用、墙上时间、无进展循环、恢复成功和人工接管。对每种失败保留一条完整 trace。再做两项消融，一次移除 `expected_diff`，一次把程序 verifier 换成模型自评。若搜索只在自评条件下显得更好，结论应当指向 evaluator 偏差，不能写成规划能力提升。

采用条件提前写好。带恢复的 ReAct 在安全成功上稳定超过固定工作流，并且额外费用与延迟处于预算内，才保留自治路径。树搜索还要相对线性方案提供可重复增益。任何方案出现未审批退款，先关闭写权限并修复门禁，停止比较平均分。

## 三层练习

### 跟做

把本章的超时轨迹写成六个计划节点，每个节点包含前置条件、获准动作、预期差分、失败信号、fallback 和 verifier。手工注入一次主接口超时，产物是一份版本化计划和一条转人工 trace。验证资金状态没有改变，人工单只创建一次，旧缓存没有被标成最新事实。本段使用 2 个标准回合，反馈来自断言输出和同伴逐步复述。

### 变式

把只读超时改成“退款提交超时，服务端可能已经执行”。设计查询、重试和补偿顺序。产物是一张恢复状态机、一个幂等键规则和两条测试。第一条模拟服务端已经退款，第二条模拟请求未到达。两种情况下都不得出现重复退款。本段使用 1 个标准回合，测试失败时先检查状态读取，不能靠增加模型轮数绕过。

### 迁移

选择一个可复位的网页或代码任务，设置一条过时观察和一条不可信指令。实现固定工作流、线性 ReAct、带恢复 ReAct 三个版本；环境允许时再加受限搜索。产物包括任务集、预算表、原始 trace、状态断言和采用 ADR。至少重复三次，并写出一条应当拒绝或交人的路径。若没有程序 verifier，先把成功缩成可以人工逐项核对的 rubric，不开放真实副作用。本段连同采用交接使用 3 个标准回合。

## 本章小结

- ReAct 给行动之间留出观察位置，可靠运行仍依赖版本化状态、权限和外部验收。
- 可执行计划的节点带前置条件、预期差分、失败信号、fallback 与状态，清单文字不能代替这些关系。
- retry、replan、backtrack、compensation 和 escalation 处理不同失败，写请求结果不明时先查真实状态。
- 反思只保存由失败证据支持、能够撤销且有适用范围的经验。
- test-time search 适合反馈可靠、动作可逆且候选路径有价值的任务，预算和分支隔离属于机制本身。
- 安全门禁与评测断言从第一轮就生效，后续专章会加深方法，不会替当前系统补上缺失的底线。
