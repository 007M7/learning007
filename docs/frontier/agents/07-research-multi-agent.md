本章允许从第二阶段直接进入。硬前置是 AGF01—12 留下的系统边界、预算与停止合同、类型化只读工具，以及有来源、作用域、有效期和删除路径的记忆边界。研究分支只能读取获准材料、写本地证据账本和生成待审报告；它没有改政策、发退款、联系外部主体或提交业务对象的权限。Computer use 与 Coding（AGF13—18）是有相关任务时的推荐前置，不是 Deep Research 的强制门槛。缺少只读权限隔离或来源可追溯时，先回到第三、四章，不靠更多搜索掩盖边界缺口。

本章 10 个标准回合分为：问题树、来源与账本机制 3 回合，固定流程跟做 2 回合，证据变化与并行消融 2 回合，陌生研究迁移及 `research_agent` 交接 3 回合。检索服务等待属于墙钟；查询设计、来源核验、冲突处理和账本审阅都计入既定回合。

## 一份退款改策建议先卡在来源上

第三阶段留下了 `RF-217` 的完整教学变更链：候选补丁在可复位夹具中通过独立合并审阅，尚未部署，也不能据此声称生产个案已经结案。接下来的研究案例从另一份受控快照开始。队列里出现 31 条“物流显示已交付、用户称未收到”的申请，运营希望退款 Agent 研究是否应该临时放宽自动退款条件。

这已经超出单个工单。系统需要核对承运方当前规则、商户合同的专属条款、近八周内部异常率和替代解释。最终建议会影响一批订单，研究者却没有改规则或发放退款的权限。这里沿用的“澄运物流”、订单数和文档编号都是教学夹具，不对应真实企业。

第一版 Agent 在二十分钟后交出六页报告。它引用了承运方帮助页、两篇行业文章和三个子 Agent 的摘要，结论写着“新赔付规则已经覆盖平台商户，可以放宽自动退款”。审阅者追问合同附件编号，报告没有回答。三个摘要追到最后还都来自同一篇承运方新闻稿。内部 31 条申请也没有分母，既可能是异常率上升，也可能只是订单量同步增加。

这次失败先暴露三个洞。待决策问题没有拆到可验证粒度，引用没有绑定适用范围，报告数量掩盖了根来源重复。此时增加搜索轮次只会让长文更长。合理动作是冻结改策建议，保存现有检索轨迹，并把“商户合同适用性”和“内部异常率分母”标成阻断项。

研究 Agent 的终止状态因此不止“完成报告”。它还可以返回“证据不足，拒绝建议”“来源冲突，交给责任人裁决”或“预算耗尽，保留未知量”。这些状态沿用第一阶段的终止与预算纪律，也继承工具服务与证据账本的外部裁决。完成过第三阶段的人还可以复用 GUI 或仓库环境的动作后验证，但那不是本章成立的前提。研究输出属于决策输入，业务授权仍由原责任系统持有。

## 先把决定拆成能被证据回答的主张

运营原问题是“要不要放宽退款”。直接搜索这句话会把政策事实、内部统计和价值选择混在一起。先写决策合同，再画问题树。

| 决策合同字段 | 本案例填写 | 审阅作用 |
|---|---|---|
| 决策对象 | 国内普通商品的未收货申请 | 排除跨境、冷链和高价值商品 |
| 候选改变 | 是否调整自动退款的证据门槛 | 不包含提高金额上限 |
| 生效窗口 | 未来十四天的临时策略 | 不把短期异常外推成长期政策 |
| 必须回答 | 外部规则、合同适用性、内部基率、替代原因 | 形成检索承诺 |
| 禁止动作 | 改规则、发退款、联系承运方承诺赔付 | 研究权限与业务权限分开 |
| 截止条件 | 关键主张全有当前一手证据，或明确拒绝 | 防止无休止搜索 |

接着把一个模糊问题拆成八条原子主张。原子意味着每条只有一个谓词，能被一段具体材料支持或挑战。

1. 承运方公共赔付规则在当前日期已经生效。
2. 规则包含“显示已交付但未收到”这一类事件。
3. 平台商户合同采纳公共规则，且没有专属附件覆盖它。
4. 近八周相关申请率高于此前基线。
5. 增量集中在某区域或服务等级。
6. 扫描延迟、仓库出库错误等替代原因不足以解释增量。
7. 现有人工复核的误拒与误放成本可估计。
8. 临时策略具备停止条件、责任人和回退路径。

前两条可从承运方的一手页面开始，第三条只能由有效合同及附件回答。第四到第七条依赖内部数据，最后一条属于运营与风控共同给出的约束。搜索 Agent 可以找证据，不能替责任人决定可接受损失。

问题分解还有一个容易忽略的测试。删除某条主张后，最终决定会不会变化。若不会，它很可能只是背景知识；若会，就要给它证据等级、负责人和缺失时的动作。这样形成的问题树服务于决策，不服务于堆材料。

[GAIA](https://arxiv.org/abs/2311.12983) 用 466 个问题检验浏览、工具与推理的组合能力，[BrowseComp](https://arxiv.org/abs/2504.12516) 则把重点放在难找且相互缠绕的网页事实。它们解释了为什么多跳研究很难，却不能替本案例定义合同适用性、报告完整度或业务门禁。基准题的唯一答案结构也不等于开放决策的证据结构。

## 单一工作流先跑出可比较的底线

团队很容易在第一次长报告失败后增加子 Agent。先忍住。没有基线就无法判断提升来自结构，还是来自更多 token、工具调用和时间。

本案例先跑一个固定流程。它不让模型自由决定下一步，只按顺序读取已知公共规则页、合同目录、内部聚合表和事故分类表。每类最多一次查询，缺文件就登记缺口。这个流程的价值不在“聪明”，而在可重放。它能发现合同附件根本没有进入材料包，也能算出 31 条申请对应的总订单分母。

第二个基线由一个 Agent 执行完整循环，但预算固定为四十分钟、十二次检索和六万输入输出 token。它可以改写查询和追随引用，仍必须使用同一问题树、相同材料权限和同一个评分器。两次运行都保存查询、抓取时间、页面版本、工具错误与停止理由。

比较表至少分开四件事。

| 维度 | 固定流程 | 单 Agent | 为什么要分开看 |
|---|---|---|---|
| 关键主张支持数 | 5/8 | 6/8 | 观察探索带来的覆盖增量 |
| 独立根来源 | 4 | 5 | 排除转载制造的虚假数量 |
| 错配引用 | 0 | 1 | 覆盖提高可能伴随准确性下降 |
| 总 token | 18k | 60k | 计算投入进入结论 |
| 墙钟时间 | 13 分钟 | 39 分钟 | 并发前先知道串行成本 |

表中的数值是教学夹具结果。它表达一种实验纪律，不宣称某个模型会得到相同分数。若固定流程已经覆盖全部关键主张，Multi-agent 没有天然价值。若单 Agent 被上下文长度卡住，也要先尝试压缩证据记录和移除无关材料。

再保留一个人工最小参照。审阅者只读合同目录和内部聚合表，用十五分钟标出阻断项，不写完整报告。这个参照若比 Agent 更快发现附件缺失，团队应把原因写进误差分类。也许工具排序错了，也许问题树没有把关键主张置顶。人工参照无法规模化执行，仍能揭示自动流程是否把简单检查包装成昂贵搜索。后续版本必须与它比较阻断发现率，不能只比报告长度。

OpenAI 的 [Deep Research System Card](https://openai.com/index/deep-research-system-card/) 描述了多步浏览、文件读取、代码执行与根据发现调整路径的系统，也同时记录网页注入、隐私和幻觉风险。它支持“深度研究是循环工作流”的认识，不能证明任意高风险业务都可无人监督。产品方系统卡还是自述材料，不能承担独立审计的角色。

## 账本让每句话留下出处和反证

单 Agent 基线里那条错配引用有一个典型形态。报告写“专属合同已采纳公共赔付规则”，紧邻链接却只说明公共规则的生效日期。链接真实，主张仍未被支持。

解决它需要一张逐条更新的主张证据账本，也就是 `claim-evidence ledger`。账本从第一次搜索开始更新；写完报告再补参考文献会丢失被拒证据与查询路径。搜索结果一进入系统，就先登记到对应主张。

```yaml
claim_id: C3
claim: 平台商户合同采纳当前公共赔付规则
decision_impact: 缺失时不得建议改自动退款条件
evidence:
  - evidence_id: E7
    root_id: R-contract-master-2026
    source_type: executed_contract
    version: 2026-04-01
    locator: section 12.2
    relation: partial_support
    applicability: 主合同提及公共规则，但附件清单缺页
counterevidence:
  - evidence_id: E9
    root_id: R-public-policy-2026-08
    relation: no_contract_scope
status: blocked
owner: contract-owner
next_action: 索取生效附件并核对签署主体
```

这张记录迫使系统区分“页面说了什么”和“页面是否管这批订单”。`relation` 至少允许支持、挑战、部分支持和无关四种值。`applicability` 记录地区、时间、商品、签署主体和账户层级。`locator` 指到页码、条款或表格单元格，审阅者无需重跑整次搜索。

内部统计也要成为证据。记录查询语句版本、时间窗、分母定义、去重方法和生成时间。若 31 个事件来自重复工单，或分母混入不适用订单，图表再精美也不能支持基率上升。原始个人信息不进入研究报告，只保存可授权访问的聚合与查询摘要。

账本还要保存反证搜索。对 C4“申请率上升”，主动检索承运扫描延迟、营销活动导致的订单峰值和分类器规则变更。若替代原因成立，就降低归因强度，不用“找到了支持材料”当作停止条件。

2026 年 9 月的新预印本 [ClaimReceipt](https://arxiv.org/abs/2609.01992) 区分证据充分性与覆盖，并提出可追踪的声明凭据和实验清单。这里借用的判断很窄。研究交付需要让遗漏可见。它的作者实验与规范还很新，不能把某套字段当作通用行业标准，也不能替代合同、隐私和权限审查。

## 搜到多少要按承诺范围计算

运营看到二十个链接时，很难判断还缺什么。问题树已经承诺八条主张，其中 C3 与 C4 会直接改变决策。若六条有合格支持、两条为空，研究团队可以说“完成了六条”，不能说“资料已经很丰富”。

这时才引入 `search coverage`。最简单的覆盖率是合格支持主张数除以承诺主张总数。

$$
coverage=\frac{|\{c\in C\mid supported(c)=1\}|}{|C|}
$$

`supported` 不能只检查是否有 URL。证据还要通过来源真实性、时效、适用性和紧邻主张的蕴含检查。八条中六条通过，覆盖率是 0.75。这个数字只对事先冻结的主张集合有意义。Agent 若在结束时删掉难答主张，分数会虚高。

关键主张不能被平均数藏住。可以给每条主张一个决策权重，再加硬门禁。C3 合同适用性为空时，即使其余七条齐全，输出仍为“阻断”。普通背景主张为空时，可以降级措辞并登记未知量。

覆盖也不等于正确。研究评测至少把四项分开。

- 覆盖检查承诺的主张是否都被处理。
- 蕴含检查证据是否支持紧邻原子主张。
- 来源质量检查权威性、直接性、版本和独立性。
- 综合检查结论是否遵守反证、适用范围和决策门禁。

停止条件由这些量共同决定。所有关键主张已通过，普通主张达到约定覆盖，新查询连续两个批次没有增加独立根来源，冲突都有裁决或升级记录，此时可以停止。若预算先耗尽，就返回实际覆盖与未完成队列。开放网络无法证明“已经搜遍”，停止理由必须比“感觉够了”具体。

## 五份报告可能只有一个证据祖先

失败报告里的三个子 Agent 各给出一份摘要。第一份直接读承运方新闻稿，第二份引用行业媒体对新闻稿的转述，第三份引用聚合站复制的行业媒体。若按报告计票，结论获得三票。若沿链接向上追，只有一个根来源。

这条上游链称为 `source ancestry`。账本里的 `root_id` 用来标记最早能提供该观察的材料。转载、镜像、同稿不同域名和子 Agent 摘要继承同一个根。它们可以帮助定位，却不会增加独立观察。

2026 年 9 月的 [Epistemic Sybil Resistance](https://arxiv.org/abs/2609.01873) 把这个问题表述得更严格。若一份报告在已知根来源后没有带来新信息，它对目标事实的条件增量可以写成 $I(\Theta;Z\mid R)=0$。论文在合成文档上的受控实验显示，仅增加同根报告数量会误导朴素聚合器。它改变了本章的一个实现判断。多 Agent 汇总必须携带祖先标识，不能只看答案相似度。该结论来自新预印本、合成文档和特定模型，不能把论文中的退化幅度当作生产失败率。

真正冲突也不靠多数票处理。合同附件说赔付只覆盖特定服务等级，公共页面说全部国内包裹都可申请。先判断它们是否谈同一对象。若对象相同，再比较法律或业务权威、签署主体、版本、生效日和条款层级。仍无法裁决时，保留一个 `conflict set`，把两边原文位置和影响交给合同负责人。

一个可操作的祖先规则如下。

```text
发现新材料
  → 找它声称事实的最早可访问来源
  → 记录 root_id 与传播路径
  → 比较版本、对象和有效期
  → 同根材料合并为一个证据簇
  → 新观察才增加独立来源计数
```

网页里的文字也可能要求 Agent 忽略系统规则、上传内部合同或改写结论。网页文字只作为不可信数据，授权来自运行时策略和责任人。抓取器保留原文和来源，执行层不响应其中的命令。遇到要求泄露内部数据的页面，当前搜索分支立即停止并记录注入事件。

## 只有互不等待的分支值得并行

到这里，团队才有资格讨论 Multi-agent。问题树画成依赖图后，三个初始分支可以同时开始。公共规则分支读取一手政策，合同分支核对签署文件，内部数据分支计算基率。它们输入不同、结果可以分别验收，也不需要等待彼此。

“公共规则是否适用于本平台”不能独立开始。它需要公共规则版本和合同附件两个前置结果。最终策略建议也必须等待替代原因与风险边界。把这些依赖任务同时扔给五个 Agent，会产生猜测、返工和共享上下文争用。

三个搜索分支共享全局上限：十二次查询、六万 token。每个 worker 最多四次查询和一万八千 token，协调器保留六千 token 只做调度、去重与合并，不额外搜索。这样才与单 Agent 的十二次查询、六万 token 同预算。每个分支只接一份窄合同。

| 字段 | 示例约束 |
|---|---|
| 输入 | C1、允许访问的公共域名、截至日期 |
| 输出 | 证据记录，不交散文报告 |
| 必查 | 官方政策及历史版本 |
| 反证 | 寻找延迟生效或地区排除 |
| 预算 | 最多四次查询、一万八千 token、十五分钟；受全局上限约束 |
| 停止 | 两个独立查询批次无新根，或关键材料命中 |
| 禁止 | 访问内部合同、修改共享结论 |

主 Agent 负责依赖调度、去重、冲突升级和预算，不负责把所有子报告拼接成长文。引用核验最好作为独立步骤读取冻结账本，逐条检查 URL、定位和蕴含。若核验者与写作者共享“必须给出建议”的压力，它也可能放过缺口。

Anthropic 的[多 Agent 研究系统工程复盘](https://www.anthropic.com/engineering/multi-agent-research-system)报告其内部评测中，特定 lead 与 subagent 配置比单 Agent 高 90.2%，同时多 Agent 相对普通对话使用约 15 倍 token。文章还指出，token 使用能解释 BrowseComp 表现的大部分方差，并把高价值、可并行的广度搜索列为合适场景。它支持“并行要与任务结构和计算量一起评估”，不构成跨模型、跨预算的普遍提升定律。数据来自单一供应商的内部系统，也缺少本案例同总计算的随机对照。

## 净收益要扣掉重复、协调与额外计算

团队用同一批八条主张跑四种配置。下表仍是教学实验数据，目的是示范该怎样报结果。

| 配置 | 合格覆盖 | 独立根 | 错配引用 | 总查询 | token | 墙钟 | 阻断项 |
|---|---|---|---|---|---|---|---|
| 固定流程 | 5/8 | 4 | 0 | 4 | 18k | 13 分 | C3、C6 |
| 单 Agent | 6/8 | 5 | 1 | 12 | 60k | 39 分 | C3 |
| 三 Agent 同总预算 | 6/8 | 5 | 0 | 12 | 60k | 22 分 | C3 |
| 三 Agent 高预算 | 7/8 | 7 | 0 | 24 | 138k | 19 分 | C3 |

同总预算的多 Agent 没增加覆盖，但减少了一条错配引用并缩短墙钟。高预算版本多找到一个独立根来源，却仍没有合同附件。它可以被评价为研究效率改善，不能被写成“问题已经解决”。

看到这些具体差异后，再定义净收益。

$$
NetGain=\Delta Q-\lambda_c\Delta Cost-\lambda_t\Delta Time-\lambda_r\Delta Risk
$$

$\Delta Q$ 可由关键覆盖、引用正确和冲突发现的增量组成。`Cost` 包含 token、工具费用与人工复核。`Time` 是墙钟时间，`Risk` 则记录敏感材料暴露、网页注入和错误合并概率。权重由业务责任人预先给出。高价值紧急研究可能愿意用更多计算换时间，普通工单则未必。

报告必须同时给出同总预算和实际高预算结果。同总预算帮助判断协调结构，高预算结果回答团队愿意多花资源后能得到什么。只展示后一组，会把 test-time compute 的增益包装成架构免费收益。

扩容也要逐级发生。先开放两个独立分支，检查重复率、失败率和主 Agent 合并负担。新增 Agent 若连续两轮只返回已有根来源，就缩回单 Agent。并发上限根据这些对照结果设定。

## 一次缺证据的拒绝比完整建议可靠

最终，公共政策、内部基率和替代原因都有材料，合同目录却显示附件缺页。运营要求“先根据公开说明给一个大概率建议”。研究 Agent 应输出下面这种拒绝。

```text
decision_status: blocked
recommendation: 不调整自动退款条件
blocking_claim: C3 合同适用性
known: 公共规则已更新；内部申请率在约定口径下上升
unknown: 已签署附件是否覆盖或排除公共规则
why_it_matters: 若专属条款优先，公开页面不能证明平台账户可按新规则追偿
safe_next_step: 由合同负责人补齐签署附件；到账本后只重跑 C3 与最终综合
expires_at: 2026-09-06T18:00:00+08:00
```

这次终止保存了可复用证据，也明确下一步和失效时间，避免把搜索者的概率判断变成退款权限。补件后，系统不必重跑全部网络搜索，只校验附件签名、主体、有效期与 C1 的政策版本，再让独立审阅者重算门禁。

若发现公共页面与合同明确冲突，也不由 Agent 自选“更新的一份”。它冻结建议、提交冲突集。若内部数据分母不可恢复，则把“异常率上升”降为未知，不能用 31 条原始计数替代。真实失败分支必须进入评测集，成功报告不应是唯一训练材料。

本章最终判断可以接受证伪。若同预算实验显示多 Agent 没有提高合格覆盖、引用正确或墙钟效率，就保持单 Agent。若任务分支高度依赖，也应跳过并行。Multi-agent 只能作为经对照后获得的运行配置，研究深度仍由证据质量衡量。

## 用一份小实验把架构争论落到数据上

下面的脚本不调用模型。它用八条虚构证据记录演示三个评分项。把代码保存为 `research_ab.py` 后执行 `python research_ab.py`，应看到覆盖、独立根数和重复率。然后按练习替换记录。

```python
records = [
    {"claim": "C1", "root": "R1", "current": True, "applicable": True, "locator": "§3"},
    {"claim": "C2", "root": "R1", "current": True, "applicable": True, "locator": "§4"},
    {"claim": "C3", "root": "R2", "current": True, "applicable": False, "locator": "§12.2"},
    {"claim": "C4", "root": "R3", "current": True, "applicable": True, "locator": "query-v4"},
    {"claim": "C5", "root": "R4", "current": True, "applicable": True, "locator": "row-18"},
    {"claim": "C6", "root": "R5", "current": True, "applicable": True, "locator": "case-7"},
    {"claim": "C7", "root": "R5", "current": True, "applicable": True, "locator": "case-9"},
    {"claim": "C7", "root": "R5", "current": True, "applicable": True, "locator": "mirror"},
]
required = {f"C{i}" for i in range(1, 9)}
critical = {"C3", "C4", "C8"}
qualified = [r for r in records if r["current"] and r["applicable"] and r["locator"]]
supported = {r["claim"] for r in qualified}
roots = {r["root"] for r in qualified}
valid_count = len(qualified)
coverage = len(required & supported) / len(required)
duplicate_rate = 1 - len(roots) / valid_count
critical_missing = critical - supported
print({"coverage": coverage, "independent_roots": len(roots),
       "duplicate_rate": round(duplicate_rate, 3),
       "critical_missing": sorted(critical_missing)})
assert "C3" not in supported
assert critical_missing == {"C3", "C8"}
assert coverage < 1.0
```

跟做任务使用 2 个标准回合。先按脚本运行原记录，观察版本、适用性和定位字段怎样共同决定 `qualified`；再为每条记录补来源类型与蕴含关系。把 C3 的不适用证据改成同一新闻稿的三个转载，验证独立根数不增加。最后提交 `decision-contract.md`、`claim-ledger.json`、运行输出和一段拒绝建议。审阅者随机抽两条证据，应能直接从账本定位原文并复算脚本结果。

变式任务把 C3 的有效合同补上，同时让 C4 的内部统计缺少分母。你要更新阻断项，不能沿用旧拒绝理由。再把三条互不等待的记录分给三个模拟 worker，记录总处理时间和重复根数。反馈标准看的是阻断是否随证据变化、是否保留旧版本，以及并行是否有可量化收益。

迁移任务选择一个不涉及退款的问题，例如判断某开源依赖是否适合进入内部工具。先列许可证、维护状态、漏洞修复和替代品四类主张，只对互不依赖的搜索分支并行。产物仍用同一账本，但不能复制退款字段值。若你无法说明某个 worker 等待谁，就先维持单 Agent。

一次合格反馈应指出具体记录。比如“E7 只支持主合同引用公共规则，不能支持附件已采纳，所以 C3 保持 blocked”。“来源不够好”太模糊，不能帮助下一轮改进。建议用 0 到 2 分审阅问题树、证据蕴含、祖先去重、并行净收益和拒绝质量，总分低于 7 分就缩小问题重做。

## 本章小结：研究协作的价值取决于独立证据与净增量

新增主张覆盖和独立证据根决定多 Agent 研究的价值，报告数量不计入证据强度。本章先以单一工作流建立同预算底线，再用主张树、证据账本、来源祖先和硬门禁审理并行分支。新增覆盖若绕过关键未知，或收益不足以抵消重复、协调与额外计算，可靠的交付仍应保留阻断结论。

研究流程跑通后，团队会积累很多成功与失败轨迹。它们还不能立刻用于训练 Agent，必须先冻结下面这组交接物。

- `task_contract_version` 固定问题树、权限与终止条件。
- `ledger_schema_version` 固定证据、祖先、冲突和未知字段。
- `environment_snapshot` 保存可访问材料、抓取时间和工具版本。
- `trace_id` 串起每次查询、观察、账本更新与拒绝。
- `eval_version` 分开覆盖、蕴含、独立根、成本和硬门禁。
- `outcome` 同时保存成功、阻断、工具错误和预算耗尽。

这些字段能让下一章判断一次失败来自计划、执行、环境还是评测。缺任何一项，奖励都可能追错对象。下一章进入 [Agent Learning、RL 与自我改进](/frontier/agents/08-agent-learning)，它只在这套轨迹和验证器稳定后讨论学习，并把训练权限与线上退款权限彻底隔离。
