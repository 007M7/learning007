## 十章不是十种产品，而是一条责任不断加深的链

第一阶段从“自动退款”这个含糊需求开始。你先把模型、scaffold、工具、环境、policy gate 和 verifier 分开，再拿 single-call、固定工作流与受限 Agent 做反事实比较。路径可以枚举时，工作流已经足够；路径必须根据新观察改变时，Agent 才得到候选资格。规划随后不再是一段漂亮步骤，而是带前置条件、预期状态差分、预算、失败恢复和停止点的可执行结构。

第二阶段让 Agent 真正接触外部世界。工具被拆成读取、提案与提交：提案是不可执行的结构化草稿，提交才是改变业务状态的动作，二者不能因为都叫“创建”而混在一起。MCP 只负责互操作和传输层能力，不替业务系统授予订单级权力。工具回执丢失时，系统保留 `outcome_unknown`，用原幂等键和状态查询恢复。记忆则从“长上下文技巧”变成数据责任：一条内容何时写入、由谁看见、何时冲突、怎样过期或删除，都必须能回答。历史批准不能经摘要变成新订单的长期授权。

第三阶段把同一边界迁移到 GUI 和代码仓库。Computer-use Agent 看到的是可能过时、遮挡或位置漂移的界面；动作前要重新定位对象，动作后要读取环境验证结果。Coding Agent 面对的也不是一个文本补全题，而是仓库版本、问题复现、依赖、最小 diff、测试、静态检查、审阅与合并权限组成的系统任务。模型说“已修复”与环境测试通过是两件事。

第四阶段才允许复杂协作和学习进入候选。Deep Research 先维护 claim—evidence ledger、来源祖先、冲突与覆盖，再判断哪些子问题真的可以并行。多名 Agent 若共享同一来源，只产生多份报告，不产生多份独立观察。Agent learning 只有在任务、轨迹、奖励、约束和 held-out 回归稳定后才成立；一次结果奖励不能自动说明长轨迹中哪一步值得强化。

第五阶段把一直存在的护栏提升为系统方法。评测拆开模型、scaffold、环境、Judge 和基础设施，让版本差异能归因；安全治理把不可信内容与高权限能力隔开，用最小权限、能力令牌、执行点授权、沙箱、网络出口、人工确认、停止和回滚限制爆炸半径。最终交付不是“Agent 更强”的宣言，而是一份可重算的 go、conditional go 或 no-go 决定。

## 五次阶段迁移共同检查一种能力

每两章后的阶段总结都换了业务对象。这样做不是为了增加案例，而是为了暴露“记住答案”和“掌握关系”的区别。

| 阶段迁移 | 被保留的知识关系 | 必须重新建立的内容 |
|---|---|---|
| 边界与规划 | 最低复杂度、状态—动作—反馈、预算与停止 | 业务目标、合法动作、环境验收和恢复规则 |
| 工具与记忆 | capability 不等于 authority；历史事实不产生当前权力 | 工具合同、主体/资源/时效、记忆生命周期与删除范围 |
| GUI 与 Coding | 动作前定位，动作后由环境验收；高风险步骤需要确认 | 页面/仓库对象、坐标或版本、测试 oracle 与回退对象 |
| 研究与学习 | 报告不等于证据；奖励必须回到可归因的决策 | claim 集、来源祖先、任务 DAG、轨迹 schema 和 held-out 集 |
| 评测与安全 | 能力主张要可证伪；不可信数据不能扩大能力 | 分层基线、攻击面、能力令牌、发布门槛和事故 owner |

迁移中最有价值的结果往往是正确拒绝。新场景缺少可复位环境，就停在模拟器；证据链不完整，就拒绝高置信结论；批准已经过期，就不提交动作；训练更新让安全切片回归，就回退模型。系统知道自己不能继续，是一种可验证能力。

## 四条不变量比任何 Agent 框架更稳定

第一，**文本不能自己产生权力**。用户消息、网页、PDF、工具描述、记忆摘要和另一个 Agent 的报告都属于输入。它们可以提出请求、提供证据或触发检查，不能自行授予工具、扩大 scope、延长批准或改变组织政策。授权要在动作提交点回到当前主体、资源、操作、参数、时效与权威状态。

第二，**模型关于成功的陈述不能替代环境成功**。工具返回“accepted”可能只是排队，网页按钮变灰不代表后台保存，测试日志缺失也不代表测试通过。验收器读取最终数据库、页面、文件、提交或外部对象的必要、允许和禁止差分。回执不明就保持未知，不能为满足用户期待把未知改写成完成。

第三，**中间产物的数量不能制造新证据**。多个检索 chunk 可能来自同一页，多个 Agent 可能共享同一来源，多个 Judge 也可能共享模型偏差。系统保存 provenance 与 evidence ancestry，区分独立来源、相关抽取和派生总结。信息可以因重复抽取而增加一些，但不能按报告数线性累积信心。

第四，**复杂升级必须与简单基线在同一合同下比较**。规划搜索要与线性 ReAct 或固定工作流比较，多 Agent 要与确定并行和单 Agent 比较，学习更新要与冻结策略比较。任务、初始环境、工具权限、预算、终止和评分不一致时，最高分不能说明机制更好。

四条不变量不会因模型升级而失效。模型更强可能改变哪些分支值得自动化，却不会让权限、外部状态、来源独立性和公平对照变得多余。

## 选择执行形态时，先走最低复杂度阶梯

一个需求可以沿六级阶梯上升，每一级都需要前一级解决不了的失败作证。

| 形态 | 路径由谁决定 | 适合什么 | 升级证据 |
|---|---|---|---|
| 确定程序 | 代码 | 规则、计算、权限与事务明确 | 输入含开放语义，规则无法可靠抽取 |
| 单次模型调用 | 一次生成 | 分类、抽取、改写、候选草稿 | 需要读取新观察才能决定下一步 |
| 固定工作流 | 预写状态机 | 合法步骤可枚举，工具顺序稳定 | 真实失败集中在不可预写的路径选择 |
| 受限单 Agent | 模型在窄动作集中选择 | 开放搜索、动态反馈、可恢复探索 | 存在可分离并行或独立权限域 |
| 多 Agent | 协调器与多个执行者 | 高价值、可并行、合并可验证的任务 | 同预算任务级对照显示净收益 |
| 学习型 Agent | 离线或受控训练更新策略 | 稳定轨迹、可归因反馈和重复任务 | held-out 与安全回归持续通过，且可回退 |

这不是成熟度模型。一个团队停在固定工作流，可能比使用多 Agent 更成熟，因为它已经知道任务不需要自由路径。形态下降也应成为运行策略：Agent 无进展时退回工作流，写工具失效时退回草稿，证据冲突时交给人，风险增大时关闭外部能力。

## 状态、证据与权限必须是三种不同的东西

Agent 讨论常把三者塞进一个 Prompt。状态说明现在发生了什么，证据说明某个事实凭什么成立，权限说明谁在什么条件下可以改变什么。它们可能互相引用，不能互相替代。

退款任务里，“物流接口返回超时”是状态；“承运商签收记录及其版本”是证据；“客服主管批准对订单 1042 退 80 元”是权限事件。模型可以根据状态选择下一条只读查询，可以依据证据提出退款草案；最终提交仍要检查当前订单、金额、批准哈希和业务规则。即使模型完整记住三者的文字，Runtime 仍需把权威值存进可审计系统。

跨日运行时再加入第四种对象：**历史经验**。它能提醒“这类请求常缺物流证据”，却不能说当前请求已经满足。记忆写入要保存来源、主体、用途、敏感度、有效期和替代关系；召回先找相关，再按当前目的审查 admissibility。删除还要传播到向量索引、摘要、图边与缓存，不能只把主表一行设为 inactive。

这种分离直接改善调试。错误事实送回证据链，重复副作用送回状态和幂等，越权送回授权，旧经验误用送回记忆政策。所有错误都改 Prompt，会让责任层继续模糊。

## GUI 和代码把“看见—行动—验证”变成工程对象

网页或桌面 Agent 的观察可以来自截图、可访问性树、DOM 或它们的组合。截图保留视觉布局，却需要坐标 grounding；结构树提供语义节点，却可能缺少画布、远程桌面或被自定义组件破坏。可靠实现会为动作绑定观察版本、目标身份、定位证据和预期变化，并在点击前重新确认高风险对象。

界面动作的风险不是由“点击”这个动词决定。同一个点击可以展开只读菜单，也可以转账、删除或发布。策略应按后果分级：可逆浏览可以自动执行，修改草稿需要预览，不可逆或高影响提交要求参数绑定确认。环境漂移、弹窗、焦点变化、缩放和滚动都要进入测试；坐标在旧截图上正确，不代表在新状态上仍指向同一对象。

Coding Agent 只是更结构化的行动环境。观察包括 issue、仓库图、搜索结果、测试和编译错误；动作包括读取、编辑、执行命令和提交。最小闭环是复现失败、定位责任、写最小补丁、运行相关与回归检查、审查 diff、再决定是否合并。仓库测试可能不足，隐藏测试可能错误，依赖安装也可能执行不可信代码，所以环境要隔离并限制网络、秘密和写范围。

无论 GUI 还是代码，最终文本都不是 oracle。页面状态差分、测试结果、静态检查、安全扫描和人工审阅共同决定完成。Agent 如果改了测试让坏实现通过，或者在页面上误点另一个同名按钮，模型自述再完整也不能挽回。

## 研究协作先解决覆盖，轨迹学习再解决可归因改进

Deep Research 的目标不是生成更长的报告，而是让一组明确主张获得足够、当前、可追溯的证据。开始前列 claim、必要来源类型、冲突处理和停止条件；搜索过程记录 query、结果、拒绝原因和遗漏。覆盖不足时继续搜索或缩小结论，来源冲突时并列展示，不能用流畅总结抹平。

并行研究只对可分离子问题有意义。协调器建立 task DAG、总预算和输出 Schema，worker 领取窄任务，合并器根据来源祖先与必要 claim 验收。若每个分支都依赖上一分支的新实体，更多 Agent 只会等待和重复上下文。若确定并行函数已经完成任务，自由 Agent 也未购买到价值。

学习发生在这套过程稳定以后。轨迹至少保存观察、可选动作、实际动作、外部结果、约束、成本和终止。最终成功是稀疏反馈，一条长轨迹中可能同时存在好决策和偶然补救；把同一个总奖励复制到每一步会错误归因。过程标签、层级 credit 或反事实重放可以提供更细信号，也会引入新的 Judge 与模型偏差。

训练执行与线上执行要隔离。生产 Agent 不能因一次成功自行改写 Prompt、工具权限或记忆政策。候选更新在离线快照或受控沙箱产生，使用 sealed holdout、安全集和旧能力回归验收；发布以后仍保留版本、shadow、canary 与回退。自我改进首先是一条受治理的软件发布链，不是一句“从经验学习”。

## 评测要把一个排行榜分数拆回多变量系统

Agent 结果可以写成一个依赖关系：任务、模型能力、scaffold、环境、评价器、基础设施、预算和随机性共同产生观察结果。换模型的同时增加工具、延长预算、修复容器并更换 Judge，最后的差异无法归因。实验卡应固定其他变量，一次只审理主要变更，并保存所有版本。

任务级比较优先使用相同初始状态和相同预算。当前版与候选版在每个任务上的配对结果，比两个独立平均更能说明哪些失败被修复、哪些旧正确回归。非确定任务可以重复，但重复运行嵌套在任务内，不能把同一任务的五次尝试当成五个独立用户。状态型任务还要报告必要、允许和禁止差分，不能只看最后回答相似度。

Judge 需要 ground-truth 锚定和人工校准。格式、对象数量、权限、最终数据库和成本能由程序判断时，不使用 LLM Judge。语义判断则写带反例的 rubric，盲掉版本名、随机左右顺序，检查位置、长度和自偏好。自动评分与人工在关键错误类不一致时，先修测量工具，不用总体一致率遮住风险。

证据是否充分与实验是否覆盖也要分开。一份日志可能足以重算某个成功率，却只保存了容易样本；另一份包声称覆盖所有分支，却缺少原始工具结果。发布主张要同时给分母、任务清单、产物哈希、计算过程和未覆盖范围。

## 安全不是让模型永远听话，而是让错误后果有上限

Prompt injection 很难只靠另一段 Prompt 消除。不可信网页、邮件、代码注释和工具返回可以影响模型计划；系统要假设模型可能采纳它们，然后限制这次采纳能获得什么能力。默认只暴露任务所需工具和数据，读写分离，敏感能力使用短期、资源绑定的 capability，执行点再次检查主体、委派、参数、状态和批准。

**Action-commit boundary** 是模型建议与真实副作用之间的共同政策点。GUI 点击、API 调用和代码合并形式不同，都可以在提交前形成规范化动作：谁准备对哪个资源做什么，参数是什么，依据哪份观察和批准，预期差分与最坏后果是什么。政策引擎和人类确认看到的必须是即将执行的真实参数，而不是模型事先写的一段摘要。

沙箱负责缩小环境影响：临时文件系统、测试账号、秘密隔离、网络出口白名单、CPU/内存/时间和工具调用上限。监控只依赖可观察 trace 也能发现循环、重复动作、导航偏离和接近关键错误的信号，但它不能替代执行点授权。检测器漏报时，最小权限仍应阻止灾难性动作。

事故响应要有独立 kill switch。关闭新动作以后，在途任务仍需查询未知结果、处理已经发生的副作用、保存受控证据并通知 owner。恢复不是简单重启模型，而是确认状态、权限和版本仍兼容。治理最终落实到谁批准风险、谁能停止、谁处理申诉与修复，而不是留在一页原则清单。

## 把整条路线收进一个可交接的自治证据包

```text
auditable-agent/
├─ manifest.yaml
├─ 01-common/
│  ├─ task-contract + complexity-adr + system-map + run-contract
│  ├─ model-scaffold-tool-environment-policy-grader-versions
│  └─ state-assertions + budget + stop-recovery + authority-delta
├─ 02-candidate/                    # 按 candidate_type 选择适用支路
│  ├─ gui_automation/
│  │  └─ gui-harness + initial-final-snapshots + forbidden-diffs
│  ├─ coding_agent/
│  │  └─ base-commit + issue-acceptance + patch-test-evidence
│  ├─ research_agent/
│  │  └─ claim-ledger + source-ancestry + conflicts-unknowns
│  └─ learned_policy/
│     └─ trajectory-schema + data-splits + training-snapshot + safety-regression
├─ 03-evaluation/
│  └─ experiment-cards + paired-results + judge-calibration + coverage
└─ 04-safety-release/
   └─ threat-model + capabilities + red-team + rollback + decision
```

顶层 manifest 记录 `candidate_type`、任务、环境、模型、scaffold、数据、工具、policy、grader 和代码版本，连接每份产物的哈希、owner、验证状态与过期条件。`01-common`、评测和安全发布是所有候选共同合同；`02-candidate` 不是四份材料同时必交，而是按本次真实变化选择一支。GUI 候选不必虚构仓库 commit，Coding 候选不必制造来源祖先，研究候选不必伪造训练快照，未训练的普通 Agent 更不能拿空 trace 冒充学习候选。若一个版本确实同时改变多层，manifest 要显式列出组合类型与每个 changed artifact，并提交每个实际变化所对应的支路，不能用另一支的材料替补缺失字段。一次结果应该能向后追到输入和动作，一次发布应该能向前列出受影响能力，一次删除或回滚应该能枚举传播对象。

综合项目仍可使用受控退款 Agent。准备正常、信息不足、物流冲突、回执丢失、跨账户、注入和预算耗尽等共同任务；页面漂移只进入 GUI 候选包，补丁失败只进入 Coding 候选包，来源独立性与训练回归也分别进入研究或学习候选包。每次实验先声明一种主要 `candidate_type`，比较固定工作流、单 Agent 和必要时的多 Agent；学习候选另在离线轨迹上产生。全部写操作指向可复位假服务，不能为了“更真实”接生产支付。

最终评审者不看提示词宣传，只拿共同 manifest、逐任务结果、状态差分、发布门槛，以及 `candidate_type` 指向的专属材料。他审 GUI 包时看界面与业务终态，审 Coding 包时看 commit、diff 与测试，审研究包时看来源祖先，审学习包时才要求轨迹、数据分区与训练快照。他应能指出哪个机制修复了哪类失败、哪个拒绝保护了什么、还剩哪些未知。如果作者必须口头补充关键条件，证据包尚未完成。

## 用三次延时复测判断是否真的形成能力

第一次复测在完成路线当天进行。选一个熟悉任务，合上正文画系统边界和 action-commit boundary，运行一个顺利样本、一个未知结果和一个越权样本。第二次在七天后换到陌生场景，例如报销、访客通行或代码发布，重新写工具和记忆合同，不沿用退款字段。第三次在三十天后给出一个表面分数很高、实际安全回归的候选，要求你独立作出 no-go 并指出回退层。

达到 `basic`，需要能选择最低复杂度、实现一次外部验收、处理超时和正确拒绝，并让同伴从 trace 重放。达到 `proficient`，还要识别来源相关、任务级比较和奖励错误归因，在新场景完成红队、回滚与发布判断。Quiz 只能提示概念误解，不替代这三次作品。

若复测失败，按现象回补。把工具发现当授权，回到第 3 章；旧历史变成新权力，回到第 4 章；点击与补丁只看模型自述，回到第 5、6 章；多 Agent 报告被当独立证据，回到第 7 章；总奖励无法定位决策，回到第 8 章；平均分掩盖环境或 Judge，回到第 9 章；攻击测试只看模型说了什么，回到第 10 章。

## 路线的出口是更精确地选择下一步

若你的主要困难仍是状态机、事务、权限、测试、可观测性和发布恢复，回补[软件与系统工程](/domains/software/)与[质量与生产交付](/domains/quality/)。如果需要理解 Transformer、适配训练、推理容量、Advanced RAG 或模型服务，回到[AI 进阶总结](/advanced/ai/summary)。如果问题是具体行业的用户、责任、指标与落地验证，进入相应产品与领域路线，不要把 Agent 机制当作行业经验。

前沿证据会继续变化。新论文先进入[证据库](/frontier/agents/evidence)，记录首次公开日、修订、实验设置、冲突与拒绝原因；只有它改变了当前机制、基线或边界，课程正文才更新。学习完成后仍保留简单实现和旧实验包，下一代模型可能让今天有效的 scaffold 变成负担。

你也可以选择不再增加自治。一个能引用、会停、可恢复、权限清楚的固定工作流，可能比开放 Agent 更适合当前任务。所谓前沿判断，不是永远走到技术最复杂处，而是能在证据变化时重新决定哪些自由值得购买、哪些责任必须留在人和程序手中。

## 参考资料

- Anthropic，[Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)，2024 年。用于 workflow 与 agent 的工程分界及从简单组合逐级增加复杂度；厂商经验不能替代当前任务的同预算实验。
- Yao 等，[ReAct](https://arxiv.org/abs/2210.03629)，ICLR 2023 年。用于 reasoning 与 action 交替的研究起点；经典论文不提供完整权限、持久状态与生产恢复机制。
- Model Context Protocol，[Specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28)，2026 年现行规范。用于当前协议角色、能力交换与授权入口；互操作能力不等于订单级业务 authority。
- Cerruti、Okamoto 与 Erol，[Agent Memory Is a Surface for Endogenous Authorization Laundering](https://arxiv.org/abs/2609.01836)，2026-09-01 预印本。用于持久记忆可能把错误摘要升级成虚假权力的近期证据；五个写入模型、两个执行模型和三个领域不能外推为生产事故率。
- Xie 等，[OSWorld](https://arxiv.org/abs/2404.07972)，2024 年。用于可复位桌面环境、真实应用和执行式评分；369 项任务与特定 OS/应用会老化，不能代表全部 GUI 工作。
- Jimenez 等，[SWE-bench](https://arxiv.org/abs/2310.06770)，ICLR 2024 年。用于真实仓库 issue、环境与测试式软件任务；数据污染、镜像可用性和测试质量会改变结果。
- Bara，[Epistemic Sybil Resistance: Multiplying AI Agents Without Multiplying Evidence](https://arxiv.org/abs/2609.01873)，2026-09-01 预印本。用于证据祖先与相关抽取的 no-minting 边界；合成证据世界和单一主要模型设置尚不能形成通用聚合标准。
- Luo 等，[Agent Lightning](https://arxiv.org/abs/2508.03680)，2025 年。用于执行与训练解耦、MDP 轨迹和层级信用分配；三类任务的作者实验不证明任意 Agent 都适合强化学习。
- Pysklo 等，[Agent-Diff](https://arxiv.org/abs/2602.11224)，2026 年预印本。支持在企业 API 沙箱里用期望环境状态差分评价终态；“必要、允许、禁止”三类业务断言是本课程为受控案例增加的本地合同，并非论文提供的通用分类。服务副本也不覆盖真实权限、并发与全部副作用。
- Abhigya Verma 等，[AgentJudgeBench](https://arxiv.org/abs/2608.26623)，2026-08-27。用于 Judge 相对 ground truth 的专门评测与 DAG 工具任务边界；其模型、rubric 和环境不构成所有 Judge 的固定误差率。
- Zhu 与 Chang，[ClaimReceipt](https://arxiv.org/abs/2609.01992)，2026-09-02 预印本。用于区分证据足以重算某项主张与证据覆盖了承诺实验范围；新规范和小规模研究仍需独立复现。
- Debenedetti 等，[AgentDojo](https://arxiv.org/abs/2406.13352)，2024 年。用于不可信工具内容、间接注入和动态 Agent 环境；攻击与防御持续演化，单个 benchmark 不能提供永久安全保证。
- NIST NCCoE，[Software and AI Agent Identity and Authorization](https://www.nccoe.nist.gov/projects/software-and-ai-agent-identity-and-authorization)，2026 年公开项目材料。用于身份、委派、最小权限与审计问题框架；征求意见材料不是强制标准或具体合规结论。
