# 《API 契约测试：让前后端改动不再靠猜》

> 这是一个虚构微课程的导航型学习页，不对应任何真实学校、教师或课程网址，也不提供外部课程链接。

## 先判断它是否值得学

如果你经历过“后端只是删了一个字段，前端却在上线后才白屏”，这门课值得用三小时试一次。你不会在这里系统学习 API 设计，而会完成一份可执行的 `contract-cases.yaml`：它把调用方真正依赖的请求、响应与失败情形写成双方都能检查的约定。随后，你将用本地假服务故意制造字段删除、类型改变和错误码改变，观察检查怎样在联调前暴露破坏。

它适合会基本 HTTP 与 JSON、已经写过或调用过 API 的读者。完全没写过 API 的读者暂时不适合：请求方法、状态码和 JSON 字段还会占用你的主要注意力，契约反而容易变成照抄。先能独立发出一次请求、读懂响应，再回来会更省时间。

## 开始前的两分钟检查

请先回答三个问题：你能否说出一次 GET 请求中地址、状态码和响应体分别在哪里？能否看出 `"count": 3` 与 `"count": "3"` 的差别？能否在本机运行一个返回固定 JSON 的假服务？前两项是硬先修；第三项可以边做边补，本课程会把假服务当作验证环境，而不是额外项目。

若前两项任一答不上来，停止计时，先用自己的旧接口做一次请求并标注这三处信息。若只卡在本地运行环境，可以先阅读案例，但必须在进入破坏实验前补齐，否则你只能理解描述，不能证明契约真的拦住了变化。

## 选择你的路线

| 路线 | 时间 | 你要完成什么 | 结束条件 |
| --- | ---: | --- | --- |
| 最小路线 | 3 小时 | 一份含三类破坏案例的契约与一次本地验证 | 三次破坏都得到明确失败结果 |
| 完整路线 | 8 小时 | 在最小路线之上补齐正常、边界和失败场景，并整理变更决策 | 别人能按文件复现实验并判断是否可发布 |

时间紧时走最小路线，不要删掉验证，只缩小接口范围。你可以只选一个“查询订单”接口：第一小时写出正常响应和调用方依赖；第二小时依次删除字段、改变字段类型、改变错误码；第三小时修正契约或实现，并记录哪一方需要迁移。三小时后的产物不是笔记，而是一份能回答“这次改动会不会伤到调用方”的证据。

完整路线再投入五小时。先补空列表、缺省值和非法参数等边界，然后让前端视角与后端视角各审阅一次 `contract-cases.yaml`。接着为每个失败写清预期、实际结果与处理决定，最后从空目录重跑。若只有你自己的机器能通过，课程还没有完成。

## 核心实践：让破坏自己说话

先在 `contract-cases.yaml` 中写一个调用方确实会读取的字段，例如订单总额。启动本地假服务，让正常响应通过。然后一次只改一个条件：删除该字段；把数字改成字符串；把约定的错误码换成另一个错误码。每次运行后都保留失败信息，并用一句话解释影响，例如“页面无法继续计算总额”。这三种变化分别检验结构存在性、值的类型和失败语义；它们共同说明，返回 JSON 看起来相似，不等于调用关系仍然安全。

遇到检查没有失败时，不要立刻添加更多工具。先确认契约是否真的声明了调用方依赖、假服务是否加载了修改后的响应、运行命令是否指向当前文件。症状是“明明破坏却通过”，原因通常藏在未表达的依赖或未生效的样本里；修正后重复同一破坏，直到结果可复现。

## 交付与下一步

请把 `contract-cases.yaml` 交给一位没有参与编写的人，只提供本地启动与验证方法。对方应能在十五分钟内重现三次失败，并指出每次是字段、类型还是错误语义被破坏。做不到，就回到契约补足上下文；做到后，再把问题带到下一阶段：当同一接口有多个调用方时，谁负责声明依赖，谁有权批准破坏性变更？
