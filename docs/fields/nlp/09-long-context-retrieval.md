# 09 · 长上下文、检索与知识边界

> 长上下文是资源上限，不是能力保证；只有控制证据位置、长度、语言、密度和干扰，才能分辨找不到、没读懂与生成没遵循。

## 先别问谁最好，先问你在优化什么

> 可放入百万 Token 是否等于能够稳定利用它们？

模型能接收 1M tokens，但审查 400 页双语招标书时漏掉中段否决条款。盲目扩大窗口会增加费用和噪声；RAG 也可能因切块丢跨页条件。需要全文、检索、结构化目录和 oracle-evidence 四组。

## 把选择拆成三条判断轴

| 知识节点 | 先用一句话说清 | 什么时候值得选择它 | 先排除的误解 |
|---|---|---|---|
| NLPF25 · 上下文容量 | 接口可接收的 token 数不等于可可靠利用的信息量 | 有效长度如何测 | 窗口大小等于阅读能力 |
| NLPF26 · 检索增强 | 外部检索把相关证据压缩进模型条件 | 召回与利用哪个是瓶颈 | RAG 只要召回率高即可 |
| NLPF27 · 长文诊断 | 位置、密度、顺序、语言和干扰共同影响利用 | 怎样定位失败层 | needle 测试代表复杂推理 |

读表时不要横向背三行。任选一行，把“定义—决定—反例”连成一句因果解释；然后把本章案例中的一个输入替换掉，检查原判断是否仍成立。

## 判断树：注意力竞争、检索瓶颈与有效上下文

位置编码允许外推不代表训练分布覆盖；大量干扰文档会争夺注意力。RAG 将问题映射到候选块，瓶颈可分为 corpus、chunk、retrieval、rerank、context assembly 与 answer utilization。Oracle evidence 能把检索误差从利用误差中分离。

flowchart LR
 Q[问题] --> R[检索/目录]
 C[版本化长文] --> R
 R --> A[上下文组装]
 A --> M[模型利用]
 M --> O[带引用答案]
 O --> V[claim 支持]
 V --> D{失败归因}
 D --> R
 D --> A
 D --> M
~~~~

## 不要让一个分数替你做决定

端到端正确率可分解近似 $P(correct)=P(recall)P(use\ correct|recalled)P(generate\ faithful|used)$。MLRBench 的思路是测有效利用而非声明窗口；实验矩阵令 $Y=f(position,length,language,density,distractor,model)$ 并报告交互效应。

把每个符号放回真实系统。下面任何一项说不清，计算正确也不能保证结论正确：

- 证据是否完整落在一个 chunk
- 关键条件是单点还是跨段组合
- 输入长度用各语言真实 token 计量
- Judge 是否也会随长度失效

## 做到什么，才算结果可信

| 观察维度 | 要留下的记录 | 它防止你误判什么 |
|---|---|---|
| 任务质量 · 上下文容量 | 主指标、分层指标、置信区间和失败类型 | 平均分不能说明关键场景是否可用；本章还要据此判断：有效长度如何测 |
| 系统表现 · 检索增强 | 端到端时延、成功率、降级/拒绝和人工介入 | 局部模型分数不是用户任务结果；本章还要据此判断：召回与利用哪个是瓶颈 |
| 资源经济 · 长文诊断 | 训练/推理/标注成本、吞吐、容量与能耗 | 确认改进在真实预算下仍成立；本章还要据此判断：怎样定位失败层 |
| 风险运维 · 上下文容量 | 漂移、越权、事故、恢复时间和残余风险 | 把一次实验转化成可持续服务；本章还要据此判断：有效长度如何测 |

## 不要只看宣传：两份可核验依据

公开结果可以帮助设置基线，却不能替代你自己的数据、预算和失败代价。

### Lost in the Middle（2023-07-06）

先看这份来源时，要带着一个具体问题：相关信息在长上下文中的位置会影响使用吗？

控制相关文档在开头、中间和末尾的位置，测试多文档问答与键值检索。 模型常在开头/末尾更好，中间显著下降，展示非均匀位置利用。 因此，本章采用它来支持这样的判断：建立长上下文位置压力测试范式。

但它没有替我们回答所有问题。模型代际已变化，具体曲线必须在当前模型和真实任务复测。

### MLRBench（2026-03-31）

最后看这份来源时，要带着一个具体问题：现代模型在多语言长上下文中实际利用多少？

覆盖 7 种语言，通过可控长度、位置和任务测有效阅读而非 API 容量。 研究报告多种模型的有效能力常低于标称上下文的 30%，并存在语言差异。 因此，本章采用它来支持这样的判断：提供截至 2026 的多语言长上下文反证。

但它没有替我们回答所有问题。基准任务与模型列表有限；30% 是实验结果而非所有系统常数。

## 一次有约束的选择：双语招标书否决条款审查

将关键条款系统移动到 10/50/90% 位置，长度从 8K 到目标上限，加入相似旧版干扰。比较全文、RAG、层级摘要和 oracle evidence；按中英分别报告召回、利用、引用支持、P95 和单位文档成本。

### 读案例时做三次停顿

1. 到 上下文容量 时停一次：有效长度如何测？
2. 到 检索增强 时再停一次：哪条数据流、状态变化或约束能证明机制真的发生？
3. 到 长文诊断 时最后停一次：如果出现“只做 needle 单点检索”，系统应继续、拒绝还是交给人？

## 做一次公平对照：测出真实有效上下文

### 第 1 步：构造位置×长度×语言×干扰全因子子集

- **这一步在验证：** 上下文容量能否支持“有效长度如何测”这项判断。
- **至少留下：** 主指标、分层指标、置信区间和失败类型。
- **先停下来而不是继续调参的信号：** 只做 needle 单点检索。

### 第 2 步：建立 no-context 与 oracle-evidence 上下界

- **这一步在验证：** 检索增强能否支持“召回与利用哪个是瓶颈”这项判断。
- **至少留下：** 端到端时延、成功率、降级/拒绝和人工介入。
- **先停下来而不是继续调参的信号：** 答案对但引用错仍算成功。

### 第 3 步：逐层记录召回、重排、组装、利用和生成

- **这一步在验证：** 长文诊断能否支持“怎样定位失败层”这项判断。
- **至少留下：** 训练/推理/标注成本、吞吐、容量与能耗。
- **先停下来而不是继续调参的信号：** 把 oracle 结果当真实 RAG。

### 第 4 步：对跨块条件、表格和旧版本做专项难例

- **这一步在验证：** 上下文容量能否支持“有效长度如何测”这项判断。
- **至少留下：** 漂移、越权、事故、恢复时间和残余风险。
- **先停下来而不是继续调参的信号：** 忽略语言 token 差异。

完成示范后再做一次变式：用一份长文构造 24 个控制样本，移动相同证据并加入干扰；画准确率/支持率随位置与长度变化，给出选全文还是 RAG 的决策。

## 什么信号会推翻当前选择

先排除这些误解：窗口大小等于阅读能力；RAG 只要召回率高即可；needle 测试代表复杂推理；更多上下文不会伤害；引用存在就算有依据。

### 只做 needle 单点检索

- **先看什么：** 主指标、分层指标、置信区间和失败类型
- **回到哪项控制：** 长文默认分层导航加检索
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“测出真实有效上下文”的回归记录。

### 答案对但引用错仍算成功

- **先看什么：** 端到端时延、成功率、降级/拒绝和人工介入
- **回到哪项控制：** 标称窗口不进入能力宣传
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“测出真实有效上下文”的回归记录。

### 把 oracle 结果当真实 RAG

- **先看什么：** 训练/推理/标注成本、吞吐、容量与能耗
- **回到哪项控制：** 上下文组装保留章节/页码/版本
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“测出真实有效上下文”的回归记录。

### 忽略语言 token 差异

- **先看什么：** 漂移、越权、事故、恢复时间和残余风险
- **回到哪项控制：** 按失败层决定改 chunk、检索还是模型
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“测出真实有效上下文”的回归记录。

### Judge 与被测模型同样读不完

- **先看什么：** 主指标、分层指标、置信区间和失败类型
- **回到哪项控制：** 长文默认分层导航加检索
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“测出真实有效上下文”的回归记录。

## 证据改变时怎样重选

### 1. 长文默认分层导航加检索

验收时查看 **任务质量**，至少保存主指标、分层指标、置信区间和失败类型。如果观察到“只做 needle 单点检索”，这项决定必须重新评审，不能因为已经实现就默认保留。

### 2. 标称窗口不进入能力宣传

验收时查看 **系统表现**，至少保存端到端时延、成功率、降级/拒绝和人工介入。如果观察到“答案对但引用错仍算成功”，这项决定必须重新评审，不能因为已经实现就默认保留。

### 3. 上下文组装保留章节/页码/版本

验收时查看 **资源经济**，至少保存训练/推理/标注成本、吞吐、容量与能耗。如果观察到“把 oracle 结果当真实 RAG”，这项决定必须重新评审，不能因为已经实现就默认保留。

### 4. 按失败层决定改 chunk、检索还是模型

验收时查看 **风险运维**，至少保存漂移、越权、事故、恢复时间和残余风险。如果观察到“忽略语言 token 差异”，这项决定必须重新评审，不能因为已经实现就默认保留。

## 本章小结

- 容量与有效利用分离
- 位置和语言必须压力测试
- oracle 分离检索与利用瓶颈
- 端到端答案需 claim 证据支持
