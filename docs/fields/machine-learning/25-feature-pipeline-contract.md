## 一位用户出现了两个“近七天消费额”

流失模型在离线测试中表现稳定，上线后概率整体下降。团队抽查同一位用户在同一决策时点的输入，训练样本里近七天消费额为 860 元，在线服务只有 520 元。

离线 SQL 按订单创建时间统计，并在次日退款后保留原金额；在线流处理按支付成功事件统计，退款实时冲减。离线使用上海自然日，在线窗口按 UTC 滚动 168 小时。两列名称相同，实体、事件和窗口都不同。

模型代码没有报错。类型都是浮点数，范围也正常。只有把具体预测连同原始事件回放，差异才显现。

> 特征的身份由计算语义决定。字段名只是索引，不能承担时间、实体、过滤和版本合同。

## 一份特征契约至少回答哪些问题

以 `spend_7d` 为例，契约需要包含以下信息。

| 维度 | 要写清的内容 |
|---|---|
| 实体 | 用户、账户还是合同，主键如何组成 |
| 可见时点 | 哪个预测时间作为截止，是否允许同刻事件 |
| 原始事件 | 支付成功、订单创建或结算记录 |
| 窗口 | 滚动 168 小时还是七个自然日，使用哪个时区 |
| 过滤与去重 | 退款、取消、重复消息、测试订单怎样处理 |
| 聚合 | 求和、去极值、币种换算与精度规则 |
| 缺失语义 | 无消费、数据未到或用户不存在怎样区分 |
| 新鲜度 | 最晚允许延迟多久，超过后采取什么动作 |
| 版本 | 定义、代码、数据源与所有者 |

契约还应给出两个手算例子和至少一个边界反例。自然语言定义若无法据此算出唯一结果，还不够精确。

字段之间也有依赖。消费额依赖汇率，用户等级依赖账户规则。谱系图要追到原始来源和上游版本。上游表换口径时，系统才能找到受影响模型。

## event time 与 processing time 不能混在一起

事件时间表示业务事实发生时刻，处理时间表示系统收到或计算它的时刻。网络延迟、离线设备和批处理会让事件迟到。

训练回填常能看到后来补到的完整事件。在线预测在当时只能看到已经到达的数据。若离线按事件时间直接聚合所有后来到达记录，训练特征会比线上更完整，形成可用性泄漏。

需要定义 watermark 或迟到容忍。预测时只使用处理时间不晚于决策时点的事件，或显式模拟系统当时可见状态。迟到事件到达后可以修正分析表，不能悄悄改写过去在线输入再把它当当时特征。

标签窗口与特征窗口也要分开。特征截止之前的信息用于预测，之后成熟的结果用于标签。一个 SQL 查询同时连接两边时，逐列检查时间谓词。

## `fit` 与 `transform` 划出统计信息边界

标准化器需要学习均值和方差，填补器学习中位数，目标编码读取标签，PCA 学习方向，特征选择读取关联。这些步骤都有 `fit` 阶段。

训练折调用 `fit`，验证、测试和线上只调用已冻结的 `transform`。嵌套交叉验证中，每个内外层训练折都要重新拟合。缓存若按错误键复用，也会让其他折的统计量泄漏。

纯函数变换不一定需要拟合，例如单位换算和固定映射。它们仍需版本，因为规则修改会改变历史可比性。明确区分拟合参数与固定业务配置，有助于决定更新频率。

未知类别必须有确定行为。直接报错、映射到 unknown、使用哈希或拒绝预测，各有影响。训练时人为加入 unknown 示例，可以验证管线，而非等上线第一次遇到才处理。

## 共享代码能减少偏差，也不是唯一方案

离线批处理与在线低延迟环境可能使用不同语言和引擎。完全共享一套代码最直接，性能和基础设施有时不允许。此时要共享契约、测试向量和参考实现。

一组黄金样本包含原始事件、决策时点和期望特征。离线与在线实现都运行它，要求逐字段一致或落在明确数值容差内。黄金样本覆盖时区边界、迟到事件、退款、重复记录、空窗口、未知类别和大数值。

代码一致也无法消除数据差异。在线流可能丢消息，离线仓库可能修订历史。需要历史回放，让两条系统在相同时间可见快照上计算同一批实体，再比较差值分布。

Feature store 可以统一定义、存储和服务，仍要正确配置实体键、事件时间与物化逻辑。引入平台不会自动修复含糊定义。

## 回填是最容易污染历史的操作

上游修复数据后，团队会重算过去特征。若新规则使用了当时不可见的信息，回填表不再代表历史在线状态。用它重新训练会高估部署表现。

回填任务需要 as-of 时间。系统在某个历史决策时点只能读取此前已经生效的数据版本。保存每条特征的有效时间与系统时间，可以支持双时间查询，成本也更高。

最低可行方案是保留原始事件到达时间、主要规则版本与关键在线快照。事故调查时可以重放一批预测。若系统只保留当前修正值，历史证据会被覆盖。

删除与隐私请求还会影响可重放性。模型治理需要在合规删除和审计之间设计允许的元数据与聚合留存，不能默认永久保存全部原始数据。

## 训练服务偏差怎样被发现

第一层是契约测试，检查字段类型、范围、单位、缺失和类别集合。它能发现明显破坏，看不见两个合理数字的语义差异。

第二层是点对点回放。对同一实体与时点比较离线和在线数值，按特征报告一致率、绝对差和相对差。对浮点聚合设置业务可接受容差。

第三层是分布比较。监控缺失率、分位数、类别频率与相关结构。分布相似不能证明点级一致，分布差异却能触发调查。

第四层是预测回放。用同一模型分别读取离线和在线向量，比较分数和阈值翻转。小数值差异若集中在决策边界，业务影响可能很大。

告警要接到所有者与回退动作。特征新鲜度超时，可以使用上次值、降级模型或拒绝自动化。每种策略都要在离线模拟后写进契约。

## 特征需要服务等级与责任人

模型可用率受所有上游共同限制。关键特征依赖的事件流若只有 99% 可用率，模型服务即使本身达到 99.99%，完整预测也可能频繁降级。契约应记录新鲜度目标、最大允许缺失、值域变更通知和故障联系人。

按重要性给特征分层。一级特征缺失时停止自动决策，二级特征可以进入带缺失标记的降级模型，三级特征允许使用最近值。分层依据来自消融、决策代价与数据可靠性，不能只按 SHAP 排名。

上游变更应触发影响分析。字段改名容易被编译或契约测试发现，枚举含义、去重规则和事件触发条件变化更隐蔽。数据生产者需要提供语义变更记录，模型团队维护受影响特征与模型清单。

责任人还要处理长期漂移。某列稳定缺失不代表故障已解决，模型可能逐渐依赖降级路径。监控应统计各模式的流量、性能与人工量，超过期限就修复来源或正式删除特征。

## 做一次拟合边界与回放测试

选择一个包含聚合、类别编码、缺失填补和缩放的任务。画出从原始事件到模型输入的谱系，为十个关键特征填写契约。

将所有拟合变换封装进管线，写测试确认验证数据不会影响均值、类别表和目标编码。人为改变验证集极端值，训练折变换参数应保持不变。

建立至少二十个黄金案例，覆盖正常路径和边界条件。再选择一段历史流量，按当时事件可见性回放在线特征，与离线训练特征逐点比较。

注入三类故障。让事件延迟一小时，修改上游单位，并引入未知类别。观察契约测试、回放差异和预测监控分别何时发现。为每类故障写回退策略。

最终产物是特征契约、谱系图、可拟合管线、黄金样本与回放报告。任何正式模型必须引用确定的特征版本，无法追溯的临时列不能进入发布。

回放通过后还要做一次服务影子测试。让新流水线读取真实请求但不影响用户，比较旧系统与新系统的特征、预测和延迟。离线历史无法复现的网络、缓存与权限问题，通常会在这里出现。

## 特征质量也包含可维护性

一列特征带来很小性能提升，却依赖三个不稳定上游和一分钟在线查询，维护成本可能超过收益。模型选型应把新鲜度、可用率、计算费用和所有权纳入。

删除特征前做消融，并检查它是否只在某个时间或群体有用。保留时写明服务等级与降级行为。没有负责人的特征等于未来无人处理的故障入口。

下一章的 AutoML 可以自动组合预处理与模型。搜索空间只能包含通过契约和拟合边界审查的组件，否则自动化会快速放大泄漏与不可维护方案。

## 与 AI 协作生成契约测试

AI 可以根据 SQL、流处理代码和字段字典整理候选契约，生成黄金样本和边界测试。让它逐列对照事件时间、处理时间与决策时间，并指出两个实现的语义差异。

AI 无法从名称判断真实业务口径。`paid_at` 是否会被回写、退款是否冲减、用户合并如何处理，需要数据所有者确认。自动生成的契约必须经过真实事件回放。
