## 为什么现在要学“工具、状态与策略必须分层”

你看到的是输出变化，真正需要追的是状态、信息和约束怎样传递。团队把 FAQ 直接设计成多 Agent，结果延迟、费用和不可复现错误暴涨。

**本章核心判断：** 模型负责概率推断，工具负责确定执行，状态负责恢复，政策负责不可绕过的边界。

本章只追一个判断：**模型能建议什么、工具能执行什么、政策必须拦什么？** 最后必须用“系统责任与权限架构图”来回答；如果产物不能暴露失败样本，就还不能算学会。

## 给“工具、状态与策略必须分层”一个可操作定义

模型负责概率推断，工具负责确定执行，状态负责恢复，政策负责不可绕过的边界。

可操作定义必须允许你回答三件事：输入或条件是什么，发生了哪条机制，最后观察什么才算支持结论。本章的观察出口是 **系统责任与权限架构图**。

### 三个支撑概念，而不是本章的替代标题

| 位置 | 概念 | 在本章中的作用 | 一旦误用会怎样 |
|---|---|---|---|
| 前置 | 系统架构边界 | 模型、知识、工具、状态、策略和安全控制分层 | 把 Agent 当默认 UI |
| 当前支点 | Build/Buy/Portability | 供应商变化时能否迁移 | 多模型投票必然可靠 |
| 下游 | 能力阶梯 | 确定性流程到开放 Agent 的不确定性逐级增加 | 模型同时承担策略与执行授权 |

现在不用背表。请把三行连成一句因果解释，再用 **工具、状态与策略必须分层** 的场景举一个反例：哪些观测出现时，原解释必须被推翻？

## “模型能建议什么、工具能执行什么、政策必须拦什么？”依赖哪些前提

本章暂时不展开整套推导，但必须把判断拆成可以检查的前提：

| 顺序 | 必须成立的前提 | 对应控制 |
|---|---|---|
| 1 | 任务是否真的需要环境反馈循环；在“工具、状态与策略必须分层”中必须显式核对 | 政策/权限不用 prompt 保证 |
| 2 | 知识更新频率与模型截止差异；在“工具、状态与策略必须分层”中必须显式核对 | 状态独立于上下文窗口持久化 |
| 3 | 工具写权限和幂等/撤销能力；在“工具、状态与策略必须分层”中必须显式核对 | 供应商合同覆盖数据权、日志和退出 |
| 4 | 供应商数据留存、可观测和出口能力；在“工具、状态与策略必须分层”中必须显式核对 | 多 Agent 需要证明优于单 Agent/工作流 |

这四项共同约束“模型能建议什么、工具能执行什么、政策必须拦什么？”。任何一项只能靠猜测回答时，都应降低结论强度或补实验。

## 沿着一条完整推理链走到底

### 第一步：固定要解释或改变的对象

不要用“整体效果更好”代替对象。把“模型能建议什么、工具能执行什么、政策必须拦什么？”改写为：在明确输入、时间点和约束下，观察什么量，比较什么基线，最后据此采取什么动作。

### 第二步：写出中间机制

上一主题“Prompt、RAG、Workflow 与 Agent 阶梯”提供前置条件，本章用 **Build/Buy/Portability** 解释关键机制，并把结果留在“系统责任与权限架构图”中。下一主题“Build、Buy 与可迁移性”只在这些证据成立后继续。 只要中间任一环只能凭主观解释，结论就应降级为假设。

### 第三步：主动寻找反例

先尝试制造“架构绑定供应商私有状态”。如果当前方法仍给出看似正常的平均分，说明评价没有覆盖真正风险，需要补切片、过程指标或拒绝条件。

### 第四步：把结论写成可撤回决定

当前决定是“供应商合同覆盖数据权、日志和退出”。同时写下适用条件、责任人和重新评审信号；这样新证据出现时能更新，而不是把旧结论当永久规则。

这条推理链最终必须落到 **系统责任与权限架构图**。只有定义、机制、观察和决定互相对得上，文章内容才真正进入工作系统。

## 在“企业 FAQ 到工单 Agent”中定位关键判断

先用检索+引用回答，写操作必须经三个固定 workflow。只有当用户目标需跨系统追踪且预定流程覆盖率不足时，试验工具 Agent；写动作 sandbox、权限最小化、幂等键、预览确认和审计齐备。比较任务成功、人工分钟、P95、严重错误和恢复时间。

| 检查点 | 应留下的证据 | 不能接受的替代品 |
|---|---|---|
| 能力阶梯 | 主指标、分层指标、置信区间和失败类型，并写入系统责任与权限架构图 | 平均分不能说明关键场景是否可用 |
| 系统架构边界 | 端到端时延、成功率、降级/拒绝和人工介入，并写入系统责任与权限架构图 | 局部模型分数不是用户任务结果 |
| Build/Buy/Portability | 训练/推理/标注成本、吞吐、容量与能耗，并写入系统责任与权限架构图 | 确认改进在真实预算下仍成立 |

案例不是为了模仿结论，而是为了练习定位：如果“工具无幂等和撤销”发生，先查哪条数据或控制链，再决定继续、拒绝或交给人。

## 两份证据把“工具、状态与策略必须分层”的边界画在哪里

### Building Effective Agents（2024-12-19）

本章用它校准“工具、状态与策略必须分层”的边界：形成产品/架构共同的复杂度语言。。**不要越过的边界：**厂商实践文章不是独立对照实验，模式须用本地任务证据选择。

### Model Cards（2019-01-28）

这项工作追问：购买或集成模型时需要什么能力边界？

模型卡记录用途、非用途、评测条件、群体表现和限制。 案例说明单一榜分不足以支持部署选择。

本章据此采用的判断是：**把供应商模型能力主张转成可审查输入。** 但不能外推到：卡片由提供方编写，需独立验证且常缺系统级风险。

两份来源若结论看似冲突，先比较任务定义、数据分布、资源预算和评价方法；不能只用发布日期或排行榜高低裁决。

## 当 Build/Buy/Portability 失效，先查哪里

先排除这些看似合理的误解：Agent 比 workflow 更先进；模型卡等于独立验证；多模型投票必然可靠；Build 可避免锁定；Prompt 能执行权限。

### 工具无幂等和撤销

先查看 **资源经济**：训练/推理/标注成本、吞吐、容量与能耗。如果证据确认失败，回到“供应商合同覆盖数据权、日志和退出”，保存触发输入、系统响应和人工处置，再把样本加入回归集。

### 架构绑定供应商私有状态

先查看 **任务质量**：主指标、分层指标、置信区间和失败类型。如果证据确认失败，回到“政策/权限不用 prompt 保证”，保存触发输入、系统响应和人工处置，再把样本加入回归集。

本章的边界不是一句“视情况而定”，而是能写进测试、监测或人工审核条件的触发器。

## “系统责任与权限架构图”怎样进入真实系统

| 决定 | 验收依据 | 重新评审的信号 |
|---|---|---|
| 供应商合同覆盖数据权、日志和退出 | 训练/推理/标注成本、吞吐、容量与能耗 | 工具无幂等和撤销 |
| 多 Agent 需要证明优于单 Agent/工作流 | 漂移、越权、事故、恢复时间和残余风险 | 只看 token 单价不看总拥有成本 |

这些不是永久最佳实践，而是当前证据下的可逆决定。把决定、理由、适用范围和退出信号一起写进“系统责任与权限架构图”，否则下一次改动只能重新争论。

## 把“工具、状态与策略必须分层”迁移到新条件

围绕“工具、状态与策略必须分层”完成如下变式：对同一任务实现或详细设计简单方案和 Agent 方案；用 30 条盲测比较质量、延迟、成本、恢复，写出是否允许晋级的 ADR。

提交“系统责任与权限架构图”时同时附上：

1. 一个成功样本和一个失败样本；
2. 失败推翻了哪条假设，而不只是报错信息；
3. 哪项结论来自公开来源，哪项只来自你的本地实验；
4. 如果换数据、人群、环境或本体，最先需要重测什么；
5. 当前仍无法消除的残余风险。

- **边界：** 多 Agent 不值得使用的任务
