## 为什么现在要学“Prompt、RAG、Workflow 与 Agent 阶梯”

先别问“谁最好”。哪一种已观察失败值得购买更高系统复杂度？ 只有把约束、失败代价和退出条件放在同一张表里，选择才有意义。

**本章核心判断：** 每增加 RAG、工作流或 Agent 都在购买新故障模式，只有增量证据足以覆盖成本才升级。

本章只追一个判断：**哪一种已观察失败值得购买更高系统复杂度？** 最后必须用“复杂度升级门槛”来回答；如果产物不能暴露失败样本，就还不能算学会。

## “复杂度升级门槛”怎样进入真实系统

| 决定 | 验收依据 | 重新评审的信号 |
|---|---|---|
| 状态独立于上下文窗口持久化 | 端到端时延、成功率、降级/拒绝和人工介入 | 模型同时承担策略与执行授权 |
| 供应商合同覆盖数据权、日志和退出 | 训练/推理/标注成本、吞吐、容量与能耗 | 工具无幂等和撤销 |

这些不是永久最佳实践，而是当前证据下的可逆决定。把决定、理由、适用范围和退出信号一起写进“复杂度升级门槛”，否则下一次改动只能重新争论。

## 给“Prompt、RAG、Workflow 与 Agent 阶梯”一个可操作定义

每增加 RAG、工作流或 Agent 都在购买新故障模式，只有增量证据足以覆盖成本才升级。

可操作定义必须允许你回答三件事：输入或条件是什么，发生了哪条机制，最后观察什么才算支持结论。本章的观察出口是 **复杂度升级门槛**。

## 用公式审查“Prompt、RAG、Workflow 与 Agent 阶梯”

用 Pareto 而非单分：方案 $s$ 的向量 $(quality,latency,cost,risk,operability)$。复杂度净值 $NV_s=\Delta V_s-\Delta C_s-\Delta R_s$；当更复杂方案在盲测与线上都无可重复净优势时被支配并淘汰。

逐个把符号放回真实任务，并检查：

- 任务是否真的需要环境反馈循环
- 知识更新频率与模型截止差异
- 工具写权限和幂等/撤销能力
- 供应商数据留存、可观测和出口能力

推导完成不代表结论成立。至少改变一次关键条件，观察 **系统架构边界** 的结论是否保持；若不保持，把条件写入“复杂度升级门槛”而不是藏在代码默认值里。

## 沿着一条完整推理链走到底

### 第一步：固定要解释或改变的对象

不要用“整体效果更好”代替对象。把“哪一种已观察失败值得购买更高系统复杂度？”改写为：在明确输入、时间点和约束下，观察什么量，比较什么基线，最后据此采取什么动作。

### 第二步：写出中间机制

上一主题“先测能力边界，再画功能清单”提供前置条件，本章用 **系统架构边界** 解释关键机制，并把结果留在“复杂度升级门槛”中。下一主题“工具、状态与策略必须分层”只在这些证据成立后继续。 只要中间任一环只能凭主观解释，结论就应降级为假设。

### 第三步：主动寻找反例

先尝试制造“只看 token 单价不看总拥有成本”。如果当前方法仍给出看似正常的平均分，说明评价没有覆盖真正风险，需要补切片、过程指标或拒绝条件。

### 第四步：把结论写成可撤回决定

当前决定是“状态独立于上下文窗口持久化”。同时写下适用条件、责任人和重新评审信号；这样新证据出现时能更新，而不是把旧结论当永久规则。

这条推理链最终必须落到 **复杂度升级门槛**。只有定义、机制、观察和决定互相对得上，文章内容才真正进入工作系统。

## 把“Prompt、RAG、Workflow 与 Agent 阶梯”做成可重放实验

实验标题：**复杂度升级门槛**。不要同时追求完整系统，只要求输入可重放、判断可观测、失败可解释。

### 1. 冻结问题和验收

把“哪一种已观察失败值得购买更高系统复杂度？”写成输入、条件、基线和通过阈值，禁止实验后改题。

- **必须保存：** 问题卡、数据/环境版本和预期失败。
- **停止信号：** 模型同时承担策略与执行授权。

### 2. 执行本章关键动作

从最低复杂度实现可运行基线

- **必须保存：** 端到端时延、成功率、降级/拒绝和人工介入。
- **停止信号：** 工具无幂等和撤销。

### 3. 主动注入反例

构造“模型同时承担策略与执行授权”，验证评价或安全控制是否真的能发现。

- **必须保存：** 触发输入、完整过程和系统响应。
- **停止信号：** 只看 token 单价不看总拥有成本。

### 4. 比较并做决定

把结果与两份来源的任务和边界对齐，决定继续、降级、拒绝或补证据。

- **必须保存：** 复杂度升级门槛及其适用范围。
- **停止信号：** 架构绑定供应商私有状态。

## 当 系统架构边界 失效，先查哪里

先排除这些看似合理的误解：Agent 比 workflow 更先进；模型卡等于独立验证；多模型投票必然可靠；Build 可避免锁定；Prompt 能执行权限。

### 模型同时承担策略与执行授权

先查看 **系统表现**：端到端时延、成功率、降级/拒绝和人工介入。如果证据确认失败，回到“状态独立于上下文窗口持久化”，保存触发输入、系统响应和人工处置，再把样本加入回归集。

### 只看 token 单价不看总拥有成本

先查看 **风险运维**：漂移、越权、事故、恢复时间和残余风险。如果证据确认失败，回到“多 Agent 需要证明优于单 Agent/工作流”，保存触发输入、系统响应和人工处置，再把样本加入回归集。

本章的边界不是一句“视情况而定”，而是能写进测试、监测或人工审核条件的触发器。

## 能力阶梯 怎样经过 系统架构边界 影响结果

层级可写为规则/搜索→单模型结构输出→RAG→确定性 workflow→带工具单 Agent→多 Agent。知识放外部可更新层，权限由工具网关控制，状态与模型上下文分离，关键策略用代码/政策执行。每层绑定失败本体、增量收益和回退路径。

~~~~mermaid
flowchart LR
 R[规则/搜索] --> M[单模型]
 M --> G[RAG]
 G --> W[确定性工作流]
 W --> A[工具型 Agent]
 A --> X[多 Agent]
 F[观测失败+盲测收益] -.晋级.-> G
 F -.晋级.-> A
 X --> B[可回退边界]
~~~~

读图时从结果逆向追问：哪一步能够观察，哪一步只是假设，哪一步失效后必须让系统拒绝或降级。

## 把“Prompt、RAG、Workflow 与 Agent 阶梯”迁移到新条件

围绕“Prompt、RAG、Workflow 与 Agent 阶梯”完成如下变式：对同一任务实现或详细设计简单方案和 Agent 方案；用 30 条盲测比较质量、延迟、成本、恢复，写出是否允许晋级的 ADR。

提交“复杂度升级门槛”时同时附上：

1. 一个成功样本和一个失败样本；
2. 失败推翻了哪条假设，而不只是报错信息；
3. 哪项结论来自公开来源，哪项只来自你的本地实验；
4. 如果换数据、人群、环境或本体，最先需要重测什么；
5. 当前仍无法消除的残余风险。

## 本章小结

- **问题：** 哪一种已观察失败值得购买更高系统复杂度？
- **机制：** 模型强不等于系统应复杂；每增加检索、工具或自主循环，都必须由一种已观测失败和一套新评价证据来购买。
- **产物：** 复杂度升级门槛
- **边界：** 多 Agent 不值得使用的任务
