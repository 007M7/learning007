## 为什么现在要学“先测能力边界，再画功能清单”

这是一章可以重放的实验。先冻结输入、基线和停止条件，再让结果回答问题，而不是边跑边改结论。

**本章核心判断：** 能力矩阵必须按任务切片、输入条件和版本记录成功、拒绝与失败，而不是列宣传能力。

本章只追一个判断：**模型在哪些任务切片、语言和输入条件下稳定？** 最后必须用“能力矩阵与拒绝边界”来回答；如果产物不能暴露失败样本，就还不能算学会。

## 把“先测能力边界，再画功能清单”做成可重放实验

实验标题：**能力矩阵与拒绝边界**。不要同时追求完整系统，只要求输入可重放、判断可观测、失败可解释。

### 1. 冻结问题和验收

把“模型在哪些任务切片、语言和输入条件下稳定？”写成输入、条件、基线和通过阈值，禁止实验后改题。

- **必须保存：** 问题卡、数据/环境版本和预期失败。
- **停止信号：** 把 Agent 当默认 UI。

### 2. 执行本章关键动作

列出每个失败应由知识、模型、流程或权限哪层处理

- **必须保存：** 主指标、分层指标、置信区间和失败类型。
- **停止信号：** 模型同时承担策略与执行授权。

### 3. 主动注入反例

构造“把 Agent 当默认 UI”，验证评价或安全控制是否真的能发现。

- **必须保存：** 触发输入、完整过程和系统响应。
- **停止信号：** 工具无幂等和撤销。

### 4. 比较并做决定

把结果与两份来源的任务和边界对齐，决定继续、降级、拒绝或补证据。

- **必须保存：** 能力矩阵与拒绝边界及其适用范围。
- **停止信号：** 只看 token 单价不看总拥有成本。

## 给“先测能力边界，再画功能清单”一个可操作定义

能力矩阵必须按任务切片、输入条件和版本记录成功、拒绝与失败，而不是列宣传能力。

可操作定义必须允许你回答三件事：输入或条件是什么，发生了哪条机制，最后观察什么才算支持结论。本章的观察出口是 **能力矩阵与拒绝边界**。

### 三个支撑概念，而不是本章的替代标题

| 位置 | 概念 | 在本章中的作用 | 一旦误用会怎样 |
|---|---|---|---|
| 前置 | Build/Buy/Portability | 能力、数据权、锁定、成本和运营共同决定选型 | 把 Agent 当默认 UI |

| 下游 | 系统架构边界 | 模型、知识、工具、状态、策略和安全控制分层 | 模型同时承担策略与执行授权 |

## 沿着一条完整推理链走到底

### 第一步：固定要解释或改变的对象

不要用“整体效果更好”代替对象。把“模型在哪些任务切片、语言和输入条件下稳定？”改写为：在明确输入、时间点和约束下，观察什么量，比较什么基线，最后据此采取什么动作。

### 第二步：写出中间机制

上一主题“别把旧流程照搬：重做任务边界”提供前置条件，本章用 **能力阶梯** 解释关键机制，并把结果留在“能力矩阵与拒绝边界”中。下一主题“Prompt、RAG、Workflow 与 Agent 阶梯”只在这些证据成立后继续。 只要中间任一环只能凭主观解释，结论就应降级为假设。

### 第三步：主动寻找反例

先尝试制造“工具无幂等和撤销”。如果当前方法仍给出看似正常的平均分，说明评价没有覆盖真正风险，需要补切片、过程指标或拒绝条件。

### 第四步：把结论写成可撤回决定

当前决定是“政策/权限不用 prompt 保证”。同时写下适用条件、责任人和重新评审信号；这样新证据出现时能更新，而不是把旧结论当永久规则。

这条推理链最终必须落到 **能力矩阵与拒绝边界**。只有定义、机制、观察和决定互相对得上，文章内容才真正进入工作系统。

## “模型在哪些任务切片、语言和输入条件下稳定？”依赖哪些前提

本章暂时不展开整套推导，但必须把判断拆成可以检查的前提：

| 顺序 | 必须成立的前提 | 对应控制 |
|---|---|---|
| 1 | 任务是否真的需要环境反馈循环；在“先测能力边界，再画功能清单”中必须显式核对 | 政策/权限不用 prompt 保证 |
| 2 | 知识更新频率与模型截止差异；在“先测能力边界，再画功能清单”中必须显式核对 | 状态独立于上下文窗口持久化 |
| 3 | 工具写权限和幂等/撤销能力；在“先测能力边界，再画功能清单”中必须显式核对 | 供应商合同覆盖数据权、日志和退出 |
| 4 | 供应商数据留存、可观测和出口能力；在“先测能力边界，再画功能清单”中必须显式核对 | 多 Agent 需要证明优于单 Agent/工作流 |

这四项共同约束“模型在哪些任务切片、语言和输入条件下稳定？”。任何一项只能靠猜测回答时，都应降低结论强度或补实验。

## 两份证据把“先测能力边界，再画功能清单”的边界画在哪里

### Building Effective Agents（2024-12-19）

这项工作追问：什么时候使用 workflow，什么时候使用 agent？

文章区分预定义代码路径的 workflow 与模型动态决定过程的 agent，并给出 routing、parallelization、orchestrator-worker 等模式。 实践建议从简单可组合模式开始，只在任务需要时增加自主性。

本章据此采用的判断是：**形成产品/架构共同的复杂度语言。** 但不能外推到：厂商实践文章不是独立对照实验，模式须用本地任务证据选择。

### Model Cards（2019-01-28）

本章用它校准“先测能力边界，再画功能清单”的边界：把供应商模型能力主张转成可审查输入。。**不要越过的边界：**卡片由提供方编写，需独立验证且常缺系统级风险。

两份来源若结论看似冲突，先比较任务定义、数据分布、资源预算和评价方法；不能只用发布日期或排行榜高低裁决。

## “能力矩阵与拒绝边界”怎样进入真实系统

| 决定 | 验收依据 | 重新评审的信号 |
|---|---|---|
| 政策/权限不用 prompt 保证 | 主指标、分层指标、置信区间和失败类型 | 把 Agent 当默认 UI |
| 状态独立于上下文窗口持久化 | 端到端时延、成功率、降级/拒绝和人工介入 | 模型同时承担策略与执行授权 |

这些不是永久最佳实践，而是当前证据下的可逆决定。把决定、理由、适用范围和退出信号一起写进“能力矩阵与拒绝边界”，否则下一次改动只能重新争论。

## 当 能力阶梯 失效，先查哪里

先排除这些看似合理的误解：Agent 比 workflow 更先进；模型卡等于独立验证；多模型投票必然可靠；Build 可避免锁定；Prompt 能执行权限。

### 把 Agent 当默认 UI

先查看 **任务质量**：主指标、分层指标、置信区间和失败类型。如果证据确认失败，回到“政策/权限不用 prompt 保证”，保存触发输入、系统响应和人工处置，再把样本加入回归集。

### 工具无幂等和撤销

先查看 **资源经济**：训练/推理/标注成本、吞吐、容量与能耗。如果证据确认失败，回到“供应商合同覆盖数据权、日志和退出”，保存触发输入、系统响应和人工处置，再把样本加入回归集。

本章的边界不是一句“视情况而定”，而是能写进测试、监测或人工审核条件的触发器。

## 把“先测能力边界，再画功能清单”迁移到新条件

围绕“先测能力边界，再画功能清单”完成如下变式：对同一任务实现或详细设计简单方案和 Agent 方案；用 30 条盲测比较质量、延迟、成本、恢复，写出是否允许晋级的 ADR。

提交“能力矩阵与拒绝边界”时同时附上：

1. 一个成功样本和一个失败样本；
2. 失败推翻了哪条假设，而不只是报错信息；
3. 哪项结论来自公开来源，哪项只来自你的本地实验；
4. 如果换数据、人群、环境或本体，最先需要重测什么；
5. 当前仍无法消除的残余风险。

- **问题：** 模型在哪些任务切片、语言和输入条件下稳定？

- **边界：** 多 Agent 不值得使用的任务
