# 03 · 能力边界与方案选型

> 模型强不等于系统应复杂；每增加检索、工具或自主循环，都必须由一种已观测失败和一套新评价证据来购买。

## 先别问谁最好，先问你在优化什么

> Prompt、RAG、工作流、Agent、微调应按什么证据升级？

团队把 FAQ 直接设计成多 Agent，结果延迟、费用和不可复现错误暴涨。真正需求是版本化知识检索加三个确定性动作。应先用单调用+约束输出，只有跨步骤环境反馈确实必要才引入 Agent 循环。

## 把选择拆成三条判断轴

| 知识节点 | 先用一句话说清 | 什么时候值得选择它 | 先排除的误解 |
|---|---|---|---|
| AIPM07 · 能力阶梯 | 确定性流程到开放 Agent 的不确定性逐级增加 | 最小方案能否达成任务 | Agent 比 workflow 更先进 |
| AIPM08 · 系统架构边界 | 模型、知识、工具、状态、策略和安全控制分层 | 错误由哪一层检测和恢复 | 模型卡等于独立验证 |
| AIPM09 · Build/Buy/Portability | 能力、数据权、锁定、成本和运营共同决定选型 | 供应商变化时能否迁移 | 多模型投票必然可靠 |

读表时不要横向背三行。任选一行，把“定义—决定—反例”连成一句因果解释；然后把本章案例中的一个输入替换掉，检查原判断是否仍成立。

## 判断树：从调用到 Agent 的复杂度晋级

层级可写为规则/搜索→单模型结构输出→RAG→确定性 workflow→带工具单 Agent→多 Agent。知识放外部可更新层，权限由工具网关控制，状态与模型上下文分离，关键策略用代码/政策执行。每层绑定失败本体、增量收益和回退路径。

~~~~mermaid
flowchart LR
 R[规则/搜索] --> M[单模型]
 M --> G[RAG]
 G --> W[确定性工作流]
 W --> A[工具型 Agent]
 A --> X[多 Agent]
 F[观测失败+盲测收益] -.晋级.-> G
 F -.晋级.-> A
 X --> B[可回退边界]
~~~~

## 不要让一个分数替你做决定

用 Pareto 而非单分：方案 $s$ 的向量 $(quality,latency,cost,risk,operability)$。复杂度净值 $NV_s=\Delta V_s-\Delta C_s-\Delta R_s$；当更复杂方案在盲测与线上都无可重复净优势时被支配并淘汰。

把每个符号放回真实系统。下面任何一项说不清，计算正确也不能保证结论正确：

- 任务是否真的需要环境反馈循环
- 知识更新频率与模型截止差异
- 工具写权限和幂等/撤销能力
- 供应商数据留存、可观测和出口能力

## 做到什么，才算结果可信

| 观察维度 | 要留下的记录 | 它防止你误判什么 |
|---|---|---|
| 任务质量 · 能力阶梯 | 主指标、分层指标、置信区间和失败类型 | 平均分不能说明关键场景是否可用；本章还要据此判断：最小方案能否达成任务 |
| 系统表现 · 系统架构边界 | 端到端时延、成功率、降级/拒绝和人工介入 | 局部模型分数不是用户任务结果；本章还要据此判断：错误由哪一层检测和恢复 |
| 资源经济 · Build/Buy/Portability | 训练/推理/标注成本、吞吐、容量与能耗 | 确认改进在真实预算下仍成立；本章还要据此判断：供应商变化时能否迁移 |
| 风险运维 · 能力阶梯 | 漂移、越权、事故、恢复时间和残余风险 | 把一次实验转化成可持续服务；本章还要据此判断：最小方案能否达成任务 |

## 不要只看宣传：两份可核验依据

公开结果可以帮助设置基线，却不能替代你自己的数据、预算和失败代价。

### Building Effective Agents（2024-12-19）

先看这份来源时，要带着一个具体问题：什么时候使用 workflow，什么时候使用 agent？

文章区分预定义代码路径的 workflow 与模型动态决定过程的 agent，并给出 routing、parallelization、orchestrator-worker 等模式。 实践建议从简单可组合模式开始，只在任务需要时增加自主性。 因此，本章采用它来支持这样的判断：形成产品/架构共同的复杂度语言。

但它没有替我们回答所有问题。厂商实践文章不是独立对照实验，模式须用本地任务证据选择。

### Model Cards（2019-01-28）

最后看这份来源时，要带着一个具体问题：购买或集成模型时需要什么能力边界？

模型卡记录用途、非用途、评测条件、群体表现和限制。 案例说明单一榜分不足以支持部署选择。 因此，本章采用它来支持这样的判断：把供应商模型能力主张转成可审查输入。

但它没有替我们回答所有问题。卡片由提供方编写，需独立验证且常缺系统级风险。

## 一次有约束的选择：企业 FAQ 到工单 Agent

先用检索+引用回答，写操作必须经三个固定 workflow。只有当用户目标需跨系统追踪且预定流程覆盖率不足时，试验工具 Agent；写动作 sandbox、权限最小化、幂等键、预览确认和审计齐备。比较任务成功、人工分钟、P95、严重错误和恢复时间。

### 读案例时做三次停顿

1. 到 能力阶梯 时停一次：最小方案能否达成任务？
2. 到 系统架构边界 时再停一次：哪条数据流、状态变化或约束能证明机制真的发生？
3. 到 Build/Buy/Portability 时最后停一次：如果出现“把 Agent 当默认 UI”，系统应继续、拒绝还是交给人？

## 做一次公平对照：完成一次复杂度消融

### 第 1 步：列出每个失败应由知识、模型、流程或权限哪层处理

- **这一步在验证：** 能力阶梯能否支持“最小方案能否达成任务”这项判断。
- **至少留下：** 主指标、分层指标、置信区间和失败类型。
- **先停下来而不是继续调参的信号：** 把 Agent 当默认 UI。

### 第 2 步：从最低复杂度实现可运行基线

- **这一步在验证：** 系统架构边界能否支持“错误由哪一层检测和恢复”这项判断。
- **至少留下：** 端到端时延、成功率、降级/拒绝和人工介入。
- **先停下来而不是继续调参的信号：** 模型同时承担策略与执行授权。

### 第 3 步：每次只加一层并做盲测/成本消融

- **这一步在验证：** Build/Buy/Portability能否支持“供应商变化时能否迁移”这项判断。
- **至少留下：** 训练/推理/标注成本、吞吐、容量与能耗。
- **先停下来而不是继续调参的信号：** 工具无幂等和撤销。

### 第 4 步：演练供应商不可用、模型降级和数据迁移

- **这一步在验证：** 能力阶梯能否支持“最小方案能否达成任务”这项判断。
- **至少留下：** 漂移、越权、事故、恢复时间和残余风险。
- **先停下来而不是继续调参的信号：** 只看 token 单价不看总拥有成本。

完成示范后再做一次变式：对同一任务实现或详细设计简单方案和 Agent 方案；用 30 条盲测比较质量、延迟、成本、恢复，写出是否允许晋级的 ADR。

## 什么信号会推翻当前选择

先排除这些误解：Agent 比 workflow 更先进；模型卡等于独立验证；多模型投票必然可靠；Build 可避免锁定；Prompt 能执行权限。

### 把 Agent 当默认 UI

- **先看什么：** 主指标、分层指标、置信区间和失败类型
- **回到哪项控制：** 政策/权限不用 prompt 保证
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“完成一次复杂度消融”的回归记录。

### 模型同时承担策略与执行授权

- **先看什么：** 端到端时延、成功率、降级/拒绝和人工介入
- **回到哪项控制：** 状态独立于上下文窗口持久化
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“完成一次复杂度消融”的回归记录。

### 工具无幂等和撤销

- **先看什么：** 训练/推理/标注成本、吞吐、容量与能耗
- **回到哪项控制：** 供应商合同覆盖数据权、日志和退出
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“完成一次复杂度消融”的回归记录。

### 只看 token 单价不看总拥有成本

- **先看什么：** 漂移、越权、事故、恢复时间和残余风险
- **回到哪项控制：** 多 Agent 需要证明优于单 Agent/工作流
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“完成一次复杂度消融”的回归记录。

### 架构绑定供应商私有状态

- **先看什么：** 主指标、分层指标、置信区间和失败类型
- **回到哪项控制：** 政策/权限不用 prompt 保证
- **怎样留下证据：** 保存触发条件、原始输入、系统响应和人工处置；修复后把同一样本加入“完成一次复杂度消融”的回归记录。

## 证据改变时怎样重选

### 1. 政策/权限不用 prompt 保证

验收时查看 **任务质量**，至少保存主指标、分层指标、置信区间和失败类型。如果观察到“把 Agent 当默认 UI”，这项决定必须重新评审，不能因为已经实现就默认保留。

### 2. 状态独立于上下文窗口持久化

验收时查看 **系统表现**，至少保存端到端时延、成功率、降级/拒绝和人工介入。如果观察到“模型同时承担策略与执行授权”，这项决定必须重新评审，不能因为已经实现就默认保留。

### 3. 供应商合同覆盖数据权、日志和退出

验收时查看 **资源经济**，至少保存训练/推理/标注成本、吞吐、容量与能耗。如果观察到“工具无幂等和撤销”，这项决定必须重新评审，不能因为已经实现就默认保留。

### 4. 多 Agent 需要证明优于单 Agent/工作流

验收时查看 **风险运维**，至少保存漂移、越权、事故、恢复时间和残余风险。如果观察到“只看 token 单价不看总拥有成本”，这项决定必须重新评审，不能因为已经实现就默认保留。

## 本章小结

- 复杂度必须由失败证据购买
- 架构分离知识、状态、策略和权限
- Pareto 选型包含运营与退出
- 自主性越高门禁越强
