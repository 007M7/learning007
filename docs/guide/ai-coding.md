# 怎样与 AI 协作编码

AI 编码的核心不是更长 Prompt，而是让需求、约束、验证和改动边界可见。

## 一次安全协作循环

```text
1. Context：目标、现状、文件、约束、非目标
2. Contract：输入、输出、不变量、错误、权限
3. Plan：要求 AI 先列假设、风险、文件清单和验证
4. Slice：一次只实现最小纵向切片
5. Inspect：看 diff 和数据/权限/失败路径
6. Verify：运行测试、构建、迁移/恢复或评测
7. Record：提交、ADR、剩余风险和下一步
```

## 可直接复用的任务说明

```markdown
目标：用户能够 [可观察结果]。
现状：入口/相关文件/当前行为是 [...]。
必须保持：接口兼容、租户隔离、数据不变量 [...]。
非目标：本次不做 [...]。
异常与边界：[...]。
允许修改：[...]；禁止修改：[...]。
完成标准：测试/构建/日志/迁移/截图/评测 [...]。

先不要改代码：
1. 区分事实、假设和未知；
2. 画调用/数据流；
3. 列出最多 3 个方案与取舍；
4. 给出最小文件清单和验证命令。
```

## 审查 AI 结果的七扇门

| 门 | 你要问 |
|---|---|
| 需求 | 是否真的满足验收，而非只让 happy path 能跑？ |
| 数据 | 约束、事务、迁移、删除与并发怎样处理？ |
| 权限 | 身份/租户来自可信边界吗？每个资源都重新授权吗？ |
| 契约 | 类型、运行时验证、错误、幂等、超时兼容吗？ |
| 故障 | 重试、重复、取消、崩溃、部分成功会怎样？ |
| 质量 | 哪一层测试/构建/评测能独立证明？ |
| 运维 | 日志/trace/指标、回滚、恢复和成本可见吗？ |

## 三个危险信号

“应该可以”“通常没问题”却没有运行证据；一次改很多无关文件；为了修复症状关闭类型/测试/权限。遇到时让 AI 缩小 diff、复现事实、解释根因，再决定。

## 你真正积累的 SOP

保存的不是某次 Prompt，而是：需求画布、状态表、API/工具 Schema、测试矩阵、ADR、发布/恢复记录、评测集和事故复盘。它们能跨模型和工具复用，才构成工作复利。
